# Git: Rebase 与 Merge 的实战抉择

> 在日常团队协作中，合并分支的策略选择一直是“圣战”。本文从底层原理和实战场景出发，解释这两种策略的本质区别。

## 1. 核心原理对比

### Git Merge
`git merge feature` 
- **行为**：Git 会寻找你当前所在分支和 `feature` 分支的共同祖先节点，并自动创建一个全新的“合并提交（Merge Commit）”，将两条分支的历史线路缝合在一起。
- **优点**：真实、无损地保留了分支开发的所有历史痕迹。
- **缺点**：如果频繁合并主干，分支网络图会变成复杂的蜘蛛网（铁路图），非常难以进行 `git log` 的追溯和审查。

### Git Rebase (变基)
`git rebase master` (在 feature 分支上执行)
- **行为**：把 `feature` 分支上所有的独有 commit “拔”下来，暂时存放在 `.git/rebase-apply` 中；然后把 `feature` 分支更新到最新的 `master` 节点上；最后把刚才“拔”下来的 commit 一个个“重新回放（Replay）”在这个最新的节点上。
- **优点**：创造了一条完美的**线性历史**，Git 提交线像一条笔直的直线，极致干净。
- **缺点**：它**重写了提交历史**。重新回放生成的 commit 虽然内容一样，但因为父节点变了，它们的 Commit Hash（哈希值）全都变了。

## 2. 团队协作中的黄金准则

业界流传着一个极其重要且必须遵守的黄金法则：
> **绝对不要在公共的（已经推送到远端、并且别人可能正在基于它开发的）分支上使用 `git rebase`。**

### 为什么？
假设你在远程的 `develop` 分支上做了一次 rebase 并强制推送。你的同事刚刚拉取过代码，在他的本地，这些 commit 的 hash 还是旧的。当他再次拉取或推送时，Git 会认为远端是一套全新的历史，本地是一套历史，强行合并后会导致大量的重复提交和恶心的冲突，整个团队的代码库会陷入极度混乱。

### 最佳实践场景推荐

✅ **使用 `git rebase` 的绝佳场景**：
- **在你个人的本地特性分支（Feature Branch）上，为了同步主干的最新代码**。
  （做法：`git fetch origin` 然后 `git rebase origin/master`）。这既能让你拿到同事刚提交的最新功能，又能保证你的分支推送到远端 PR（Pull Request）时，评审者看到的是一条干净的直线提交记录。
- **合并前清理自己散乱的本地提交**。
  （做法：`git rebase -i HEAD~4` 交互式变基，使用 `squash` 将多个 "fix bug" / "update typo" 这种低质量的琐碎提交合并为一个完整的功能提交）。

✅ **使用 `git merge` 的绝佳场景**：
- **将特性分支合并到主干分支（Master / Main）时**。
  （做法：在 GitHub/GitLab 上点击 `Merge Pull Request`，通常会产生一个合并提交）。因为这个合并提交能清晰地标记出“某个特定功能是在何时合入主干的”，如果未来发现这个功能有致命 bug，通过这个 Merge Commit 可以方便地一键还原整个功能的代码。

---
**一句话总结**：
- 在个人的私有分支开发中：尽情使用 `Rebase`，保持提交的线性与整洁。
- 在跨团队的主干分支集成时：严格使用 `Merge`，真实记录特性的汇入点。
