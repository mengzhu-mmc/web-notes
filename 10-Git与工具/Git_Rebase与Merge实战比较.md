# Git: Rebase 与 Merge 的实战抉择（通俗易懂版）

很多刚接触 Git 的开发者会觉得：`merge` 就是合并，`rebase` 也是合并，它们不就是把代码拼在一起吗？什么叫“一个有历史记录，一个没有历史”？为什么非要找“公共祖先”？

这里我们换一个更通俗的比喻，并配上 ASCII 示意图，帮你彻底搞懂它们的底层逻辑。

## 1. 为什么一定要找“公共祖先”？

Git 并不是简单地把两个文本文件的内容“加”在一起（像复制粘贴那样）。如果你改了第 5 行，我也改了第 5 行，Git 怎么知道谁对谁错？
因此，Git 需要找一个**参照物**——也就是你们两个人**分道扬镳之前的那一次提交**，这就是“公共祖先”。
Git 会分别算出：你相对于祖先改了什么，我相对于祖先改了什么，然后再把这两份“修改量”融合在一起。

## 2. 通俗比喻与示意图

假设我们在开发一个项目，`主干(Master)` 是公路，`特性分支(Feature)` 是你开出去修的一条辅路。

### Git Merge：修建一座立交桥

`git merge feature`（在主干上执行）

**通俗比喻**：
你（Feature）在辅路上修了几个月，现在要和主干道（Master）汇合。`Merge` 的做法是：**保留你的辅路原样不动，在两条路的尽头，修一座“立交桥”（也就是 Merge Commit）把它们连接起来。**

**示意图**：

```text
           A---B---C (Feature 分支: 你的开发记录)
          /         \
D---E---F------------G (Master 分支: 主干道)
(祖先)              (合并节点 / Merge Commit)
```

- **特点**：你的开发记录（A、B、C）完好无损地被保留了，并且多出了一个明确的节点 `G`。
- **你理解的“有历史记录”**：就是指这条分叉的“辅路”轨迹被永远记录在了 Git 树上。以后别人一看图谱，就知道在这段时间里，有一条独立的分支曾经存在过。

---

### Git Rebase (变基)：连根拔起，移花接木

`git rebase master`（在 Feature 分支上执行）

**通俗比喻**：
`Base` 就是“基底/起点”。`Rebase` 就是“改变你的起点”。
Git 发现你的辅路是从历史上的 `F` 点开出去的，而现在主干已经修到了 `H`。Git 会**把你的辅路整个“连根拔起”，然后原封不动地移植到主干最新的尽头 `H` 上面**。

**示意图**：
**Rebase 之前**：

```text
           A---B---C (Feature 分支: 你的开发记录)
          /
D---E---F---G---H (Master 分支: 主干道别人新提交的代码)
(祖先)
```

**Rebase 之后**：

```text
                  A'---B'---C' (Feature 分支被“移花接木”到了最前面)
                 /
D---E---F---G---H (Master 分支)
```

- **特点**：分叉不见了！所有的提交变成了一条笔直的线（线性历史）。没有产生任何像立交桥那样的合并节点。
- **你理解的“没有历史记录”**：并不是说你的代码没了，而是**你的“分叉痕迹”被抹除了**。看起来就像是你昨天才刚基于最新代码写完的，假装你从来没和别人兵分两路过。
- **注意**：图里的 `A'` 意味着虽然代码内容没变，但因为它的起点变了（从 F 变成了 H），Git 把它当成了一个**全新**的提交，生成了新的哈希值。

## 3. 团队协作中的黄金准则

业界流传着一个极其重要且必须遵守的黄金法则：

> **绝对不要在公共的（已经推送到远端、并且别人可能正在基于它开发的）分支上使用 `git rebase`。**

### 为什么？

因为 Rebase 是“连根拔起，重新生成提交”。如果你在公共分支上拔树，而你的同事还在那棵旧树上继续干活。等他提交时，Git 会认为你们完全不在一个世界，强行合并会导致毁灭性的冲突。

### 最佳实践场景推荐

✅ **使用 `git rebase` 的绝佳场景（修剪自己的草坪）**：

- **在你自己本地还没推到远程的分支上，同步最新主干代码**。
  （做法：`git fetch origin` 然后 `git rebase origin/master`）。这既能让你解决掉落后的问题，推送到远程时又能保持提交记录干净整洁，没有恶心的分叉。

✅ **使用 `git merge` 的绝佳场景（修建公共立交桥）**：

- **把一个已经开发完的功能分支合入到主干时**。
  （在 GitHub 上点 `Merge Pull Request`）。因为合并节点能清晰地记录“某年某月某日，XX功能作为一个整体合入了主干”。如果未来代码崩了，可以通过这个节点一把撤回（Revert）。

---

**一句话总结**：

- **Rebase 是为了掩盖分叉痕迹，把自己的历史变得像一条直线，适合本地自娱自乐。**
- **Merge 是为了保留真实的开发轨迹，并生成一个明确的合并点，适合跨团队大集成。**
