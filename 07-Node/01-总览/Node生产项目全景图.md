## 二、逐层说明：这一层解决什么问题、不做会出什么事故

### 2.1 CDN / Nginx 层

| 项 | 内容 |
| --- | --- |
| **解决什么** | TLS 卸载、静态资源不打到 Node、连接复用、请求体大小限制、超时兜底 |
| **不做的后果** | Node 直接暴露在公网，被慢连接（Slowloris）拖住；大文件上传打爆内存；静态资源占满 Node 的事件循环 |
| **真实事故** | 某活动页把图片放在 Node 的 `koa-static` 上直出，大促时静态请求占了 90% 的连接数，接口请求排队超时。修复：静态资源全量迁 CDN/OSS |

### 2.2 网关层

| 项 | 内容 |
| --- | --- |
| **解决什么** | 全局限流、鉴权前置、灰度路由、黑白名单、统一访问日志 |
| **不做的后果** | 恶意刷接口直达业务进程；无法在不发版的情况下做流量切分 |
| **真实事故** | 没有网关限流，某爬虫以 2000 QPS 拉列表接口，DB 连接池耗尽，正常用户全部报错。修复：网关按 IP + 用户维度限流，Node 内再加一层兜底限流 |

### 2.3 进程集群层

| 项 | 内容 |
| --- | --- |
| **解决什么** | Node 单进程只用一个核，必须靠多进程/多副本吃满多核；单进程崩溃时保证服务可用 |
| **不做的后果** | 8 核机器只跑一个进程 → 87% 的 CPU 闲置；进程崩了没人重启 → 服务直接下线 |
| **真实事故** | 单进程部署，一个未捕获异常导致进程退出，服务全挂 4 分钟。修复：K8s 多副本 + `restartPolicy`，或 cluster 主进程监听 `exit` 事件重新 fork（示例见 [Node.js 面试核心知识点](../Node.js面试核心知识点.md) 5.2 节） |

**选择建议**：在 K8s 环境下优先用「单容器单进程 + 多副本」，让编排系统负责重启与扩缩；`cluster` 更适合裸机/单机部署。两者叠加（多副本 × 每副本多进程）时要特别注意下一节的连接池乘法。

### 2.4 中间件链

洋葱模型的顺序不是随意的，**顺序错了等于没做**。

```javascript
// ✅ 正确顺序：外层先执行、后收尾
app.use(traceIdMiddleware);   // 1. 最外层：先有 traceId，后面的日志才能关联
app.use(accessLogMiddleware); // 2. 记录请求进入 + 响应耗时（洋葱的前后两半）
app.use(errorMiddleware);     // 3. 错误兜底：要能捕获它内层的所有异常
app.use(bodyParser);          // 4. 解析请求体（必须限制大小）
app.use(rateLimitMiddleware); // 5. 限流：放在鉴权前，防止未登录流量打穿
app.use(authMiddleware);      // 6. 鉴权
app.use(validateMiddleware);  // 7. 参数校验：脏数据不许进入业务层
app.use(router.routes());     // 8. 业务

// ❌ 常见错序 1：错误中间件挂在最后 → 它内层没有东西，什么也捕获不到
// ❌ 常见错序 2：traceId 挂在日志之后 → 日志里没有 traceId，排障时无法串联
// ❌ 常见错序 3：限流挂在鉴权之后 → 攻击者用无效 token 就能压垮 JWT 验签的 CPU 开销
```

| 项 | 内容 |
| --- | --- |
| **不做的后果** | 无 traceId → 线上报错只能靠时间戳猜是哪条请求；无参数校验 → `undefined` 进 SQL 或全表扫描；无限流 → 单个客户端拖垮全站 |
| **真实事故** | 上传接口没限制 body 大小，用户传了 200MB 文件，进程内存瞬间打满被 OOM Kill。修复：Nginx 层 `client_max_body_size` + body parser 的 `maxFileSize` 双重限制 |

### 2.5 Service 层与请求上下文

| 项 | 内容 |
| --- | --- |
| **解决什么** | 业务编排、事务边界、领域逻辑归属；请求态（userId / traceId）的正确传递 |
| **不做的后果** | 业务逻辑散落在 Controller 里，无法复用与测试；请求态存错位置 → 数据串号 |
| **真实事故（最经典）** | 模块级变量存当前用户 → 用户 A 看到用户 B 的数据。原因是服务端一个进程服务所有用户，模块级变量是全局共享的，不是每用户一份 |

```javascript
// ❌ 事故代码：模块级变量存请求态
let currentUserId = null;
async function setUser(id) { currentUserId = id; }
async function listTodos() {
  return Todo.findAll({ where: { userId: currentUserId } }); // 并发下必然串号
}

// ✅ 方案 1（显式传参）：你的 Todo 项目用的就是这种，简单可靠
async function listTodos(userId) {
  return Todo.findAll({ where: { userId } });
}

// ✅ 方案 2（AsyncLocalStorage）：traceId 这类跨层数据用它，避免层层穿透
// 完整示例见 ../Node.js现代特性与新API.md 第四章
const store = requestContext.getStore();
logger.info("查询列表", { traceId: store.traceId, userId: store.userId });
```

### 2.6 数据层：连接池、缓存、事务

**连接池是最容易算错的一格。** 记住这个乘法：

```
数据库实际被占用的连接数 = 副本数 × 每副本进程数 × 单进程连接池 max

举例：K8s 4 副本 × cluster 4 进程 × pool.max 10 = 160 个连接
      而 MySQL 的 max_connections 默认是 151
      → 扩容到第 4 个副本时，DB 开始拒连
      → 所有服务（包括其他共用这个 DB 的服务）一起雪崩

正确做法：
  1. 先确认 DB 的 max_connections，并预留给运维/其他服务的余量
  2. 反推单进程 pool.max = (可用连接数 × 0.8) / (副本数 × 每副本进程数)
  3. 关键：pool.max 大不等于快。连接数超过 DB 的 CPU 核数后，
     吞吐不再上升反而因锁竞争下降。宁可让请求在应用侧排队等连接，
     也不要把压力推给 DB。
  4. 必须配 acquire 超时，拿不到连接要快速失败，而不是无限等待
```

对照你的 Todo 项目 `src/config/db.js`：`pool.max = 10`、`acquire = 30000`。单机开发没问题，但 `acquire` 30 秒太长——生产环境下 30 秒的等待意味着上游早就超时了，请求还在占着内存。生产建议压到 3 到 5 秒并配合明确的错误码。

| 项 | 内容 |
| --- | --- |
| **缓存不做的后果** | 热点数据每次打 DB，QPS 上不去；缓存做错 → 缓存穿透（查不存在的 key 全部落 DB）、缓存雪崩（大量 key 同时过期）、数据不一致 |
| **事务不做的后果** | 多表写入部分成功，数据永久不一致。注意：Sequelize 里不显式传 `transaction` 参数的查询**不在事务内** |
| **超时不做的后果** | 下游卡住 → 请求堆积 → 内存上涨 → OOM。所有出网调用（DB、Redis、HTTP）必须有超时 |

### 2.7 可观测性旁路（当前最短板）

| 三大支柱 | 作用 | 不做的后果 |
| --- | --- | --- |
| **日志（Logging）** | 事后定位单条请求发生了什么 | 只有 `console.log` → 无结构、无级别、无 traceId，采集平台无法检索，出事只能看着乱码猜 |
| **指标（Metrics）** | 实时看服务健康度：QPS、P99 延迟、错误率、**事件循环延迟**、堆内存、GC 次数 | 不知道服务什么时候开始变慢，用户投诉了才发现 |
| **链路（Tracing）** | 一个请求跨服务的完整耗时分解 | 接口慢 800ms，不知道是哪个下游拖的，只能一层层加日志复现 |

**Node 专属的两个必埋指标**：

```javascript
// 1. 事件循环延迟（Event Loop Delay）—— Node 最重要的健康指标
//    它直接反映「JS 线程是不是被同步计算堵住了」
const { monitorEventLoopDelay } = require("node:perf_hooks");
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  // p99 持续 > 100ms 说明有同步阻塞代码，必须告警
  reportMetric("event_loop_delay_p99_ms", h.percentile(99));
  h.reset();
}, 10000);

// 2. 堆内存趋势 —— 判断内存泄漏
setInterval(() => {
  const { heapUsed, heapTotal, rss } = process.memoryUsage();
  reportMetric("heap_used_bytes", heapUsed);
  reportMetric("rss_bytes", rss); // rss 含 Buffer 等堆外内存
}, 10000);
// 判断泄漏看的是「多次 GC 后 heapUsed 的基线是否持续抬升」，
// 而不是某个瞬时值高。GC 原理见 ../../02-JavaScript/10-性能与优化/V8垃圾回收机制.md
```

**真实事故**：某接口内联了一段正则回溯，事件循环延迟 P99 从 5ms 涨到 800ms，但因为没埋这个指标，团队查了两天以为是 DB 慢。

### 2.8 底座：部署、健康检查、优雅退出

**优雅退出（Graceful Shutdown）是滚动发布不丢请求的前提。**

```javascript
// ❌ 不做优雅退出：K8s 发 SIGTERM，进程立刻死
// 后果：正在处理的请求连接被直接切断 → 网关拿不到响应 → 用户看到 502
//       每次滚动发布都会产生一批 502，发布 10 个副本就是 10 波错误

// ✅ 完整的优雅退出流程
const server = app.listen(PORT);
let shuttingDown = false;

// 配合 readiness 探针：让流量先停止进来
app.use(async (ctx, next) => {
  if (shuttingDown && ctx.path === "/readyz") {
    ctx.status = 503; // 探针失败 → K8s 把本实例从 Service 端点摘除
    return;
  }
  await next();
});

async function shutdown(signal) {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log(`收到 ${signal}，开始优雅退出`);

  // 1. 先让 readiness 变红，等一个探针周期，确保上游不再发新流量
  await sleep(5000);

  // 2. 停止接受新连接，但保持已有连接直到处理完
  server.close(async () => {
    // 3. 关闭资源：DB 连接池、Redis、MQ 消费者
    await sequelize.close();
    await redis.quit();
    process.exit(0);
  });

  // 4. 兜底：超过宽限期强杀，避免僵死
  //    这个时间必须小于 K8s 的 terminationGracePeriodSeconds（默认 30s）
  setTimeout(() => process.exit(1), 20000);
}

process.on("SIGTERM", () => shutdown("SIGTERM")); // K8s / Docker stop
process.on("SIGINT", () => shutdown("SIGINT"));   // Ctrl+C

// 未捕获异常：只做「记日志 + 优雅退出」，不要试图恢复
// 因为此刻进程状态已不可信，继续运行可能产生脏数据
process.on("uncaughtException", (err) => {
  logger.fatal({ err }, "uncaughtException");
  shutdown("uncaughtException");
});
process.on("unhandledRejection", (reason) => {
  logger.fatal({ reason }, "unhandledRejection");
  shutdown("unhandledRejection");
});
```

**健康检查要分两种，混用是常见错误**：

| **探针** | 语义 | 检查内容 | 混用的后果 |
| --- | --- | --- | --- |
| **liveness（存活）** | 进程还活着吗？死了就重启 | 只检查进程本身能响应，**不要**检查 DB | 如果检查了 DB，DB 抖动会导致所有实例被同时重启，小故障变大故障 |
| **readiness（就绪）** | 能接流量吗？不能就摘流 | 检查 DB / Redis / 依赖是否就绪 | 如果不检查依赖，启动未完成就接流量 → 首批请求全失败 |

| 底座其他项 | 不做的后果 |
| --- | --- |
| **配置外置** | 配置写死在代码里 → 改一个开关要发版；`.env` 提交到仓库 → 密钥泄露 |
| **资源限额** | 不设内存 limit → 泄漏时把整台机器吃光，影响同节点其他服务 |
| **灰度发布** | 全量直发 → 有 bug 时 100% 用户受影响，且没有对比样本 |
| **压测基线** | 不知道单实例能扛多少 → 扩容靠猜，大促必翻车 |

## 三、玩具项目 vs 生产项目差距对照表

左列是 [Todo 全栈项目](../../11-项目实战/Todo全栈项目/README.md) 的现状（跑得起来就行），右列是生产标准。这张表就是改造清单。

| **维度** | Todo 项目现状 | 生产标准 | 差距 | 补齐读哪篇 |
| --- | --- | --- | --- | --- |
| **配置管理** | `dotenv` 读本地 `.env`，默认值写死在 `config/db.js` | 多环境隔离（dev/staging/prod）、配置中心热更新、Secret 独立管理、启动时校验配置完整性 | 无环境区分；密钥与配置混在一起；缺失配置时静默用默认值 | 待补：`Node配置管理与多环境.md` |
| **日志** | `console.log` / `console.error`，只打 `err.message` | 结构化 JSON 日志（pino/winston）、分级、带 traceId、含错误堆栈、脱敏、按需采样 | 无结构无法检索；丢了 `err.stack` 导致无法定位代码行；无 traceId 无法串联 | 待补：`Node日志与错误处理规范.md` |
| **错误处理** | 全局中间件 try/catch，`err.status` 决定状态码 | 区分业务错误 / 系统错误 / 依赖错误；统一错误码体系；对外不暴露内部细节；`uncaughtException` 兜底 + 优雅退出 | 缺少错误分类；`err.message` 直接返回给客户端有信息泄露风险；无进程级兜底 | 待补：`Node日志与错误处理规范.md` |
| **鉴权** | JWT `verify` 挂 `ctx.user`，7 天长期有效 | 短 accessToken + refreshToken 轮换、支持吊销（黑名单/版本号）、密钥可轮转、权限粒度（RBAC） | Token 无法主动失效（改密码后旧 token 仍可用）；有效期过长 | 协议原理见 [认证与会话](../../08-网络与浏览器/认证与会话/README.md)；Node 侧实现待补：`Node鉴权与会话工程实现.md` |
| **参数校验** | 手工 `if (fields.title !== undefined)` 白名单 | Schema 驱动（zod/joi/class-validator），入口即校验，自动生成类型与文档 | 校验散落在 service 里；未校验类型与长度；无统一错误响应 | 待补：`Node参数校验与接口契约.md` |
| **连接池** | `pool.max=10`、`acquire=30000` | 按「DB max_connections / (副本数 × 进程数)」反推；`acquire` 3-5 秒快速失败；监控池等待队列长度 | `acquire` 过长导致请求堆积；未考虑多副本乘法效应 | 待补：`Node数据层工程实践.md` |
| **缓存** | 无 | Redis 缓存热点；防穿透（空值缓存/布隆过滤器）、防雪崩（过期时间加随机）、防击穿（互斥重建） | 完全没有缓存层 | 待补：`Node缓存策略实践.md` |
| **限流** | 无 | 网关全局限流 + 应用内兜底（令牌桶/滑动窗口）、按用户与 IP 维度、超限返回 429 | 任何客户端都能无限压 | 待补：`Node限流熔断与降级.md` |
| **超时与重试** | 无（Sequelize / 无下游调用） | 所有出网调用设超时；幂等接口才重试；重试要有退避与上限；配熔断器 | 无超时 → 下游卡住会拖垮自己 | 待补：`Node限流熔断与降级.md` |
| **进程模型** | `node src/app.js` 单进程 | 多副本（K8s）或 cluster 吃满多核；崩溃自动重启；CPU 密集任务移到 worker_threads | 只用一个核；崩了不重启 | 待补：`Node进程模型与多核利用.md` |
| **部署方式** | 本地 `npm run dev`（nodemon） | Dockerfile 多阶段构建、非 root 用户、`npm ci --omit=dev`、镜像瘦身、K8s 编排、CI/CD 流水线 | 无容器化，无法复现环境 | 待补：`Node容器化与部署.md` |
| **数据库变更** | `sequelize.sync({ force: false })` 自动同步表结构 | Migration 脚本版本化管理，可回滚，评审后执行 | `sync` 在生产可能产生意外 DDL，且无变更记录、无法回滚 | 待补：`Node数据层工程实践.md` |
| **健康检查** | 无 | `/livez`（只查进程）+ `/readyz`（查依赖），配 K8s 探针 | 启动未就绪就接流量；进程僵死无人发现 | 待补：`Node容器化与部署.md` |
| **优雅退出** | 无（启动失败才 `process.exit(1)`） | 监听 SIGTERM → readiness 变红 → 等待在途请求 → 关闭连接池 → 超时强杀 | 每次发布都会切断在途请求，产生 502 | 本篇 2.8 节 + 待补：`Node进程模型与多核利用.md` |
| **监控告警** | 无 | Metrics（QPS/P99/错误率/事件循环延迟/堆内存）+ 看板 + 分级告警 + 值班 | 完全黑盒，用户先发现问题 | 待补：`Node可观测性实践.md` |
| **链路追踪** | 无 | OpenTelemetry span，traceId 贯穿日志与下游调用 | 跨服务问题无法定位 | 基础能力见 [Node.js 现代特性与新 API](../Node.js现代特性与新API.md) 第四章；待补：`Node可观测性实践.md` |
| **压测基线** | 无 | 用 autocannon/k6 压出单实例 QPS 与 P99 曲线，定容量与扩容阈值 | 不知道容量，扩容靠猜 | 待补：`Node性能压测与调优.md` |
| **测试覆盖** | 无测试 | Service 层单元测试 + 接口集成测试，CI 门禁 | 改一行不知道会不会坏 | 内置测试框架见 [Node.js 现代特性与新 API](../Node.js现代特性与新API.md) 第二章；待补：`Node测试策略.md` |

## 四、生产就绪度自检清单

改造 Todo 项目时按这个顺序打勾。

### 必须做（Must）—— 不做就是线上事故

- [ ] **配置全部外置到环境变量 / 配置中心**，启动时校验必填项 —— 不做：改配置要发版，缺配置时静默跑错
- [ ] **`.env` 与密钥不进仓库**，只保留 `.env.example` —— 不做：密钥泄露
- [ ] **结构化日志（含 traceId、错误堆栈、级别）替换所有 `console.log`** —— 不做：线上出错无法定位
- [ ] **全局错误兜底**：中间件 try/catch + `uncaughtException` / `unhandledRejection` —— 不做：一个异常打挂整个进程
- [ ] **对外错误响应不含内部细节**（堆栈、SQL、路径） —— 不做：信息泄露被利用
- [ ] **所有入参 Schema 校验**（类型 + 长度 + 必填） —— 不做：脏数据入库，或 `undefined` 触发全表扫描
- [ ] **所有出网调用设超时**（DB / Redis / HTTP） —— 不做：下游卡住导致请求堆积 OOM
- [ ] **连接池上限按「副本数 × 进程数」反推**，`acquire` 超时收到 5 秒内 —— 不做：DB 拒连雪崩
- [ ] **请求态绝不放模块级变量**（显式传参或 AsyncLocalStorage） —— 不做：用户数据串号，越权事故
- [ ] **健康检查双探针**：liveness 不查依赖，readiness 查依赖 —— 不做：启动即接流量，或依赖抖动引发全体重启
- [ ] **优雅退出**：SIGTERM → 摘流 → 等在途 → 关连接 → 超时强杀 —— 不做：每次发布都产生 502
- [ ] **多副本或 cluster 部署 + 崩溃自动重启** —— 不做：单点故障，多核浪费
- [ ] **CORS 白名单而非 `*`**，上传文件校验类型并重命名 —— 不做：跨站攻击、任意文件上传
- [ ] **数据库变更用 Migration，禁用生产 `sync()`** —— 不做：意外 DDL 且无法回滚
- [ ] **容器镜像化部署**，非 root 用户运行，设 CPU/内存 limit —— 不做：环境不可复现，泄漏时拖垮整机

### 应该做（Should）—— 不做会持续踩坑

- [ ] **核心指标上报**：QPS、P99 延迟、错误率、事件循环延迟、堆内存、GC —— 不做：服务黑盒，被动救火
- [ ] **分级告警 + 值班机制** —— 不做：故障靠用户投诉发现
- [ ] **限流兜底**（应用内令牌桶），超限返回 429 —— 不做：单个客户端能压垮全站
- [ ] **热点数据缓存 + 穿透/雪崩防护** —— 不做：DB 成为唯一瓶颈
- [ ] **重要下游配熔断降级** —— 不做：一个非核心依赖挂了拖垮主流程
- [ ] **压测拿到单实例基线**，据此定副本数与 HPA 阈值 —— 不做：容量靠猜
- [ ] **Service 层单测 + 关键接口集成测试，CI 门禁** —— 不做：不敢重构
- [ ] **灰度发布 + 一键回滚** —— 不做：有问题时全量用户受影响
- [ ] **JWT 改为短 accessToken + refreshToken，支持吊销** —— 不做：改密码后旧 token 仍有效
- [ ] **依赖漏洞扫描（`npm audit` / SCA）进 CI** —— 不做：带着已知漏洞上线

### 可以做（Could）—— 锦上添花

- [ ] **分布式链路追踪（OpenTelemetry）** —— 不做：跨服务定位慢，但单服务阶段影响有限
- [ ] **接口契约自动化**（OpenAPI 生成 + 前端类型同步） —— 不做：前后端联调靠口头对齐
- [ ] **慢查询与慢接口自动巡检报告** —— 不做：性能退化悄悄累积
- [ ] **混沌演练**（随机杀实例、注入下游延迟） —— 不做：不知道预案是否真的有效
- [ ] **多级缓存（进程内 LRU + Redis）** —— 不做：Redis 网络往返成为瓶颈（仅高 QPS 时才需要）
- [ ] **CPU 密集任务迁 worker_threads 池** —— 不做：当前无重计算就先不做

## 五、一个请求的完整旅程

```
客户端                网关            Node 进程                    DB / 下游
  │                    │                 │                            │
  ├── TCP 三次握手 ────▶│                 │   ① 连接建立
  ├── TLS 握手 ────────▶│                 │      风险：证书过期 / 握手耗时高
  │                    │                 │      埋点：连接数、握手耗时
  │                    │                 │
  ├── HTTP 请求 ───────▶│                 │   ② 网关处理
  │                    ├─ 限流判定        │      风险：限流阈值配错误伤正常用户
  │                    ├─ 鉴权前置        │      埋点：限流拒绝数、429 比例
  │                    ├─ 灰度路由        │
  │                    │                 │
  │                    ├── 转发 ─────────▶│   ③ 进入 Node 进程
  │                    │                 ├─ traceId 注入（ALS）
  │                    │                 │     风险：忘注入 → 全链路无法关联
  │                    │                 │     埋点：请求开始时间戳
  │                    │                 ├─ 访问日志（前半）
  │                    │                 ├─ 错误兜底包裹
  │                    │                 ├─ body 解析
  │                    │                 │     风险：未限大小 → 内存打满
  │                    │                 ├─ 应用内限流兜底
  │                    │                 ├─ JWT 验签
  │                    │                 │     风险：验签是 CPU 操作，
  │                    │                 │           被大量无效 token 攻击会占满事件循环
  │                    │                 ├─ 参数 Schema 校验
  │                    │                 │     风险：漏校验 → 脏数据 / 全表扫描
  │                    │                 │
  │                    │                 ├─ Controller 取参
  │                    │                 ├─ Service 业务编排
  │                    │                 │     埋点：业务分支计数
  │                    │                 │
  │                    │                 ├─ 查缓存 ─────────────────▶│ Redis
  │                    │                 │◀── 命中则直接返回 ─────────┤
  │                    │                 │     埋点：缓存命中率
  │                    │                 │     风险：穿透 / 雪崩 / 击穿
  │                    │                 │
  │                    │                 ├─ 从连接池取连接
  │                    │                 │     风险：池满等待 → 请求堆积
  │                    │                 │     埋点：池等待队列长度、获取耗时
  │                    │                 │
  │                    │                 ├─ SQL 查询 ───────────────▶│ MySQL
  │                    │                 │      ▲ 此处让出执行权，       │
  │                    │                 │        进程去处理别的请求      │
  │                    │                 │◀── 结果返回（20ms） ────────┤
  │                    │                 │     埋点：SQL 耗时、慢查询
  │                    │                 │     风险：无超时 / 无索引
  │                    │                 │
  │                    │                 ├─ 归还连接（必须在 finally 里）
  │                    │                 │     风险：异常路径忘归还 → 连接泄漏
  │                    │                 │
  │                    │                 ├─ 序列化响应
  │                    │                 │     风险：大对象 JSON.stringify 是同步
  │                    │                 │           CPU 操作，会阻塞事件循环
  │                    │                 ├─ 访问日志（后半：状态码 + 总耗时）
  │                    │                 │     埋点：P99 延迟、错误率
  │◀── HTTP 响应 ──────┤◀────────────────┤
  │                    │                 │
  │                    │                 ├─ 异步上报 metrics / trace（不阻塞响应）
  │                    │                 │     风险：上报写成同步 → 拖慢每个请求
```

**排障口诀**：接口慢，先看是「排队慢」还是「执行慢」。排队慢看事件循环延迟和连接池等待；执行慢看 SQL 耗时和下游耗时。两者都正常还慢，就看网关和网络。

## 面试常见问答

**Q1：不做优雅退出会出什么问题？怎么实现？**

滚动发布时 K8s 会给旧实例发 SIGTERM，如果进程立刻退出，那些正在处理中的请求连接会被直接切断，网关拿不到响应就返回 502，用户能看到报错。每发布一次、每个副本都会产生一批错误。实现分四步：收到 SIGTERM 后先让 readiness 探针返回 503 并等一个探针周期，让上游把这个实例摘掉不再发新流量；然后 `server.close()` 停止接受新连接但保留已有连接处理完；接着关闭数据库连接池、Redis 这些资源；最后设一个强杀定时器兜底，这个时间必须小于 K8s 的 terminationGracePeriodSeconds，否则会被直接 SIGKILL。

**Q2：连接池大小怎么定？**

关键是算清乘法：数据库实际被占用的连接数等于副本数乘以每副本进程数再乘以单进程池上限。比如 4 副本、每副本 4 个 cluster 进程、池上限 10，就是 160 个连接，而 MySQL 默认 max_connections 只有 151，扩容时就会拒连雪崩。所以要反着算：先确认 DB 的连接上限并给运维和其他服务留余量，再除以「副本数乘进程数」。另外池子大不等于快，连接数超过 DB 的处理能力后吞吐反而下降，宁可让请求在应用侧排队，也不要把压力推给 DB。最后一定要配 acquire 超时，几秒内拿不到连接就快速失败。

**Q3：你的服务怎么做可观测性？traceId 怎么串起来的？**

三个支柱。日志用 pino 打结构化 JSON，每条都带 traceId 和错误堆栈；指标上报 QPS、P99 延迟、错误率，Node 还要额外埋事件循环延迟和堆内存这两个专属指标；链路用 OpenTelemetry 生成 span。traceId 的做法是在最外层中间件生成或从网关的请求头继承，然后用 AsyncLocalStorage 存进请求上下文，这样日志函数在任何深度的异步调用里都能 getStore 拿到，不需要一层层传参；调下游时再把 traceId 放进请求头传下去，整条链路就串起来了。

**Q4：liveness 和 readiness 探针有什么区别？为什么不能写成一个？**

liveness 回答「进程是不是死了」，死了就重启；readiness 回答「能不能接流量」，不能就从负载均衡里摘掉但不重启。最关键的区别是 liveness 绝对不能检查数据库这类外部依赖——如果检查了，DB 抖动一下会让所有实例的 liveness 同时失败，K8s 把整个集群重启一遍，小故障立刻变成大故障。readiness 反过来必须检查依赖，否则进程启动了但连接池还没建好就开始接流量，第一批请求全部失败。

**Q5：怎么判断一个 Node 服务能上线了？**

我会过一份清单，分三档。必须做的：配置外置且启动校验、结构化日志带 traceId、全局错误兜底、所有入参校验、所有出网调用有超时、连接池按副本数反推、请求态不放模块级变量、双探针健康检查、优雅退出、多副本部署、CORS 白名单、用 Migration 而不是 sync。应该做的：核心指标上报和告警、限流兜底、热点缓存、熔断降级、压测基线、关键路径测试、灰度和回滚能力。这些过完才敢说生产就绪。反过来，只有「本地能跑通」而没有日志、监控、优雅退出的服务，上线就是在赌运气。
