# 生产运维

> Node 服务从「能跑起来」到「能扛住线上」需要补齐的四件事：进程如何安全下线、错误如何分类兜底、问题如何被观测到、应用如何部署与守护。

这四篇是「有没有做过生产项目」的试金石——面试里必问，一问就能听出是否真的上线过服务。

## 📚 本模块文档

按推荐阅读顺序：

1. [优雅退出与健康检查](./优雅退出与健康检查.md) — 信号机制、`server.close` 与 in-flight 等待、liveness/readiness/startup 三种探针的语义差异、K8s 宽限期配合
2. [Node 错误处理与异常兜底体系](./Node错误处理与异常兜底体系.md) — 错误三分类与 `isOperational`、自定义错误类、中间件统一处理、`uncaughtException` 为何不能 resume、异步错误丢失陷阱、重试熔断降级
3. [Node 日志与可观测性体系](./Node日志与可观测性体系.md) — 为何弃用 `console.log`、结构化日志与脱敏、traceId 全链路串联、可观测性三支柱分工、事件循环延迟为何是 Node 核心指标、OpenTelemetry
4. [Node 应用部署与进程守护](./Node应用部署与进程守护.md) — PM2/Docker/K8s 三种托管形态选型、多阶段 Dockerfile、容器内存与 V8 堆的配合、PID 1 与信号转发、配置管理、发布策略

为什么是这个顺序：优雅退出是最基础的一环（不做则每次发布必掉请求）；错误分类决定了日志该记什么、该不该告警；日志与指标是发现问题的唯一手段；部署配置则是让前三者真正生效的前提（比如 PID 1 配置错误会让优雅退出完全失效）。

## 四篇的交叉关系

```
        部署与进程守护
        （让信号能到达进程）
                │
                ▼
        优雅退出与健康检查
        （进程安全下线、摘流量）
                │
                ├──────────────┐
                ▼              ▼
          错误处理与兜底 ──▶ 日志与可观测性
          （错误怎么分类）   （分好类的错误怎么记录告警）
```

典型的连锁关系：

- Dockerfile 用了 shell 形式 CMD → SIGTERM 到不了进程 → **优雅退出代码白写** → 滚动发布必掉请求
- liveness 探针误查下游依赖 → 下游抖动时全集群同时重启 → **雪崩**
- 错误没分类，业务 4xx 也告警 → 告警疲劳 → **真故障被淹没**
- 异步日志未 flush 就退出 → **崩溃现场的最后一条日志丢失**
