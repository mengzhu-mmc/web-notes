# 优雅退出与健康检查

> 生产环境的 Node 服务不是「跑起来」就算完，而是要能「安全地停下来」。优雅退出（Graceful Shutdown）与健康检查（Health Check）是发布不掉请求的两块基石。

## 面试高频考点

1. **滚动发布时用户为什么会看到 502？怎么从代码层面根治？**
2. **SIGTERM、SIGINT、SIGKILL 有什么区别？哪个捕获不了？**
3. **`server.close()` 到底关掉了什么？为什么调用后进程还是不退出？**
4. **liveness、readiness、startup 三种探针的语义差异是什么？为什么 liveness 不能检查下游依赖？**
5. **`terminationGracePeriodSeconds` 和代码里的强杀超时该怎么配合？**

## 一、为什么必须优雅退出

### 1.1 一个真实的发布事故

场景：一个 Koa 服务部署在 K8s 上，4 个副本，滚动发布。发布过程中监控报警——5xx 错误率从 0.01% 飙到 3%，客户端日志里大量 502 Bad Gateway。

复盘链路：

1. K8s 决定替换 Pod A，向 Pod A 的容器发送 `SIGTERM`
2. 代码里没有注册 `SIGTERM` 监听器，Node 走默认行为——**立即终止进程**
3. 此时 Pod A 上还有 30 多个 in-flight 请求（有的正在查库，有的正在等下游 RPC），TCP 连接被内核直接 RST
4. 更糟的是：K8s 摘除 Endpoint 和发送 SIGTERM 是**并发**的，网关的负载均衡表还没更新完，新请求继续被转发到已经死掉的 Pod A
5. 网关收到 RST → 返回 502

结论：**进程立即退出 ≠ 优雅**。「立即退出」丢的是已经承诺给用户的请求。

### 1.2 暴力退出 vs 优雅退出

```
【暴力退出】进程收到信号即死，请求被斩断

  时间轴 ──────────────────────────────────────────────────────>
             │
  编排层     ├─ 发 SIGTERM ─┐
             │              │ (摘流量还在异步进行中)
             ├─ 摘 Endpoint ─────────┐
             │              │        │
  Node 进程  ├─ 处理中: R1 R2 R3     │
             │              ↓        │
             │            [进程死]   │
             │         R1 R2 R3 全部被 RST ✗
             │                       │
  新请求 R4  ├──────────── 转发到已死 Pod ──> 502 ✗
             │                       │
                                  (此时才摘完)


【优雅退出】先摘流量，再停 accept，等存量做完才退出

  时间轴 ──────────────────────────────────────────────────────>
             │
  编排层     ├─ preStop sleep 5s ─┐
             ├─ 摘 Endpoint ──────┤ (这段时间进程还活着，继续服务)
             │                    │
             ├────────────── 发 SIGTERM ─┐
             │                    │      │
  Node 进程  ├─ readiness 转 false│      │
             │  (探针失败 → 加速摘流量)   │
             ├─ server.close()  ──┼──────┤ 不再 accept 新连接
             ├─ 处理中: R1 R2 R3  │      │
             │      R1 ✓  R2 ✓  R3 ✓ 全部正常返回
             ├─ 关 DB / Redis / MQ       │
             ├─ process.exit(0) ─────────┘
             │
  新请求 R4  ├─ 已被摘流量，转发到健康 Pod ──> 200 ✓
```

## 二、信号机制

### 2.1 常见信号与场景

| 信号 | 编号 | 能否捕获 | 谁会发它 | 默认行为 | 语义 |
| --- | --- | --- | --- | --- | --- |
| `SIGTERM` | 15 | ✅ 可捕获 | K8s、`docker stop`、`kill <pid>` | 终止进程 | **礼貌请求退出**，生产优雅退出的主入口 |
| `SIGINT` | 2 | ✅ 可捕获 | 终端 Ctrl+C、PM2（默认 `kill_signal`） | 终止进程 | 交互式中断 |
| `SIGKILL` | 9 | ❌ **不可捕获、不可忽略、不可阻塞** | `kill -9`、K8s 宽限期超时、OOMKiller | 立即由内核销毁进程 | 最后手段，代码完全无法响应 |
| `SIGHUP` | 1 | ✅ 可捕获 | 终端断开、`nginx -s reload` 类约定 | 终止进程 | 常被约定为「重载配置」 |
| `SIGQUIT` | 3 | ✅ 可捕获 | Ctrl+\\ | 终止 + core dump | 排查用 |
| `SIGUSR2` | 12 | ✅ 可捕获 | 自定义 | 终止进程 | 常被工具占用（如 nodemon 重启） |

```javascript
// 关键认知：SIGKILL 和 SIGSTOP 是内核级别的，注册监听器完全没有效果
process.on("SIGKILL", () => {
  // ❌ 这段代码永远不会执行
  // Node 在注册 SIGKILL / SIGSTOP 监听器时甚至会直接抛错（EINVAL）
  console.log("清理资源");
});

// ✅ 正确做法：只监听可捕获的信号，SIGKILL 是「兜底强杀」而不是「可处理事件」
["SIGTERM", "SIGINT"].forEach((sig) => {
  process.on(sig, () => shutdown(sig));
});
```

> [!important] 面试高频
> 「优雅退出能不能处理 `kill -9`？」标准答案是**不能**。`SIGKILL` 由内核直接回收进程，用户态代码没有任何执行机会。所以设计上的正确姿势是：让编排层在**发 SIGKILL 之前**留出足够宽限期（K8s 的 `terminationGracePeriodSeconds`），并保证代码里的强杀超时**小于**这个宽限期，从而永远不需要走到 SIGKILL 这一步。

### 2.2 优雅退出的六个步骤

```
收到 SIGTERM
    │
    ├─ ① 置 shuttingDown = true，readiness 探针立刻返回 503（摘流量）
    │      ↓ 关键顺序：先摘流量，再停服务
    │      ↓ 反了的话，新请求还会被路由进来，但服务已经不 accept 了 → 连接被拒
    │
    ├─ ② 可选：等待 drainDelay（给网关刷新 LB 表的时间）
    │
    ├─ ③ server.close()：停止 accept 新连接，已建立连接继续处理
    │
    ├─ ④ 等待 in-flight 请求完成 + forceTimeout 兜底
    │      ↓ 不能无限等：某个请求卡在下游超时上，会把整个退出流程拖死
    │
    ├─ ⑤ 关闭外部资源：DB 连接池 → Redis → MQ 消费者 → 定时任务
    │      ↓ 顺序：先停「消费入口」，再关「数据出口」
    │
    └─ ⑥ process.exit(0)
```

## 三、完整实现

### 3.1 Koa 版（可直接用）

```javascript
// src/shutdown.js —— 优雅退出编排器
const STATE = {
  shuttingDown: false, // readiness 探针读这个字段
};

/**
 * @param {import('http').Server} server  http.createServer(app.callback()) 的返回值
 * @param {object} deps                   需要关闭的外部资源
 * @param {object} opts
 *   drainDelay   摘流量后的等待时间（给网关刷新 LB 表），K8s 有 preStop 时可设 0
 *   forceTimeout 从收到信号到强杀的总超时，必须 < terminationGracePeriodSeconds
 */
function setupGracefulShutdown(server, deps = {}, opts = {}) {
  const { drainDelay = 3000, forceTimeout = 15000 } = opts;

  const shutdown = async (signal) => {
    // 幂等：连按两次 Ctrl+C 或编排层重发信号时不要走两遍
    if (STATE.shuttingDown) {
      console.warn(JSON.stringify({ level: "warn", msg: "已在退出流程中，忽略重复信号", signal }));
      return;
    }
    STATE.shuttingDown = true;
    console.info(JSON.stringify({ level: "info", msg: "收到退出信号，开始优雅退出", signal }));

    // 兜底强杀：无论上面卡在哪一步，到点必须走
    // unref() 让这个定时器不阻止事件循环自然退出（正常路径下进程能提前退干净）
    const forceTimer = setTimeout(() => {
      console.error(JSON.stringify({ level: "error", msg: "优雅退出超时，强制退出", forceTimeout }));
      process.exit(1); // 非 0 退出码，便于监控区分「正常退出」和「超时强杀」
    }, forceTimeout);
    forceTimer.unref();

    try {
      // ① readiness 已经在上面置为 false，等一会儿让网关把流量摘干净
      //    ❌ 错误做法：先 server.close() 再摘流量 —— 新请求会打在已关闭的监听上
      //    ✅ 正确做法：先让探针失败，等网关反应过来，再停 accept
      if (drainDelay > 0) {
        await sleep(drainDelay);
      }

      // ② 停止 accept 新连接；回调在「所有连接都结束」后触发
      await closeServer(server);
      console.info(JSON.stringify({ level: "info", msg: "HTTP server 已关闭" }));

      // ③ 关闭外部资源：先停消费入口，再关数据出口
      if (deps.consumer) await deps.consumer.disconnect(); // MQ 消费者：先停止拉新消息
      if (deps.cron) deps.cron.stop(); // 定时任务
      if (deps.sequelize) await deps.sequelize.close(); // Sequelize 连接池
      if (deps.redis) await deps.redis.quit(); // quit() 会等待队列中命令执行完；disconnect() 是立即断
      console.info(JSON.stringify({ level: "info", msg: "外部资源已释放，正常退出" }));

      clearTimeout(forceTimer);
      process.exit(0);
    } catch (err) {
      console.error(JSON.stringify({ level: "error", msg: "退出流程异常", err: err.message }));
      process.exit(1);
    }
  };

  ["SIGTERM", "SIGINT"].forEach((sig) => process.on(sig, () => shutdown(sig)));
  return STATE;
}

function sleep(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

function closeServer(server) {
  return new Promise((resolve, reject) => {
    server.close((err) => (err ? reject(err) : resolve()));

    // 关键：server.close() 不会动空闲的 keep-alive 连接（详见第四章）
    // 有这两个 API 时立刻断开空闲连接，否则 close 回调可能要等 keepAliveTimeout 才触发
    if (typeof server.closeIdleConnections === "function") {
      server.closeIdleConnections();
    }
  });
}

module.exports = { setupGracefulShutdown, STATE };
```

```javascript
// src/server.js —— 接到 Koa 应用上
const http = require("node:http");
const Koa = require("koa");
const { setupGracefulShutdown } = require("./shutdown");
const { sequelize } = require("./models");
const redis = require("./config/redis");

const app = new Koa();
// ... 中间件与路由

// ❌ 常见写法：app.listen() 的返回值被丢掉，之后拿不到 server 实例做 close()
// app.listen(3000)

// ✅ 显式持有 server 实例
const server = http.createServer(app.callback());

// keep-alive 超时必须比上游网关的 idle 超时「短」，避免网关复用一个即将被服务端关闭的连接
server.keepAliveTimeout = 65_000;
// headersTimeout 应大于 keepAliveTimeout，否则可能在等请求头时提前掐断
server.headersTimeout = 70_000;

server.listen(process.env.PORT || 3000, async () => {
  await sequelize.authenticate();
  console.info(JSON.stringify({ level: "info", msg: "服务启动", port: server.address().port }));
});

setupGracefulShutdown(
  server,
  { sequelize, redis },
  { drainDelay: 3000, forceTimeout: 15_000 }, // 15s < K8s 宽限期 30s ✓
);
```

```javascript
  next();
});

  res.json({ data: [] });
});

const server = http.createServer(app);
server.keepAliveTimeout = 65_000;
server.headersTimeout = 70_000;
server.listen(3000);

setupGracefulShutdown(server, {}, { forceTimeout: 15_000 });
```

## 四、keep-alive 连接的坑

### 4.1 为什么 `server.close()` 的回调迟迟不触发

`server.close()` 的语义是：**停止接受新连接**，并在**所有已存在连接都关闭后**触发回调。问题就在后半句。

```
浏览器/网关 与服务端建立 keep-alive 连接后，请求处理完连接不会断，
它处于「空闲但保持」状态，等着复用。

server.close() 之后：
  ┌──────────────────────────────────────────────┐
  │  连接 C1  正在处理请求  → 处理完自然关闭 ✓     │
  │  连接 C2  空闲 keep-alive → close() 不管它 ✗   │
  │  连接 C3  空闲 keep-alive → close() 不管它 ✗   │
  └──────────────────────────────────────────────┘
                    ↓
   回调要等 C2 / C3 被 keepAliveTimeout 自然回收才触发
                    ↓
   退出流程被硬生生拖长 → 撞上 forceTimeout 或编排层的 SIGKILL
```

### 4.2 Node 18.2+ 的两个 API

```javascript
// Node 18.2.0 起提供，用来解决上面的问题
server.closeIdleConnections();
// 只断开「当前空闲」的连接，正在处理请求的连接不受影响
// ✅ 优雅退出场景应该用这个：既加速 close 回调，又不伤害 in-flight 请求

server.closeAllConnections();
// 断开所有连接，包括正在处理请求的
// ⚠️ 这是「强杀级」操作，只应放在 forceTimeout 到期后的最后挣扎里，不要一上来就调

// 版本兜底写法（老版本 Node 上不存在这两个方法）
if (typeof server.closeIdleConnections === "function") {
  server.closeIdleConnections();
}
```

### 4.3 keepAliveTimeout 与网关超时的配合

| 配置项 | 作用 | 配置原则 |
| --- | --- | --- |
| Node `server.keepAliveTimeout` | 服务端保持空闲 keep-alive 连接的时长 | **必须大于**上游网关的 keep-alive idle 超时 |
| Node `server.headersTimeout` | 从连接建立到收完请求头的允许时长 | 应**大于** `keepAliveTimeout`，否则可能提前掐断 |
| 网关（Nginx `keepalive_timeout` / ALB idle timeout） | 网关侧保持连接的时长 | 取比服务端**更小**的值 |

```
❌ 危险配置：网关 60s > Node 5s（Node 默认值较小）

  t=0    网关与 Node 建立连接
  t=5s   Node 侧到 keepAliveTimeout，发 FIN 关闭连接
  t=5s   网关认为这条连接还能用（它的超时是 60s），把新请求写进去
         ↓
       请求打在正在关闭的连接上 → 502 / ECONNRESET（典型的「偶发 502」根因）

✅ 安全配置：Node 65s > 网关 60s
  永远由「网关」这一侧先主动关闭连接，服务端不会在网关不知情时断开
```

## 五、三种探针的语义差异

### 5.1 对照表

| 探针 | 回答的问题 | 失败后的动作 | 能否检查下游依赖 | 典型实现 |
| --- | --- | --- | --- | --- |
| **liveness**（存活） | 进程是不是**卡死了 / 死循环了**？ | **重启容器** | ❌ **绝对不能** | 只回 200，或检查事件循环延迟 |
| **readiness**（就绪） | 现在**能不能接流量**？ | 从 Service Endpoint 摘除（**不重启**） | ✅ **应该检查** | 查 DB `SELECT 1`、Redis `PING` |
| **startup**（启动） | **启动完成了吗**？ | 继续等；超过阈值才重启 | 视情况 | 检查预热/迁移是否完成 |

### 5.2 为什么 liveness 绝对不能检查下游

```
❌ liveness 里写了「查 MySQL，查不到就返回 500」

  t=0    MySQL 主库抖动 3 秒（很常见：主从切换、慢查询堆积、网络闪断）
           ↓
  t=0~3s  所有 20 个 Pod 的 liveness 探针同时失败
           ↓
  kubelet 判定「进程死了」→ 同时重启全部 20 个 Pod
           ↓
  t=3s    MySQL 恢复了，但此时集群里 0 个可用实例
           ↓
  20 个 Pod 同时冷启动 → 同时建连接池 → 连接数瞬间打满 MySQL
           ↓
  MySQL 再次被打挂 → liveness 再次全体失败 → 无限重启雪崩 💀

  根因：把「下游不可用」误判成了「自己进程死了」。
        下游抖动是暂态的，重启进程完全无助于修复，反而放大故障。


✅ 正确分工

  liveness  只问自己：事件循环还在转吗？我还能响应 HTTP 吗？
            → MySQL 抖动时它依然返回 200，Pod 不会被重启

  readiness 才问下游：MySQL 通吗？
            → MySQL 抖动时它返回 503，Pod 被摘流量（但保持存活）
            → MySQL 恢复后探针自动转成功，流量自动回来，全程无重启 ✓
```

### 5.3 Koa 实现

```javascript
// src/router/health.js
const Router = require("@koa/router");
const { STATE } = require("../shutdown");

const router = new Router();

// ───────── liveness：只检查自身，绝不碰下游 ─────────
router.get("/healthz", (ctx) => {
  // ❌ 千万不要写成这样：
  // await sequelize.query('SELECT 1')   → 下游抖动会引发全集群重启雪崩

  // ✅ 只回答「我这个进程还能干活吗」
  ctx.status = 200;
  ctx.body = { status: "ok", pid: process.pid, uptime: process.uptime() };
});

// ───────── readiness：检查下游 + 感知退出状态 ─────────
let cache = { at: 0, ok: false };
const CACHE_TTL = 2000; // 探针 1s 一次，做个短缓存避免把下游打爆

router.get("/readyz", async (ctx) => {
  // ① 退出流程中一律不就绪 —— 这是「先摘流量再停服务」的实现点
  if (STATE.shuttingDown) {
    ctx.status = 503;
    ctx.body = { status: "shutting_down" };
    return;
  }

  if (Date.now() - cache.at < CACHE_TTL) {
    ctx.status = cache.ok ? 200 : 503;
    ctx.body = { status: cache.ok ? "ready" : "not_ready", cached: true };
    return;
  }

  const checks = {};
  try {
    // ② 每个检查都要带超时：探针自己不能被下游拖死
    await withTimeout(ctx.app.context.sequelize.query("SELECT 1"), 1000);
    checks.mysql = "ok";
    await withTimeout(ctx.app.context.redis.ping(), 500);
    checks.redis = "ok";

    cache = { at: Date.now(), ok: true };
    ctx.status = 200;
    ctx.body = { status: "ready", checks };
  } catch (err) {
    cache = { at: Date.now(), ok: false };
    ctx.status = 503; // 非 2xx 才算失败，一定不要 catch 完还返回 200
    ctx.body = { status: "not_ready", checks, error: err.message };
  }
});

// ───────── startup：启动慢的应用用它挡住 liveness ─────────
let started = false;
router.get("/startupz", (ctx) => {
  ctx.status = started ? 200 : 503;
  ctx.body = { status: started ? "started" : "starting" };
});
router.markStarted = () => (started = true); // 迁移/预热完成后调用

function withTimeout(promise, ms) {
  return Promise.race([
    promise,
    new Promise((_, reject) => setTimeout(() => reject(new Error(`check timeout ${ms}ms`)), ms)),
  ]);
}

module.exports = router;
```

## 六、与 Kubernetes 配合

### 6.1 完整 Deployment 片段

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: todo-api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1 # 先起新的，再停老的，容量不下降
      maxUnavailable: 0 # 发布期间不允许可用副本数减少
  template:
    spec:
      # 宽限期：从发 SIGTERM 到发 SIGKILL 的时间上限
      # 必须 > preStop 时长 + 代码里的 forceTimeout
      terminationGracePeriodSeconds: 30
      containers:
        - name: app
          image: registry.example.com/todo-api:v1.2.3
          ports:
            - containerPort: 3000
          lifecycle:
            preStop:
              exec:
                # preStop 在发 SIGTERM 之前执行，给「摘 Endpoint」争取时间
                # K8s 里「摘 Endpoint」和「发 SIGTERM」是并发的，这个 sleep 是业界通用补偿手段
                command: ["sh", "-c", "sleep 5"]
          startupProbe:
            httpGet: { path: /startupz, port: 3000 }
            periodSeconds: 2
            failureThreshold: 30 # 最多容忍 2×30 = 60s 启动时间
          livenessProbe:
            httpGet: { path: /healthz, port: 3000 } # 只检查自身
            initialDelaySeconds: 0 # 有 startupProbe 时这里可以为 0
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3 # 连续 3 次失败才重启，避免单次抖动误杀
          readinessProbe:
            httpGet: { path: /readyz, port: 3000 } # 检查下游
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2 # 摘流量代价小，可以更灵敏
            successThreshold: 1
```

### 6.2 时间预算的数值关系（最容易配错的地方）

```
terminationGracePeriodSeconds = 30s
│
├─ preStop: sleep 5s          ← 让 Endpoint 摘除先生效（此时进程仍正常服务）
│
└─ SIGTERM 之后代码的预算 = 30 - 5 = 25s
   │
   ├─ drainDelay        3s    ← 有 preStop 时可以调小甚至设 0
   ├─ 等 in-flight 完成 ~10s  ← 取业务 P99 耗时的 1~2 倍
   └─ 关闭资源          ~2s
       ────────────────────
       forceTimeout = 15s  ✓  15 < 25，永远走不到 SIGKILL

❌ 反面案例：forceTimeout = 60s，宽限期 = 30s
   → 代码还在等第 40 秒，K8s 已经在第 30 秒发了 SIGKILL
   → 优雅退出逻辑白写，效果等同于暴力退出

📌 铁律：代码强杀超时 + preStop 时长 < terminationGracePeriodSeconds
```

| 配置项 | 推荐值 | 理由 |
| --- | --- | --- |
| `terminationGracePeriodSeconds` | 30~60s | 默认 30s，业务 P99 长的要放大 |
| `preStop sleep` | 5~10s | 覆盖 Endpoint 传播到所有网关节点的时间 |
| 代码 `forceTimeout` | 宽限期 − preStop − 5s 余量 | 必须留出安全边界 |
| `livenessProbe.failureThreshold` | ≥ 3 | 防止单次 GC 停顿导致误重启 |
| `readinessProbe.periodSeconds` | 5s | 太密会给下游探测压力 |

## 七、cluster / PM2 下的信号传递链

### 7.1 cluster 的信号转发

Node 的 `cluster` 模块**不会**自动把主进程收到的信号转发给 worker，需要手动编排。基础 API 见 [Node.js 面试核心知识点 · 五、进程与集群](../Node.js面试核心知识点.md)，这里只补退出编排的部分。

```javascript
const cluster = require("node:cluster");
const os = require("node:os");

if (cluster.isPrimary) {
  const workers = new Set();
  for (let i = 0; i < os.availableParallelism(); i++) {
    workers.add(cluster.fork());
  }

  let shuttingDown = false;
  cluster.on("exit", (worker) => {
    workers.delete(worker);
    // ✅ 关键：退出期间不要重启 worker，否则永远退不掉
    if (!shuttingDown) workers.add(cluster.fork());
  });

  const shutdown = () => {
    shuttingDown = true;

    for (const worker of workers) {
      // disconnect() 让 worker 关闭监听的 server handle，处理完存量请求后自然退出
      // 比直接 worker.kill() 温和，是 cluster 场景下的「优雅」入口
      worker.disconnect();

      // 兜底：worker 卡住时强杀（SIGKILL 由内核执行，worker 无从抵抗）
      const t = setTimeout(() => worker.process.kill("SIGKILL"), 15_000);
      worker.on("exit", () => clearTimeout(t));
    }
  };

  ["SIGTERM", "SIGINT"].forEach((s) => process.on(s, shutdown));
} else {
  // worker 内部：正常挂第三章的 setupGracefulShutdown
  require("./server");
}
```

### 7.2 PM2 的 reload 与 restart

| 命令 | 行为 | 是否零停机 | 适用场景 |
| --- | --- | --- | --- |
| `pm2 restart <app>` | 全部 worker 一起停，再一起起 | ❌ 有停机窗口 | 改了 `ecosystem.config.js`、换 Node 版本 |
| `pm2 reload <app>` | **逐个**替换 worker：起新的 → 摘老的 → 老的优雅退出 | ✅ 零停机 | 日常代码发布（cluster 模式下才有意义） |
| `pm2 stop <app>` | 停止但保留在进程列表里 | — | 临时下线 |
| `pm2 delete <app>` | 停止并从列表移除 | — | 彻底下线 |

```bash
# 零停机滚动重启（要求 exec_mode: cluster）
pm2 reload todo-api

# fork 模式下 reload 退化成 restart —— 只有一个进程，没法「滚动」
```

```javascript
// ecosystem.config.js 中与优雅退出相关的三个关键字段
module.exports = {
  apps: [
    {
      name: "todo-api",
      script: "src/server.js",
      exec_mode: "cluster", // reload 零停机的前提
      instances: "max",

      // PM2 默认发 SIGINT（不是 SIGTERM），所以代码里两个信号都要监听
      kill_signal: "SIGINT",

      // PM2 默认 kill_timeout 是 1600ms，对需要 drain 的服务远远不够
      // 这个值要 ≥ 代码里的 forceTimeout
      kill_timeout: 20000,

      // 进程发出 'ready' 事件后才算启动完成（配合 wait_ready 做 reload 的就绪判定）
      wait_ready: true,
      listen_timeout: 10000,
    },
  ],
};
```

```javascript
// 配合 wait_ready：启动完成后主动通知 PM2，reload 才知道什么时候可以摘老进程
server.listen(PORT, async () => {
  await sequelize.authenticate();
  if (process.send) process.send("ready"); // ← 少了这行，wait_ready 会一直等到 listen_timeout
});
```

## 生产实践清单

### 必须做（Must）

- [ ] 显式持有 `http.Server` 实例（`http.createServer(app.callback())`），不要丢掉 `app.listen()` 的返回值
- [ ] 同时监听 `SIGTERM` 和 `SIGINT`（K8s 发前者，PM2 默认发后者）
- [ ] 退出流程严格按「readiness 转 false → drain → `server.close()` → 关资源 → exit」的顺序
- [ ] `server.close()` 时调用 `server.closeIdleConnections()`（有此 API 的版本），否则回调会被空闲 keep-alive 连接拖住
- [ ] 强杀兜底定时器必须存在，且 `forceTimeout + preStop < terminationGracePeriodSeconds`
- [ ] 退出流程幂等（重复信号直接忽略），退出中的请求返回 503 且带 `Connection: close`
- [ ] liveness 探针**只检查自身**，不查任何下游
- [ ] readiness 探针检查下游，且每个检查带独立超时 + 短缓存
- [ ] `server.keepAliveTimeout` 大于上游网关的 idle 超时，`headersTimeout` 大于 `keepAliveTimeout`
- [ ] K8s 配 `preStop sleep`，`maxUnavailable: 0`
- [ ] cluster/PM2 场景下退出期间禁止重启 worker
- [ ] 退出流程的每一步都打日志，退出码区分正常（0）与超时强杀（1）

### 常见踩坑

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 滚动发布必现少量 502 | 没注册 SIGTERM，进程被立即终止 | 实现优雅退出；配 `preStop sleep` |
| 优雅退出代码写了，502 依旧 | 摘流量和停服务顺序反了，或 `preStop` 缺失导致 Endpoint 还没摘完 | 先让 readiness 失败并等 drainDelay，再 `server.close()` |
| `server.close()` 回调不触发，进程挂在退出中 | 空闲 keep-alive 连接不被 `close()` 关闭 | 调 `server.closeIdleConnections()`；配 `forceTimeout` |
| 日志显示「优雅退出超时，强制退出」 | 某个下游请求卡死，或忘了关某个 handle（定时器/长连接） | 用 `process.getActiveResourcesInfo()` 排查残留 handle；给下游调用加超时 |
| 下游 MySQL 抖动 3 秒，全集群 Pod 一起重启 | liveness 探针里检查了 MySQL | liveness 只检查自身；下游检查放 readiness |
| 启动慢的服务反复被重启，起不来 | 只配了 liveness，`initialDelaySeconds` 不够 | 加 `startupProbe`，或放大 `initialDelaySeconds` |
| PM2 reload 时请求被斩断 | `kill_timeout` 默认 1600ms，代码 drain 还没走完就被杀 | 把 `kill_timeout` 设为 ≥ `forceTimeout` |
| PM2 reload 期间流量打到没起好的新进程 | 未配 `wait_ready` / 代码未 `process.send('ready')` | 两者都补上 |
| 偶发 502 / ECONNRESET，与发布无关 | Node `keepAliveTimeout` 小于网关 idle 超时，服务端先关连接 | 放大 Node 侧 `keepAliveTimeout` |
| 容器里 SIGTERM 完全收不到 | PID 1 是 shell（`CMD npm start`），信号没转发给 node | 用 `docker run --init` / `dumb-init`，`CMD ["node","src/server.js"]`（见[部署与进程守护](./Node应用部署与进程守护.md)） |

### 排查手册

| 看什么指标 | 用什么工具 | 定位到代码 | 怎么验证 |
| --- | --- | --- | --- |
| 发布窗口内 5xx / 502 是否有尖刺 | 网关监控、APM 按时间对齐发布事件 | 有尖刺 → 退出流程或探针配置 | 灰度 1 个副本，压测下 `kubectl delete pod`，5xx 应为 0 |
| Pod 退出耗时（`terminationGracePeriod` 是否被打满） | `kubectl get events`、Pod 终止时间戳 | 打满 → `server.close()` 被 keep-alive 或残留 handle 拖住 | 本地 `kill -TERM <pid>`，观察退出日志时序 |
| 是否出现 `Exit Code: 137` | `kubectl describe pod` 的 Last State | 137 = 128+9，被 SIGKILL：宽限期不够或 OOMKill | 调大宽限期 / 调小 `forceTimeout` 后复测 |
| 重启次数 `RESTARTS` 持续增长 | `kubectl get pod -w` | liveness 配置过激或探针查了下游 | 临时关掉 liveness，看是否止损 |
| 退出时残留哪些 handle | `process.getActiveResourcesInfo()`、`why-is-node-running` | 定位到未 `clearInterval` 的定时器 / 未关的连接池 | 补关闭逻辑后进程应立即自然退出，不再依赖 `process.exit()` |
| 网关 upstream 侧 RST 计数 | Nginx `error.log`、LB 指标 | 连接被服务端提前关闭 | 调整 `keepAliveTimeout` 后 RST 应归零 |

## 面试常见问答

**Q1：滚动发布时用户偶发看到 502，怎么排查和根治？**

先看 502 是不是只集中在发布窗口，如果是，基本就是优雅退出的问题。链路是这样的：K8s 摘 Endpoint 和发 SIGTERM 是并发的，如果代码不处理 SIGTERM，进程立刻死，正在处理的请求被 RST，同时网关 LB 表还没刷新，新请求还会打进来，两头都是 502。根治要两手：代码侧实现优雅退出——readiness 转 false、`server.close()`、等存量请求、带超时强杀兜底；编排侧配 `preStop sleep 5s` 给摘流量留时间，`maxUnavailable: 0` 保证容量不掉。另外别忘了检查 `keepAliveTimeout` 是不是比网关小，那会导致跟发布无关的偶发 502。

**Q2：`kill -9` 能被优雅退出处理吗？**

不能。`SIGKILL` 和 `SIGSTOP` 是内核直接执行的，不可捕获、不可忽略、不可阻塞，用户态代码没有任何执行机会，注册监听器也无效。所以正确的设计思路不是「处理 SIGKILL」，而是「让它永远不发生」：编排层先发 `SIGTERM` 并给足宽限期，代码在宽限期内自己退干净。K8s 里就是保证 `forceTimeout + preStop < terminationGracePeriodSeconds`。如果看到 Pod 的 Exit Code 是 137，说明宽限期被打满走到了 SIGKILL，要么代码退太慢，要么宽限期给太短。

**Q3：`server.close()` 之后进程为什么不退出？**

`server.close()` 只做两件事：停止 accept 新连接，以及在所有已有连接关闭后触发回调。它不会主动关闭空闲的 keep-alive 连接，这些连接要等 `keepAliveTimeout` 自然回收，所以回调可能迟迟不来。Node 18.2 起可以用 `server.closeIdleConnections()` 立刻断开空闲连接，正在处理请求的连接不受影响；`closeAllConnections()` 会连 in-flight 一起断，只能当最后手段。另一类原因是有残留 handle 没关——没 `clearInterval` 的定时器、DB 连接池、MQ 消费者，可以用 `process.getActiveResourcesInfo()` 查。

**Q4：liveness 和 readiness 有什么区别？为什么 liveness 不能查数据库？**

区别在失败后的动作：liveness 失败会**重启容器**，readiness 失败只是**摘流量、不重启**。所以 liveness 回答的是「我这个进程是不是卡死了」，只能检查自身；readiness 回答的是「我现在能不能干活」，应该检查下游。如果 liveness 里查了 MySQL，MySQL 抖动三秒就会让全集群 Pod 的 liveness 同时失败、同时重启，恢复后所有实例一起冷启动建连接池，又把 MySQL 打挂，形成重启雪崩——而重启进程对修复 MySQL 毫无帮助。放在 readiness 里就很优雅：抖动期间摘流量保持存活，下游一恢复流量自动回来，全程零重启。

**Q5：PM2 的 reload 和 restart 有什么区别？**

`restart` 是把所有进程一起停掉再一起起来，中间有停机窗口。`reload` 是逐个替换 worker：先起一个新进程，等它就绪，再让老进程优雅退出，因此是零停机的，但前提是 `exec_mode: cluster`（fork 模式只有一个进程，reload 会退化成 restart）。用 reload 有两个必配项：`kill_timeout` 要设得比代码里的 `forceTimeout` 大（PM2 默认只有 1600ms，drain 根本走不完就被杀），以及配 `wait_ready: true` 并在代码里 `process.send('ready')`，让 PM2 知道新进程什么时候真的能接流量。还要注意 PM2 默认发的是 `SIGINT` 而不是 `SIGTERM`，代码里两个信号都要监听。
