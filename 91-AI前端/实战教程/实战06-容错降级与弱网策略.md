# 实战06 · 容错、降级与弱网策略

> 目标：AI 请求的失败率天然高于普通接口（上游模型服务、长连接、内容审核都会出幺蛾子），本篇把「失败之后怎么办」系统化：**超时分类、重试与续写、模型降级链、弱网队列**。这一篇决定 AI 功能是"Demo"还是"产品"。
> 更新时间：2026-10-30 ｜ 前置：实战01、实战05

## 先画失败面：AI 请求会怎么死

| 失败点 | 现象 | 该做什么 |
| --- | --- | --- |
| 鉴权/参数错误 | 401 / 400 | **不重试**，提示用户（代码 bug 或 key 过期） |
| 限流 | 429 | 退避后重试，次数多了提示"稍后再来" |
| 上游故障 | 500 / 502 / 503 | 重试 1-2 次 → 切备用模型（降级） |
| 网络断 | fetch reject / ECONNRESET | 重试 → 离线队列 |
| 首 token 慢 | loading 30s 用户跑路 | TTFT 超时 → 降级小模型 |
| 流中途停 | 回答写到一半断流 | 流间隔超时 → **续写重试** |
| 内容截断 | `finish_reason: 'length'` | 前端提示"回答被截断"+ 续写按钮 |
| 内容审核拒绝 | finish_reason 为内容策略类 | 不重试，换个提示 |

**原则先立住：可重试的静默重试（≤2 次），不可重试的立刻给用户明确原因；所有降级要对用户透明，不能装作一切正常。**

## Step 1：两个超时——loading 态和 streaming 态要分开管

普通请求一个总超时就够，流式请求必须拆成两段：

- **TTFT 超时**（Time To First Token）：发出请求到第一个 delta，超过 10s 说明上游拥堵，继续等毫无意义；
- **流间隔超时**：streaming 中两个 delta 间隔超过 15s，连接大概率已死（SSE 没有内置死亡检测）。

```ts
// web/src/chat/useTimeouts.ts
export function createStreamTimeouts(onTimeout: (kind: 'ttft' | 'stall') => void) {
  const controller = new AbortController()

  let ttft: ReturnType<typeof setTimeout>
  let stall: ReturnType<typeof setTimeout> | undefined

  const armTTFT = () => {
    ttft = setTimeout(() => {
      controller.abort(new DOMException('TTFT_TIMEOUT', 'TimeoutError'))
    }, 10_000)
  }
  const markFirstToken = () => {
    clearTimeout(ttft)
    touchStall() // 从此转入流间隔看护
  }
  const touchStall = () => {
    if (stall) clearTimeout(stall)
    stall = setTimeout(() => {
      controller.abort(new DOMException('STREAM_STALL', 'TimeoutError'))
    }, 15_000)
  }
  const dispose = () => {
    clearTimeout(ttft); clearTimeout(stall!)
  }

  return { signal: controller.signal, armTTFT, markFirstToken, touchStall, dispose, controller }
}
```

接入实战01：每个 `delta` 事件里 `timeouts.touchStall()`，第一个 delta 时 `markFirstToken()`。**abort 的 reason 会成为 fetch 抛出的错误**，catch 里据此区分「用户主动停」/「TTFT 超时」/「流停了」三种中断，分别走不同分支——用户停止保留内容（实战01），超时则进入重试（下一步）。

## Step 2：重试——不是所有错误都值得再试

### 可重试判定

```ts
const NO_RETRY_STATUS = new Set([400, 401, 403, 404, 422]) // 参数/权限类，重试必然同结果

function isRetryable(err: any): boolean {
  if (err?.name === 'TimeoutError') return true                    // 自己人：TTFT / 流停
  if (err?.name === 'AbortError') return false                     // 用户主动停
  if (NO_RETRY_STATUS.has(err?.status)) return false
  if (err?.status === 429 || err?.status >= 500) return true       // 限流/上游故障
  return err instanceof TypeError || /network|fetch/i.test(err?.message ?? '') // 断网
}
```

指数退避 + 抖动（jitter 防多端同步重试形成尖峰）：

```ts
const backoff = (n: number) => Math.min(1000 * 2 ** n, 10_000) * (0.5 + Math.random() / 2)
```

### AI 特有的重试：续写，而不是重来

普通接口重试=原样重发。流式 AI 重试有个更聪明的选项：**半截内容别扔，让模型接着写**——用户已经看到 600 字，重来一遍体验极差：

```ts
async function resumeOrRetry(messages: Message[], partial: string) {
  if (partial.length > 200) {
    // 续写：把半截回答作为 assistant 消息回填，要求继续
    const continued = await sendStream([
      ...messages,
      { role: 'assistant', content: partial },
      { role: 'user', content: '继续，从中断处接着写，不要重复已有内容。' },
    ])
    return partial + continued
  }
  return sendStream(messages) // 太短不如重来
}
```

注意：续写结果和前半段拼接口感上大概率无缝，但**不保证严格连贯**（衔接处可能重复几个字），前端拼接时去掉重叠头部即可。

## Step 3：降级链——后端路由 + 前端透明

重试用尽后进入降级。降级决策在后端（它知道有哪些备用通道），但**必须通过事件流告诉前端**，让用户知情：

```
主模型（deepseek-chat，效果好，偶尔拥堵）
  → 超时/失败
备用模型（gpt-4o-mini 或另一家厂商，质量略降但稳定）
  → 再失败
语义缓存命中（问题相似度 > 0.92，实战03 的索引可复用）
  → 再未命中
静态兜底（"服务繁忙" + 推荐问题列表）
```

```ts
// server/degrade.ts —— 降级链的骨架
const CHANNELS = [
  { name: 'primary', model: process.env.MODEL!, timeoutMs: 10_000 },
  { name: 'backup',  model: process.env.BACKUP_MODEL!, timeoutMs: 8_000 },
]

async function chatWithFallback(messages: any[], emit: Emit) {
  for (const ch of CHANNELS) {
    try {
      return await streamWithTimeout(ch, messages)   // 内部把 ch.timeoutMs 转成 abort
    } catch (err) {
      if (!isRetryable(err) || isLastChannel(ch)) continue
      emit({ type: 'degraded', from: ch.name, to: nextOf(ch).name, reason: err.message })
      //      ↑ 前端收到后显示"已切换备用通道（可能略慢/略简）"
    }
  }
  const cached = await semanticCacheLookup(messages) // 实战03 的向量检索改造成缓存
  if (cached) { emit({ type: 'degraded', to: 'cache' }); return cached }
  throw new FallbackExhaustedError()
}
```

前端只是把 `degraded` 事件渲染成一条不打断对话的浅色提示：

```tsx
{event.type === 'degraded' && (
  <div className="text-xs text-amber-500">已自动切换到备用通道，回答可能略有简化</div>
)}
```

**为什么坚持透明**：降级回答质量确实会掉，用户不知情就会归因成"这产品变笨了"。明说反而保住信任——对照指南 §10 的「AI 产品要传达不确定性」。

## 深入理解①：给降级链装上熔断器

上面的降级链有个隐藏缺陷：**它是无状态的**——主模型故障时，每一个请求都要先等 10s 超时才轮到备用模型，高峰期全部请求变慢 10 倍，雪崩就是这么发生的。

熔断器（Circuit Breaker）给每个通道加上"记忆"，三态流转：

```
closed（正常放行，记录连续失败数）
   │ 连续 N 次失败
   ▼
open（直接跳过，不再浪费超时等待）──冷却期满──▶ half-open
   ▲                                              │ 放一个探测请求
   │ 探测成功                                      ▼
   └──────────────────────────────────── 成功→closed / 失败→回到 open
```

```ts
class Breaker {
  private fails = 0
  private state: 'closed' | 'open' | 'half-open' = 'closed'
  private openedAt = 0
  constructor(private threshold = 3, private cooldownMs = 30_000) {}

  canTry(): boolean {
    if (this.state !== 'open') return true
    if (Date.now() - this.openedAt > this.cooldownMs) { this.state = 'half-open'; return true }
    return false // 熔断中：跳过这个通道，连超时都不用等
  }
  onSuccess() { this.fails = 0; this.state = 'closed' }
  onFailure() {
    if (++this.fails >= this.threshold) { this.state = 'open'; this.openedAt = Date.now() }
  }
}
```

接入降级链只改循环：

```ts
for (const ch of CHANNELS) {
  if (!ch.breaker.canTry()) { emit({ type: 'degraded', reason: '通道熔断中，已跳过' }); continue }
  try {
    const r = await streamWithTimeout(ch, messages)
    ch.breaker.onSuccess()
    return r
  } catch (err) {
    ch.breaker.onFailure()
    // ...同 Step 3
  }
}
```

主模型故障时，第 3 个请求触发熔断，之后所有请求**零等待**直达备用通道；30 秒后放一个探测请求试探恢复。两个生产细节：half-open 态会有并发探测请求同时放行（单飞/singleflight 控制是进阶版）；熔断状态应暴露到 `/healthz` 之类端点，运维能一眼看到"当前在用哪个通道"。

## Step 4：乐观 UI 与防重复发送

```ts
// 发送即上屏（本地 id），失败标记回滚——不等网络往返
const localId = crypto.randomUUID()
setMessages((prev) => [...prev, { id: localId, role: 'user', content: text, pending: true }])

// 防重复：实战01 用 abortRef 判断忙碌；这里再挡一层"双击/双触发"
if (inflightRef.current) return
inflightRef.current = true
try { /* ... */ } finally { inflightRef.current = false }
```

`crypto.randomUUID()` 生成的本地 id 同时是乐观更新的锚点：请求成功后用服务端确认替换 `pending: true`，失败则给该条消息挂红色边框 + 重试按钮。**用户已经打出去的字，任何失败路径都不能让它消失。**

## Step 5：弱网——断网不丢输入，恢复自动续

```ts
// web/src/chat/offline-queue.ts
export function useOfflineQueue() {
  const [online, setOnline] = useState(navigator.onLine)
  const queueRef = useRef<string[]>([])

  useEffect(() => {
    const goOffline = () => setOnline(false)
    const goOnline = () => {
      setOnline(true)
      const queued = queueRef.current.splice(0)   // 恢复联网：按序补发
      queued.forEach((text) => void sendRef.current?.(text))
    }
    addEventListener('offline', goOffline)
    addEventListener('online', goOnline)
    return () => { removeEventListener('offline', goOffline); removeEventListener('online', goOnline) }
  }, [])

  const send = (text: string) => {
    if (!navigator.onLine) {
      queueRef.current.push(text)
      setPendingCount(queueRef.current.length)   // UI："已加入待发队列（2）"
      return
    }
    void sendRef.current?.(text)
  }
  return { online, send }
}
```

### SSE 断线重连：带上"游标"

SSE 原生重连（`Last-Event-ID`）只对 EventSource 有效，我们是 fetch——自己实现游标重放：

```
① 流中断时记录：已收到的字符数 cursor = 742
② 重连带参：POST /api/chat { ..., resumeFrom: 742 }
③ 后端方案 A（简单）：重新生成完整回答，只发 cursor 之后的部分
   后端方案 B（省 token）：缓存本次生成结果 60s，直接从缓存切片续发
```

方案 A 实现只需一行 `full.slice(cursor)`，代价是重新计费；方案 B 省钱但要服务端暂存。Demo 阶段用 A，上量后换 B。

## 深入理解②：SSE 标准里本来就有断线重连

我们手写游标之前，先看标准答案——SSE 协议原生支持重连，靠两个帧字段：

```
data: ...
id: 42            ← 服务端给每条消息编号
retry: 3000       ← 告诉浏览器：断线后 3 秒再重连
```

浏览器原生 `EventSource` 会自动重连，并自动带上 `Last-Event-ID: 42` 请求头——服务端据此从第 43 条开始续发。**但我们的技术栈用不了它**：实战01 已经讲过，`EventSource` 只支持 GET、不能 POST 消息体，所以全 AI 行业都用 fetch 手动解析，"自动重连"这个免费福利也就没了——这正是我们自实现 `resumeFrom` 的根本原因。

不过标准机制的设计思想值得抄：**"从哪续"标准化（游标编号），"怎么续"依然是服务端的活**（EventSource 的重连也要求服务端有事件日志才能回放，等价于我们的方案 A/B 选型）。所以生产上建议：即使 fetch 解析，也照样发 `id:` 帧——网关日志可追踪，将来若有端换回 EventSource 也无缝。

## 常见坑

| 症状 | 原因 | 解法 |
| --- | --- | --- |
| 重试后用户消息消失/重复 | 重试闭包读了旧 messages | 重试函数显式接收消息参数（实战01 的教训） |
| 双倍计费 | 双击发送 / StrictMode 双触发 | inflight ref 闸门 |
| 429 越重试越密 | 多端同时退避 | 指数退避 + 随机抖动 |
| 半截回答被丢弃重来 | abort 分支一律清空 | 区分中断原因，超时走续写 |
| 降级后用户以为产品坏了 | 降级无提示 | degraded 事件 + UI 提示 |
| 主模型故障期所有请求都等超时才降级 | 降级链无状态 | 熔断器（深入理解①） |
| 断网时输入直接报错 | 无离线处理 | 待发队列 + online 事件补发 |
| 流"假活"：一直转圈不出字 | SSE 死了但没有超时看护 | 流间隔超时（本篇 Step 1） |
| 重试把 401 也重了 | 无错误分类 | NO_RETRY_STATUS |
