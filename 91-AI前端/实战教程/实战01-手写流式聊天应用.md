# 实战01 · 手写流式聊天应用（React + Node + SSE）

> 目标：不用任何 AI 框架，从零实现一个生产形态的流式聊天应用。做完你将真正理解 SSE 协议、fetch 流式读取、中断恢复——这是所有 AI 前端面试的高频考点，也是 [实战02](./实战02-AI-SDK重构聊天与工具调用.md) 里 AI SDK 帮你封装掉的全部东西。

## 最终效果

```
┌──────────────────────────────────────┐
│  user: 用一句话解释 useEffect         │
```

## Step 1：后端——先跑通非流式版

先把「请求→模型→响应」链路打通，流式下一步再加。**永远不要跳过这一步**，链路不通时流式只会让你更难排查。

```ts
// server/index.ts
import express from 'express'
import OpenAI from 'openai'

const app = express()
app.use(express.json({ limit: '1mb' }))

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,          // 密钥只在服务端
  baseURL: process.env.OPENAI_BASE_URL,
})

const SYSTEM_PROMPT = '你是一个简洁的前端技术助手，用中文回答，优先给结论再给解释。'

app.post('/api/chat', async (req, res) => {
  const history = req.body?.messages
  if (!Array.isArray(history)) {
    return res.status(400).json({ error: 'messages 必须是数组' })
  }

  const response = await client.chat.completions.create({
    model: process.env.MODEL!,
    messages: [
      { role: 'system', content: SYSTEM_PROMPT },
      ...history.slice(-20),   // 只带最近 20 条，控制 token 成本
    ],
  })

  res.json({ content: response.choices[0].message.content })
})

app.listen(3000, () => console.log('http://localhost:3000'))
```

用 curl 自测：`curl -X POST localhost:3000/api/chat -H "content-type: application/json" -d '{"messages":[{"role":"user","content":"hi"}]}'`。通了再往下。

## Step 2：后端——改成 SSE 流式

**原理**：给模型的请求加 `stream: true`，SDK 返回一个异步迭代器，每个 chunk 带一小段增量文字（`delta`）；后端把增量用 SSE 格式（`data: {...}\n\n`）写给浏览器。SSE 的详细协议对比见 `08-网络与浏览器/WebSocket深入理解.md`。

```ts
// SSE 响应头三件套 + 反向代理透传
function writeSSEHeader(res: express.Response) {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream; charset=utf-8',
    'Cache-Control': 'no-cache, no-transform',
    Connection: 'keep-alive',
    'X-Accel-Buffering': 'no', // 告诉 nginx 不要缓冲，否则前端"一次性收到全文"
  })
}

// 统一的事件协议：前端只认这 4 种事件
type SSEEvent =
  | { type: 'delta'; content: string }
  | { type: 'done'; content: string }                    // 全文，供前端校验
  | { type: 'error'; message: string }

app.post('/api/chat', async (req, res) => {
  const history = req.body?.messages
  if (!Array.isArray(history)) return res.status(400).json({ error: '参数错误' })

  writeSSEHeader(res)

  // ① 客户端断开时，中断对上游模型的请求，别浪费 token
  const abort = new AbortController()
  req.on('close', () => abort.abort())

  // ② 心跳：防止中间代理因为 15s+ 无数据而掐断连接
  const heartbeat = setInterval(() => res.write(': ping\n\n'), 15_000)

  let full = ''
  try {
    const stream = await client.chat.completions.create(
      {
        model: process.env.MODEL!,
        stream: true,                                    // ← 关键
        messages: [{ role: 'system', content: SYSTEM_PROMPT }, ...history.slice(-20)],
      },
      { signal: abort.signal },                          // 用户断开 → 上游也取消
    )

    for await (const chunk of stream) {
      const delta = chunk.choices[0]?.delta?.content ?? ''
      if (delta) {
        full += delta
        res.write(`data: ${JSON.stringify({ type: 'delta', content: delta } as SSEEvent)}\n\n`)
      }
    }
    res.write(`data: ${JSON.stringify({ type: 'done', content: full } as SSEEvent)}\n\n`)
  } catch (err: any) {
    // 用户主动断开不算错误
    if (err?.name !== 'AbortError') {
      res.write(`data: ${JSON.stringify({ type: 'error', message: err?.message ?? '模型调用失败' } as SSEEvent)}\n\n`)
    }
  } finally {
    clearInterval(heartbeat)
    res.end()
  }
})
```

**3 个容易忽略的细节**：

1. `: ping\n\n` 是 SSE 的注释行，客户端会忽略它，但能让代理认为连接活跃。
2. 事件用 JSON 包装并带 `type` 字段，前端好做分发——这是为实战04 的多事件协议打基础。
3. 如果你的 Express 挂了 `compression` 之类的压缩中间件，务必对 `text/event-stream` 跳过，否则输出会被缓冲。

## 深入理解：两个被 Demo 掩盖的网络层问题

这两个问题本地跑 Demo 时永远遇不到，一上生产全是事故。读懂它们，你对 SSE 的理解就从「会调 API」变成「懂连接本身」。

### ① HTTP/1.1 的 6 连接限制：聊天页为什么"越用越卡"

**机制**：浏览器对同一 origin 的 HTTP/1.1 并发连接数有限制（规范建议 2，现代浏览器放宽到 6，且**所有标签页共享**）。SSE 恰恰是一条常驻连接——每开一个正在生成的对话就永久占用一个名额，直到流结束。

**事故现场**：用户开 3 个标签页各挂一个流式会话 → 6 个名额耗尽 → 页面上**所有** HTTP/1.1 请求（图片、CSS、普通接口）全部排队，表现为"聊天还在收字，页面其他东西全卡死"。最小复现：

```js
// 同一个页面的控制台里跑：6 条流占满限额
for (let i = 0; i < 6; i++) {
  fetch('/api/chat', { method: 'POST', body: JSON.stringify({ messages: [{ role: 'user', content: '写一篇 2000 字的文章' }] }) })
}
// 之后页面再加载任何图片/接口——全部 pending，直到某条流结束
```

**解法按优先级**：

1. **全站上 HTTP/2**（真正解法）：h2 多路复用让所有请求共享一条 TCP 连接，"按连接数限流"的机制整个失效。Nginx 一行 `listen 443 http2`。这也解释了为什么本地开发（h1.1）能复现、上了网关就"自愈"。
2. **前端限并发**：同一 tab 最多 1 个进行中的流（本教程 hook 已做到）；跨 tab 可用 `localStorage` + `storage` 事件做简易互斥。
3. **流式走独立域名**（历史方案）：`/api/stream` 挂独立子域隔离限额，h2 普及前的主流 workaround，今天只在老网关上还有意义。

对照记忆：WebSocket 连接同样计入这个限额（Chrome 实现如此），这是 SSE vs WS 选型时「连接开销」讨论的真实背景（完整对比见 `08-网络与浏览器/WebSocket深入理解.md`）。

### ② 背压（Backpressure）：`res.write()` 的返回值不是装饰

**机制**：`res.write()` 返回 `false` 表示 socket 发送缓冲已满（超过 `highWaterMark`，默认 16KB），这段数据**没有发出去，而是堆在 Node 进程内存里排队**。Step 2 的循环无视了返回值：

```ts
for await (const chunk of stream) {
  res.write(`data: ...\n\n`)   // 返回值被丢弃了——这是个隐患
}
```

Demo 没事是因为本机回环延迟≈0；生产上手机 3G 用户收 5 万字长回答，消费速度远低于模型吐字速度 → 内存堆积 × 并发慢用户数 → Node 进程 OOM。**AI 流式是背压问题的放大器**：单响应大、耗时长、移动端占比高，三个因素全占。

**修法：await drain，让消费端反向约束生产端**：

```ts
function writeWithBackpressure(res: express.Response, data: string): Promise<void> {
  return res.write(data) ? Promise.resolve() : new Promise((r) => res.once('drain', r))
}

// 循环里改为：
await writeWithBackpressure(res, frame)
```

**精妙之处在传导链**：`await drain` 让 Node 暂停从上游模型流取数据 → SDK 的异步迭代器暂停 → 上游连接的 TCP 接收窗口收缩 → 模型服务的发送端感知到背压。整条链路没人"丢数据"，只是集体慢下来。（不能假设所有上游都会因此停止计费，所以 Step 2 的"断连即 abort 上游"仍是必要兜底。）

这正是 `07-Node/Node.js-Stream流与中间件机制.md` 里 `highWaterMark` / `drain` / `pipe` 的知识：`pipeline()` 会自动处理背压，而我们手写 SSE 等于"绕过了管道系统"，必须手工补上这一环。

> 取舍：Demo 不写背压也没事，但它成本为零（一个 await），建议从第一行代码就带上。

## Step 3：前端——正确地解析 SSE 流

**为什么不能用 `EventSource`**：它只支持 GET、不能自定义 header、不能 POST 消息体。所以 AI 应用统一用 `fetch` + `ReadableStream` 手动解析。

**最关键的认知：网络 chunk 的边界 ≠ SSE 消息的边界**。一次 `read()` 拿到的可能是半条消息、一条消息或三条半，必须用缓冲区拼接后按 `\n\n` 切分：

```ts
// web/src/chat/readSSE.ts
export async function readSSE(
  response: Response,
  onEvent: (payload: string) => void,
  signal?: AbortSignal,
) {
  const reader = response.body!.getReader()
  const decoder = new TextDecoder()
  let buffer = ''

  try {
    while (true) {
      const { done, value } = await reader.read()
      if (done) break

      buffer += decoder.decode(value, { stream: true }) // stream:true 处理跨 chunk 的多字节中文
      const messages = buffer.split('\n\n')
      buffer = messages.pop() ?? ''                     // 最后一段可能不完整，留到下一轮

      for (const msg of messages) {
        for (const line of msg.split('\n')) {
          if (line.startsWith('data: ')) onEvent(line.slice(6)) // 忽略注释行和空行
        }
      }
    }
  } finally {
    reader.releaseLock()
    void signal // 中断时 read() 会抛 AbortError，由调用方处理
  }
}
```

`decoder.decode(value, { stream: true })` 这行是中文场景的隐形坑：一个中文字符的 UTF-8 字节可能被拆在两个网络包里，不带 `stream: true` 会解码出乱码。

## Step 4：核心 Hook——状态机 + 中断

聊天本质是一个状态机。用 `status` 而不是多个 boolean，状态不可能出现矛盾组合：

```ts
// web/src/chat/useChatStream.ts
import { useCallback, useRef, useState } from 'react'
import { readSSE } from './readSSE'

export interface Message {
  role: 'user' | 'assistant'
  content: string
  stopped?: boolean   // 标记"用户中断的不完整回答"
}

type Status = 'idle' | 'loading' | 'streaming' | 'error'
// loading = 已发请求还没收到第一个字；streaming = 正在逐字输出

export function useChatStream() {
  const [messages, setMessages] = useState<Message[]>([])
  const [status, setStatus] = useState<Status>('idle')
  const abortRef = useRef<AbortController | null>(null)

  const send = useCallback(async (input: string) => {
    const text = input.trim()
    // 用 ref 判断"忙碌中"：status 是 state，闭包里拿到的是旧值，retry 后立刻 send 会被误拦
    if (!text || abortRef.current) return

    const userMsg: Message = { role: 'user', content: text }
    const aiMsg: Message = { role: 'assistant', content: '' }
    const history = [...messages, userMsg]        // 发给后端的完整历史
    setMessages([...history, aiMsg])              // UI 立刻出现空气泡
    setStatus('loading')

    const abort = new AbortController()
    abortRef.current = abort

    try {
      const res = await fetch('/api/chat', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ messages: history }),
        signal: abort.signal,
      })
      if (!res.ok || !res.body) throw new Error(`请求失败（${res.status}）`)

      setStatus('streaming')
      await readSSE(res, (payload) => {
        const event = JSON.parse(payload)
        if (event.type === 'delta') {
          setMessages((prev) => {
            const next = [...prev]
            next[next.length - 1] = {
              ...next[next.length - 1],
              content: next[next.length - 1].content + event.content,
            }
            return next
          })
        } else if (event.type === 'done') {
          setStatus('idle')
        } else if (event.type === 'error') {
          throw new Error(event.message)
        }
      }, abort.signal)
    } catch (err: any) {
      if (err.name === 'AbortError') {
        // 用户主动停止：保留半截内容并打标，状态归位
        setMessages((prev) => {
          const next = [...prev]
          const last = next[next.length - 1]
          next[next.length - 1] = { ...last, stopped: true }
          return next
        })
        setStatus('idle')
      } else {
        setStatus('error')
      }
    } finally {
      abortRef.current = null
    }
  }, [messages])

  const stop = useCallback(() => abortRef.current?.abort(), [])
  const retry = useCallback(() => {
    // 丢弃最后一条 user + 失败的 assistant 消息，重新发送同一段文字
    const lastUserIdx = messages.findLastIndex((m) => m.role === 'user')
    if (lastUserIdx === -1) return
    const text = messages[lastUserIdx].content
    setMessages(messages.slice(0, lastUserIdx)) // send 会重新追加 user 消息
    void send(text)
  }, [messages, send])

  return { messages, status, send, stop, retry }
}
```

**两个设计决策的 why**：

- **中断时保留半截内容**：用户花了 15 秒等来的 800 字不应该因为点了停止就消失。`stopped: true` 让 UI 可以显示「已停止」标记。
- **error 状态下保留用户输入和空气泡**：重试按钮直接复用 `retry()`，用户永远不需要重新打一遍字——这是 AI 产品 UX 的底线（对照指南 §10）。

## Step 5：聊天 UI

```tsx
// web/src/chat/ChatUI.tsx
import { useEffect, useRef, useState } from 'react'
import { useChatStream } from './useChatStream'

export default function ChatUI() {
  const { messages, status, send, stop, retry } = useChatStream()
  const [input, setInput] = useState('')
  const listRef = useRef<HTMLDivElement>(null)
  const userScrolledUp = useRef(false)

  // 自动滚动：贴底时跟随，用户上滑查看历史时不打扰
  useEffect(() => {
    const el = listRef.current!
    if (!userScrolledUp.current) el.scrollTop = el.scrollHeight
  }, [messages])

  const onScroll = () => {
    const el = listRef.current!
    const distanceFromBottom = el.scrollHeight - el.scrollTop - el.clientHeight
    userScrolledUp.current = distanceFromBottom > 80 // 距底超过 80px 视为在看历史
  }

  const onKeyDown = (e: React.KeyboardEvent) => {
    if (e.key === 'Enter' && !e.shiftKey) {
      e.preventDefault()
      void send(input)
      setInput('')
    }
  }

  return (
    <div className="flex h-screen flex-col">
      <div ref={listRef} onScroll={onScroll} className="flex-1 overflow-y-auto p-4">
        {messages.map((m, i) => (
          <div key={i} className={`mb-3 flex ${m.role === 'user' ? 'justify-end' : 'justify-start'}`}>
            <div className={`max-w-[80%] whitespace-pre-wrap rounded-lg px-3 py-2 ${
              m.role === 'user' ? 'bg-blue-500 text-white' : 'bg-gray-100'
            }`}>
              {m.content || (status === 'loading' ? '思考中…' : '')}
              {m.stopped && <span className="ml-1 text-xs text-gray-400">（已停止）</span>}
              {status === 'streaming' && i === messages.length - 1 && m.role === 'assistant' && (
                <span className="animate-pulse">▍</span>
              )}
            </div>
          </div>
        ))}
      </div>

      {status === 'error' && (
        <div className="bg-red-50 px-4 py-2 text-sm text-red-600">
          生成失败 <button onClick={retry} className="underline">重试</button>
        </div>
      )}

      <div className="flex gap-2 border-t p-4">
        <textarea
          value={input}
          onChange={(e) => setInput(e.target.value)}
          onKeyDown={onKeyDown}
          rows={2}
          className="flex-1 resize-none rounded border p-2"
          placeholder="Enter 发送，Shift+Enter 换行"
        />
        {status === 'idle' || status === 'error' ? (
          <button onClick={() => { void send(input); setInput('') }}>发送</button>
        ) : (
          <button onClick={stop}>停止</button>
        )}
      </div>
    </div>
  )
}
```

> StrictMode 提醒：如果你把 `send` 挂在 `useEffect` 里自动触发，React 18 开发模式下 effect 会执行两次，需要在中断后判断 `messages` 是否已有回答再决定是否重发。手动点击触发的场景没有这个问题。更多 Hooks 避坑见 `05-React/React_Hooks原理与实战避坑.md`。

## 常见坑（生产事故预防清单）

| 症状 | 原因 | 解法 |
| --- | --- | --- |
| 等很久后一次性出全文 | 代理/中间件缓冲了 SSE | 响应头加 `X-Accel-Buffering: no`；跳过压缩中间件 |
| 中文偶尔出现乱码/方块 | 多字节字符被网络包拆开 | `decoder.decode(value, { stream: true })` |
| 内容偶尔缺失或 JSON 解析报错 | 按网络 chunk 直接解析，没按 `\n\n` 切分 | 缓冲区拼接后再切（Step 3） |
| 长回答中途断了 | 代理空闲超时 | 服务端 15s 心跳注释行 |
| 点停止后内容消失 | abort 后把状态清空了 | catch `AbortError`，保留已累积内容 |
| 用户停止了，模型还在生成计费 | 只断了浏览器连接 | `req.on('close')` 里 abort 上游请求 |
| 手机上打字时页面抖动 | 自动滚动强制 `scrollTop` | 距底判断，用户上滑时不跟随 |
| 页面其他请求莫名排队卡死 | HTTP/1.1 同域 6 连接被多条 SSE 占满 | 全站 h2 或限制并发流（深入理解①） |
| 高并发慢客户端下 Node 内存暴涨 | `res.write` 忽略背压，数据堆在内存 | `await writeWithBackpressure()`（深入理解②） |
| API Key 出现在前端 bundle | 直接在浏览器调模型接口 | 一律走后端代理（本教程架构） |

## 延伸练习

1. 给消息加 Markdown 渲染（`react-markdown`），注意**流式结束后再渲染代码块**，避免语法高亮反复重排（对照指南 §4）。
2. 后端加简单限流：内存 Map 记录 IP → 时间戳数组，1 分钟最多 20 次。
3. 把对话历史存进 `localStorage`，刷新页面不丢失。
4. 复现深入理解①：同页开 6 条流，观察图片加载排队；再打开 Chrome DevTools 的网络限速（Slow 3G），在 `writeWithBackpressure` 加个内存日志，对比开/关背压时 `process.memoryUsage()` 的差异。
