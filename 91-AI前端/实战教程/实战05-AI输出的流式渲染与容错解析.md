# 实战05 · AI 输出的流式渲染与容错解析

> 目标：AI 的回答到达浏览器之后，前端还有一层硬仗——流式 Markdown 不闪不卡、半截 JSON 能用、渲染不引入 XSS。本篇把「处理 AI 返回内容」的三件武器讲透：**增量渲染、partial 解析、安全净化**。
> 更新时间：2026-10-30 ｜ 前置：实战01（流式接收）

## 问题设定：你收到的是"半截文本"

流式输出意味着任何时刻你手里的内容都是**不完整的**：

```
1. 一个没闭合的代码块：   "```js\nfunction add(a, b"
2. 一段没写完的 JSON：     {"title":"防抖","tags":["Java
3. 一个跨 chunk 的表格：   | 参数 | 说明 |\n| --- | --- |\n| id
```

原生思维（收完整再 parse/render）在这里全部失效。三个子问题分别对应本篇三步：**渲染性能与半截语法** → **partial JSON 解析** → **安全**。

## Step 1：流式 Markdown——分块渲染 + 合帧节流

### 先看两性能问题

**问题 A：每个 delta 都 setState**。模型一秒能吐 30+ 个 chunk，每次都触发整棵消息树 re-render，5000 token 的长回答后面越来越卡。

**问题 B：全量重解析**。`<ReactMarkdown>{content}</ReactMarkdown>` 每次渲染都从头解析整篇 Markdown——回答越长解析越慢，而前面 90% 的内容根本没变。

### 解法：稳定块 memo 化，只有"活动块"在动

流式内容是**追加式**的——按空行切成段落后，除最后一段外全部不再变化。这是可以吃的免费红利：

```tsx
// web/src/render/StreamingMarkdown.tsx
import { memo, useMemo } from 'react'
import ReactMarkdown from 'react-markdown'

export function StreamingMarkdown({ content }: { content: string }) {
  // 按空行分块：前面的块永远稳定，最后一块在增长
  const { stable, active } = useMemo(() => {
    const parts = content.split(/\n{2,}/)
    // 松散列表/块引用是"语法上连续"的块，空行不等于边界，要并回上一块（见文末深入理解①）
    const merged: string[] = []
    for (const part of parts) {
      const prev = merged[merged.length - 1]
      if (prev && /^\s*(?:[-*+]\s|\d{1,3}[.)]\s|>\s?)/.test(part)) {
        merged[merged.length - 1] = `${prev}\n\n${part}`
      } else {
        merged.push(part)
      }
    }
    return { stable: merged.slice(0, -1), active: merged.at(-1) ?? '' }
  }, [content])

  return (
    <>
      {stable.map((text, i) => (
        <StableBlock key={i} text={text} />   // memo：text 不变就跳过重渲
      ))}
      {active && <ActiveBlock text={active} />}
    </>
  )
}

// 关键：稳定块用 memo 锁死。内容追加时只有 active 块在重解析
const StableBlock = memo(function StableBlock({ text }: { text: string }) {
  return <ReactMarkdown>{text}</ReactMarkdown>
})
```

### 活动块：处理"半截代码围栏"

半截 ```js 代码块交给语法高亮器会反复报错/闪烁。**用围栏数量奇偶性判断是否闭合**，未闭合时先按纯文本渲染，闭合瞬间切换高亮：

```tsx
function ActiveBlock({ text }: { text: string }) {
  const fences = (text.match(/```/g) ?? []).length
  if (fences % 2 === 1) {
    // 未闭合：取最后一个围栏之后的内容，纯文本渲染（低透明度提示"生成中"）
    const code = text.split('```').at(-1) ?? ''
    return <pre className="opacity-70"><code>{code.replace(/^\w*\n/, '')}</code></pre>
  }
  return <ReactMarkdown>{text}</ReactMarkdown>
}
```

同样的奇偶技巧适用于任何"成对语法"：行内公式 `$...$`、表格分隔行、HTML 标签。**核心思路统一：语法没闭合前降级渲染，闭合后再升级**。

### 合帧节流：渲染频率与到达频率解耦

delta 到达频率（30+/秒）远超屏幕刷新（60 帧即每秒最多 60 次可见变化）。用 ref 缓冲、rAF 合帧，一秒最多真实渲染 60 次：

```ts
// web/src/render/useStreamBuffer.ts
export function useStreamBuffer() {
  const bufRef = useRef('')
  const rafRef = useRef(0)
  const [visible, setVisible] = useState('')

  const push = useCallback((delta: string) => {
    bufRef.current += delta
    if (!rafRef.current) {
      rafRef.current = requestAnimationFrame(() => {
        rafRef.current = 0
        setVisible((v) => v + bufRef.current)   // 一次性吐出这一帧攒的量
        bufRef.current = ''
      })
    }
  }, [])

  // 结束时把残留刷出 + 取消挂起的 rAF
  const flush = useCallback(() => {
    if (rafRef.current) cancelAnimationFrame(rafRef.current)
    rafRef.current = 0
    if (bufRef.current) { setVisible((v) => v + bufRef.current); bufRef.current = '' }
  }, [])

  useEffect(() => () => { if (rafRef.current) cancelAnimationFrame(rafRef.current) }, [])

  return { visible, push, flush }
}
```

实战01 的 `useChatStream` 里把 `setMessages(追加 delta)` 换成 `buffer.push(delta)`，`done` 事件时 `flush()`，长回答的卡顿感立刻消失。

### 长对话：消息级 memo + 虚拟列表

实战01 的 `setMessages(prev => [...prev, 改最后一条])` 写法有个隐藏好处：旧消息对象引用不变。给消息条目套上 `memo` 后，流式期间只有最后一条在重渲。上百条消息的会话再加虚拟列表（`react-virtuoso`，自动滚动的 followOutput 属性正好覆盖实战01 的滚动逻辑）。

## 深入理解：分块渲染的两个进阶话题

### ① 空行分块的正确性缺口：松散列表与块引用

"按空行分块"有一个隐含假设：**空行 = Markdown 块的边界**。它不总是成立——松散列表和块引用是语法上连续的块，中间允许有空行：

```markdown
1. 甲            ← 有序列表项之间有空行（松散列表）
                  ← 空行没有结束列表！
2. 乙
3. 丙
```

被空行切成三块后，每块独立解析——**有序列表编号重置，渲染成 1. 1. 1.**；块引用同理被拆成两段不相干的引用。Step 1 代码里的 `merged` 修正就是治这个：空行切完后再扫一遍，下一块若以列表标记（`-`/`*`/`1.`）或引用标记（`>`）开头，就并回上一块。

代价是 memo 粒度略降（合并块变大，"稳定"得晚一点），正确性优先。更彻底的方案是真正的增量 Markdown 解析（流式喂给 remark 之类的解析器），复杂度高一个数量级——教学版到"规则修正"为止，长文生产场景值得投入。

### ② rAF 合帧 vs React 并发：useDeferredValue 的边界

React 18 有自己的答案——`useDeferredValue`。它和 rAF 合帧解决的不是同一个问题：

| | rAF 合帧（本教程方案） | useDeferredValue |
| --- | --- | --- |
| 控制的是 | 更新**频率**（每秒最多 N 次解析渲染） | 更新**优先级**（不减少次数，渲染可中断让位） |
| 依赖 | 任何框架可用 | React 并发特性专属 |
| 解决 | 流式高频 setState + 重复解析的成本 | 输入/滚动被大渲染阻塞的卡顿 |

```tsx
const visible = useStreamBuffer()            // rAF 合帧后的文本
const deferred = useDeferredValue(visible)   // 可叠加：解析慢时输入先走
```

为什么本教程主推合帧：`useDeferredValue` 让渲染"可中断"，但**每次渲染的解析成本一分不少**——markdown 解析 5000 字该慢还是慢，只是不再阻塞输入；合帧则直接减少了每秒的解析次数。两者正交，追求极致可以叠加。并发特性的原理背景见 `05-React/React_Fiber与Concurrent_Mode详解.md`。

## Step 2：partial JSON——没收完就先用人话总结

场景：让模型输出结构化 JSON（表单预填、卡片数据），用户不该盯着进度条等最后一个 `}`。

### 手写一个"尽力补全"解析器

思路：一次遍历，跟踪**引号状态**和**括号栈**，结尾缺什么补什么：

```ts
// web/src/render/partial-json.ts
export function parsePartialJson(raw: string): unknown {
  try { return JSON.parse(raw) } catch { /* 继续补救 */ }

  // ① 扫描：记录是否悬在字符串里 + 未闭合的括号栈
  let inString = false, escape = false
  const stack: string[] = []
  for (const ch of raw) {
    if (inString) {
      if (escape) escape = false
      else if (ch === '\\') escape = true
      else if (ch === '"') inString = false
      continue
    }
    if (ch === '"') { inString = true; continue }
    if (ch === '{' || ch === '[') stack.push(ch)
    else if (ch === '}' || ch === ']') stack.pop()
  }

  // ② 补全：悬空字符串补引号；尾部悬空的 , 和 : 截掉；栈逆序补括号
  let out = raw
  if (inString) out += '"'
  out = out.replace(/,\s*$/, '')
  if (/:\s*$/.test(out)) out = out.replace(/,?\s*"[^"]*"\s*:\s*$/, '') // 悬空键连键一起删
  while (stack.length) out += stack.pop() === '{' ? '}' : ']'

  try { return JSON.parse(out) } catch { return undefined } // 真救不了就返回 undefined
}
```

教学版覆盖 90% 场景（悬空字符串、悬空逗号、悬空键、未闭合容器）。极端 case（字符串里出现转义边界、数字写到一半 `"total": 12`）用成熟库（`partial-json`）或 AI SDK 的 `streamObject`——它直接给你 partial state，不用自己解析。

### 增量填表的"脏字段保护"

流式填表最大的坑：**AI 正在慢慢填 title，用户已经手动改了 summary，一刷新又把用户的修改覆盖了**。解法：只覆盖用户没碰过的字段：

```ts
function applyPartialFill(form: FormState, partial: Partial<FormState>) {
  const next = { ...form }
  for (const [key, value] of Object.entries(partial)) {
    if (!(key in next)) (next as any)[key] = value          // 新字段：填入
    else if (!dirtyRef.current.has(key)) (next as any)[key] = value // 旧字段且用户没改过：更新
    // 用户改过：跳过，人的输入永远优先
  }
  return next
}
```

「AI 建议覆盖，人的编辑锁定」——这是实战04 审批思想在表单场景的变体。

## Step 3：安全——流式场景的三条红线

**红线 1：永远不要用 `dangerouslySetInnerHTML` 直接渲染 AI 输出**。`react-markdown` 默认不执行内嵌 HTML，安全；但一旦为了样式接了 `rehype-raw`（解析原始 HTML），必须过 DOMPurify：

```ts
import DOMPurify from 'dompurify'
const clean = DOMPurify.sanitize(html, { USE_PROFILES: { html: true } })
```

**红线 2：链接协议白名单**。模型可能输出 `[点击领奖](javascript:alert(1))` 或 `data:text/html,...`：

```tsx
<ReactMarkdown
  // 只放行 http(s)，其余一律替换成 #（react-markdown v9 的 urlTransform）
  urlTransform={(url) => /^(https?:)?\/\//.test(url) ? url : '#'}
>
  {content}
</ReactMarkdown>
```

**红线 3：净化要作用于"已到达的全部内容"，不是单个 delta**。半截 `<scr` + 下一个 delta `ipt>` 分开看都是无害字符串——净化必须放在聚合后的完整内容上（本篇 Step 1 的架构天然满足：净化在块渲染处做）。

再加一层兜底：页面 CSP 头（`Content-Security-Policy` 禁 inline script），即使前两层失守，注入也不执行。

## 常见坑

| 症状 | 原因 | 解法 |
| --- | --- | --- |
| 长回答越流越卡 | 每 delta setState + 全量 Markdown 重解析 | 分块 memo + rAF 合帧 |
| 代码块反复闪烁/高亮报错 | 半截围栏就送高亮器 | 围栏奇偶检测，闭合前纯文本 |
| 流式中 JSON.parse 频繁抛错 | 内容天然不完整 | parsePartialJson / streamObject |
| 用户改过的字段被 AI 覆盖 | 流式更新无脑全量 set | 脏字段保护 |
| markdown 里点链接执行脚本 | urlTransform 没限制协议 | 协议白名单 + CSP |
| 表格渲染错乱 | 表头和分隔行跨 chunk | 分块渲染天然规避（空行分块）+ 表格行缓存 |
| 有序列表编号变成 1. 1. 1. | 松散列表被空行分块切断 | 延续标记并回上一块（深入理解①） |
| 停止生成时最后几个字丢了 | rAF 还没执行就 abort | abort 时手动 `flush()` |

## 延伸练习

1. 给 `ActiveBlock` 加表格支持：检测 `|---|` 分隔行是否已出现，未出现时整块降级为纯文本。
2. 用 `partial-json` 库替换手写解析器，对比边界 case 的成功率。
3. 把消息列表接入 `react-virtuoso`，验证 200 条消息 + 流式中滚动依然 60fps。
4. 用一段松散有序列表（项间有空行）做流式测试，先注释掉 `merged` 修正观察编号重置，再恢复验证——亲手触发一次深入理解①的 bug。
