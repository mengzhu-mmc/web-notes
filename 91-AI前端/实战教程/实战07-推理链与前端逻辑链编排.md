# 实战07 · 推理链与前端逻辑链编排

> 目标：把「链」这个 AI 前端的高级形态讲透——**模型的思考链**（推理模型的 reasoning 流如何展示）和**开发者的逻辑链**（多步 AI 任务如何编排、单步重试、人可介入）。做完这一篇，7 篇教程闭环。
> 更新时间：2026-10-30 ｜ 前置：实战01（SSE）、实战04（会对照 Agent）、实战05（流式渲染）

## 先分清两种"链"

| | 思考链（CoT / reasoning） | 逻辑链（Chain / Pipeline） |
| --- | --- | --- |
| 谁决定步骤 | **模型**（推理模型自动展开思考） | **开发者**（代码里定义死步骤顺序） |
| 前端做什么 | 展示：思考过程折叠面板、计时、双流切换 | 编排：步骤卡片、单步重试、中间结果编辑 |
| 典型场景 | DeepSeek-R1、o 系列做数学/代码/规划 | 翻译→审校→润色；提纲→扩写→配图建议 |
| 可控性 | 低（思考是黑盒） | 高（每步可测、可换模型） |

两者经常组合：逻辑链的某一步内部用推理模型。先做展示（Part 1），再做编排（Part 2）。

## Part 1：推理模型的思考流展示

### 现状与协议

推理模型（DeepSeek `deepseek-reasoner`、智谱等，OpenAI 兼容接口普遍采用此约定）的流式返回有**两路内容**：`reasoning_content`（思考过程）和 `content`（最终答案）。OpenAI 的 o 系列思考过程不直接随 content 暴露，接口各异，但前端模式是一样的。

后端只需在实战01 的分流处加一个分支：

```ts
// server/index.ts —— 在 for await 循环里
for await (const chunk of stream) {
  const delta = chunk.choices[0]?.delta ?? {}
  if (delta.reasoning_content) {
    res.write(`data: ${JSON.stringify({ type: 'reasoning-delta', content: delta.reasoning_content })}\n\n`)
  }
  if (delta.content) {
    res.write(`data: ${JSON.stringify({ type: 'delta', content: delta.content })}\n\n`)
  }
}
```

### 前端消息结构：思考与答案分开存

```ts
interface AssistantMessage {
  role: 'assistant'
  reasoning: string   // 思考流——仅前端展示
  content: string     // 答案流
  thinkingMs?: number // 思考耗时
}
```

### 思考面板交互（照抄主流产品）

```
┌─ 💭 已深度思考（用时 12 秒）      [展开/收起] ─┐
│  用户想要的是…先排除 A…再验证 B…               │   ← 默认收起，灰色小字
└───────────────────────────────────────────────┘
┌─ 答案正文（正常气泡渲染）                        ─┐
```

状态机要点：

```tsx
function ThinkingPanel({ reasoning, answerStarted, elapsed }: Props) {
  const [open, setOpen] = useState(true)

  // 答案开始流出时自动折叠思考面板（用户如果手动展开过就不打扰）
  const userToggled = useRef(false)
  useEffect(() => {
    if (answerStarted && !userToggled.current) setOpen(false)
  }, [answerStarted])

  return (
    <div className="mb-2 rounded border border-gray-200 bg-gray-50 text-sm text-gray-500">
      <button onClick={() => { userToggled.current = true; setOpen(!open) }}>
        💭 {answerStarted ? `已深度思考（用时 ${Math.round(elapsed / 1000)} 秒）` : `思考中… ${(elapsed / 1000).toFixed(0)}s`}
      </button>
      {open && (
        <div className="max-h-64 overflow-y-auto whitespace-pre-wrap px-3 pb-2 text-xs">
          {reasoning || '（等待模型输出思考…）'}
        </div>
      )}
    </div>
  )
}
```

细节：

- **思考中计时器**用 `setInterval` 每秒更新 elapsed，答案开始即停——用户等 60 秒时"正在思考 47s…"比转圈图标安抚得多；
- 思考文本用实战05 的 `StreamingMarkdown` 渲染？**不要**——思考流是过程性内容，纯文本 + 自动滚动就够，省下的解析开销留给答案流；
- 思考面板默认展开、答案出现自动收起：让用户"看见它在想"，建立对延迟的容忍。

### ⚠️ 本 Part 最大的坑：reasoning_content 不能回传

下一轮请求的历史里，assistant 消息**只能带 content**。把 `reasoning_content` 塞回 messages，DeepSeek 等兼容接口会直接 400。所以发送历史时必须剔除：

```ts
// 发给后端前序列化：只保留答案
const history = messages.map((m) =>
  m.role === 'assistant' ? { role: m.role, content: m.content } : m,
)
```

这也解释了为什么把 `reasoning` 存成独立字段（而不是拼进 content）是对的——回传时天然干净。

## Part 2：前端逻辑链编排（Chain）

### 场景：长文创作流水线

「主题 → 提纲 → 扩写 → 润色」，三步各有最佳温度：提纲要稳（低温度），扩写要活（高温度），润色再收紧。**步骤固定、逐步可控**——这是链相对 Agent（实战04）的核心优势。

### 链的定义：数据驱动，不是代码驱动

```ts
// web/src/chain/define.ts
export interface ChainStep {
  id: string
  title: string
  temperature: number          // 每步独立调参——链的专属福利
  model?: string               // 甚至可以换模型（提纲用推理模型，润色用普通模型）
  prompt: (inputs: Record<string, string>) => string
  // 步间契约：声明本步产出什么，下游才能依赖
  outputHint: string
}

export const writingChain: ChainStep[] = [
  {
    id: 'outline',
    title: '生成提纲',
    temperature: 0.2,
    outputHint: 'Markdown 列表，每项一个章节标题',
    prompt: (i) => `为主题「${i.topic}」拟 5 章提纲，只输出列表。`,
  },
  {
    id: 'draft',
    title: '按提纲扩写',
    temperature: 0.7,
    outputHint: '按提纲章节组织的长文',
    prompt: (i) => `按此提纲逐章扩写成文，每章 200 字：\n${i.outline}`,
  },
  {
    id: 'polish',
    title: '润色定稿',
    temperature: 0.3,
    outputHint: '润色后的最终稿',
    prompt: (i) => `润色下面文章，保持章节结构不变，删掉空话：\n${i.draft}`,
  },
]
```

### 执行器：checkpoint 是灵魂

```ts
// web/src/chain/run.ts
export interface StepState {
  status: 'pending' | 'streaming' | 'done' | 'error'
  output: string
  error?: string
}

export async function runChain(
  chain: ChainStep[],
  inputs: Record<string, string>,
  states: Record<string, StepState>,
  onUpdate: (id: string, patch: Partial<StepState>) => void,
  options: { fromStep?: string } = {},
) {
  const results = { ...inputs }
  const startIdx = chain.findIndex((s) => s.id === options.fromStep) // 从失败步续跑
  if (startIdx === -1) throw new Error('fromStep 不在链中')

  for (const step of chain.slice(startIdx)) {
    // 复用前面步骤的 checkpoint，绝不重复计算已成功的步骤
    if (states[step.id]?.status === 'done') { results[step.id] = states[step.id].output; continue }

    onUpdate(step.id, { status: 'streaming' })
    try {
      // runStep 内部 = 实战01 的 SSE 消费 + 实战06 的超时看护，略
      results[step.id] = await runStep(step, results)
      onUpdate(step.id, { status: 'done', output: results[step.id] })
    } catch (err: any) {
      onUpdate(step.id, { status: 'error', error: err.message })
      throw new ChainStepError(step.id, err) // 停在失败步，上游 checkpoint 保留
    }
  }
  return results
}
```

**单步重试 = `runChain(chain, inputs, states, onUpdate, { fromStep: 'polish' })`**：提纲和扩写的结果直接从 checkpoint 复用，只重跑润色。这是逻辑链对用户体验最大的贡献——三步链最后一步失败，不用烧三倍 token 重来。

### 步骤卡片 UI：进度 + 中间结果 + 人工介入

```tsx
function StepCard({ step, state, onRetry, onEdit }: Props) {
  return (
    <div className={`rounded border p-3 ${
      state.status === 'error' ? 'border-red-300 bg-red-50'
      : state.status === 'streaming' ? 'border-blue-300' : 'border-gray-200'
    }`}>
      <div className="mb-2 flex items-center justify-between text-sm">
        <span>{state.status === 'done' ? '✅' : state.status === 'error' ? '❌' : '⏳'} {step.title}</span>
        <div className="flex gap-2">
          {state.status === 'done' && (
            <button onClick={() => {
              // 人工介入：改完中间结果，从本步重跑（后续步骤作废重来）
              const next = prompt('编辑中间结果', state.output)
              if (next !== null) onEdit(step.id, next)
            }}>编辑</button>
          )}
          {state.status === 'error' && <button onClick={onRetry}>重试本步</button>}
        </div>
      </div>

      {/* 中间结果默认折叠，避免界面被长文淹没 */}
      <details>
        <summary className="text-xs text-gray-400">{state.output ? `${state.output.length} 字` : state.status}</summary>
        <div className="mt-2 whitespace-pre-wrap text-sm">{state.output || state.error}</div>
      </details>
    </div>
  )
}
```

**「编辑」按钮就是链的 Human-in-the-loop**：AI 写的提纲不合适，用户改两笔再继续——比实战04 的事前审批更轻（事后修正），两种模式按场景选：**不可逆操作用事前审批，可迭代产出用事后编辑**。

### 并行分支：fan-out → 汇总

```ts
// 三个角度并行生成，全部完成后再汇总
async function runFanOut(topic: string) {
  const angles = ['性能视角', '安全视角', '体验视角']
  const parts = await Promise.all(
    angles.map((a) => runStep(singleStep(`从${a}分析：${topic}`), { topic })),
  )
  return runStep(mergeStep, { parts: parts.join('\n\n') }) // 汇总步依赖全部结果
}
```

UI 上并行步骤显示为并排卡片，全部转完才亮起汇总卡。注意 `Promise.all` 任一分支失败的处理策略：**任一失败即整体可重试失败分支**（把 `Promise.all` 换成 `allSettled` + 逐个判断）。

## 链 vs Agent：怎么选（对照实战04）

| 维度 | 逻辑链（本篇） | Agent（实战04） |
| --- | --- | --- |
| 步骤决策 | 开发者写死 | 模型现场决定 |
| 可测试性 | 每步独立可测、可 mock | 难（行为不确定） |
| 成本 | 固定（N 步 = N 次调用） | 不定（maxSteps 内浮动） |
| 失败处理 | 精确到单步重跑 | 整轮重来或从挂起点恢复 |
| 适用 | 生产管道、流程明确的任务 | 开放式任务、工具组合探索 |
| 混合用法 | 链中某一步内部跑一个 mini-agent | Agent 的某个工具内部是一条链 |

**经验法则**：能用链就用链（可控可测），链表达不了的自由度才交给 Agent；两者嵌套使用是常态。

## 常见坑

| 症状 | 原因 | 解法 |
| --- | --- | --- |
| 下一轮请求 400 | reasoning_content 被塞回历史 | 发送前剔除，只传 content |
| 思考面板白屏干等 | 思考流没渲染/没计时 | 纯文本流式 + 秒级计时器 |
| 链中途失败全部重来 | 无 checkpoint | states 记录 + fromStep 续跑 |
| 中间结果格式漂移 | 上游输出变化破坏下游 prompt | outputHint 契约 + 步间校验（实战05 的 partial 解析 + schema 校验） |
| 上下文爆炸 | 每步都带全部前文 | prompt 函数只引用必要输入，长文传摘要 |
| 用户改了中间结果被覆盖 | 重跑时读了旧 checkpoint | onEdit 更新 states 后再 fromStep 重跑 |
| 并行分支一个失败全链崩 | Promise.all 短路 | allSettled + 分支级重试 |
| 答案出现时思考面板还占半屏 | 没做自动折叠 | answerStarted 时收起（用户手动展开过则尊重） |

## 延伸练习

1. 给链加"条件跳过"：润色步根据 `draft` 长度决定执行或跳过（`skipIf` 字段）。
2. 把 fan-out 的三个分支结果做相似度去重后再汇总（复用实战03 的 embedding）。
3. 链的某一步换成推理模型，思考面板嵌进步骤卡片里展示。
