## 六、包管理

### Q: pnpm 的工作原理是什么？

**难度**：⭐⭐⭐⭐ | **频率**：🔥🔥🔥

**答：**

pnpm 通过**硬链接 + 虚拟 store**解决了 npm/yarn 的空间浪费和幽灵依赖问题。

**npm/yarn 的问题：**

```
问题1：磁盘空间浪费
  每个项目都把 node_modules 完整拷贝一份
  100 个项目 × react@18（3MB）= 300MB 重复存储

问题2：幽灵依赖（Ghost Dependencies）
  npm 的扁平化安装（hoisting）把所有依赖都提升到顶层 node_modules
  你的代码可以 import 到没有在 package.json 声明的包
  → 代码脆弱：这个包被某个依赖升级/删除时，你的代码莫名崩溃
```

**pnpm 的核心机制：**

```
pnpm 的全局 content-addressable store（内容寻址存储）：
  ~/.pnpm-store/
  └── v3/
      └── files/
          ├── 00/
          │   └── abc123...（文件内容的 SHA256 hash 作为文件名）
          ├── 01/
          └── ...
  
  每个文件只存一份（按内容 hash 存储），不同版本的包可以共享相同内容的文件

项目的 node_modules 结构：
  node_modules/
  ├── .pnpm/                          ← 虚拟 store（所有包的真实位置）
  │   ├── react@18.2.0/
  │   │   └── node_modules/
  │   │       └── react/              ← 通过硬链接指向全局 store
  │   └── lodash@4.17.21/
  │       └── node_modules/
  │           └── lodash/             ← 硬链接到全局 store
  ├── react → .pnpm/react@18.2.0/node_modules/react   ← 符号链接（symlink）
  └── lodash → .pnpm/lodash@4.17.21/...
  
  只有在 package.json 声明的包才会出现在 node_modules 顶层（符号链接）
  未声明的包在 node_modules 顶层不可见 → 解决幽灵依赖
```

**硬链接 vs 符号链接：**

```bash
# 硬链接（Hard Link）：
# 两个文件名指向磁盘上同一块数据（inode）
# 任意一个"被删除"，数据还在（引用计数 > 0）
# 不占额外空间
ln /global/store/react/index.js ./node_modules/.pnpm/react@18/index.js

# 符号链接（Symbolic Link / Symlink）：
# 类似快捷方式，指向另一个路径
# node_modules/react → .pnpm/react@18.2.0/node_modules/react
ln -s ../.pnpm/react@18.2.0/node_modules/react ./node_modules/react
```

**效果对比：**

| 特性 | npm/yarn | pnpm |
|---|---|---|
| 磁盘空间 | 每个项目完整拷贝 | 全局 store 共享（硬链接）|
| 安装速度 | 慢（复制文件）| 快（创建链接）|
| 幽灵依赖 | ❌ 有（扁平化 hoisting）| ✅ 无（严格模式）|
| node_modules 结构 | 扁平（所有包并列）| 嵌套 + 符号链接 |
| Monorepo 支持 | yarn workspaces | pnpm workspace（更省空间）|

**🔍 深层原理**

pnpm 的核心思想来自**内容寻址存储**（content-addressable storage）：

1. 安装包时，把每个文件的内容 hash（SHA256）作为 key 存入全局 store
2. 同一内容的文件在全局 store 里只存一份（去重）
3. 项目 node_modules 里的文件通过**硬链接**指向全局 store 里的对应文件
4. 不同版本的同一个包，只有差异的文件需要新存储，相同的文件共享

结果：100 个项目使用同版本 react，磁盘只存 1 份，但每个项目的 node_modules 里都"有" react（通过硬链接）。

**💡 踩坑点**

```bash
# 坑1：某些工具不支持 pnpm 的符号链接结构
# Electron、某些 bundler 的 node_modules 解析不走 symlink
# ✅ .npmrc 配置
node-linker=hoisted  # 退回到 npm 扁平化结构（失去 pnpm 优势但兼容性好）
# 或针对特定包
public-hoist-pattern[]=*electron*

# 坑2：pnpm 不会自动安装 peerDependencies（npm7+ 会自动安装）
# 如果包的 peerDependencies 没满足，会有警告但不报错
# ✅ 手动安装 peerDependencies
pnpm add react react-dom  # 确保 peer deps 已安装

# 坑3：CI 环境没有全局 store，pnpm 退化为普通安装
# ✅ 配置 CI 缓存 ~/.pnpm-store 目录
# GitHub Actions:
# - uses: actions/cache@v3
#   with:
#     path: ~/.pnpm-store
#     key: pnpm-${{ hashFiles('pnpm-lock.yaml') }}
```

**🎯 面试追问**

- **Q: pnpm 和 yarn PnP（Plug'n'Play）有什么区别？**
  - A: yarn PnP 完全不生成 `node_modules`，用 `.pnp.cjs` 文件记录包位置，Node.js 通过 monkey-patch `require` 从 zip 压缩包直接读取模块（零解压）；pnpm 仍然有 `node_modules`（但用链接而非拷贝）。PnP 磁盘效率最高，但兼容性问题更多；pnpm 是兼容性和效率的平衡点。
- **Q: 为什么 pnpm 能比 npm 安装快？**
  - A: npm 安装 = 从 registry 下载 tarball + 解压 + 拷贝到项目 node_modules；pnpm 安装 = 检查全局 store 是否有该版本（有则直接硬链接，不用下载）。重复使用的包无需重新下载和解压，只需创建硬链接（微秒级操作）。
- **Q: pnpm workspace 和 npm workspace 有什么区别？**
  - A: 功能类似（多包管理），但 pnpm workspace 利用了 pnpm 的链接机制，workspace 内的包互相引用时也是硬链接，不会重复存储；pnpm 还有 `--filter` 参数可以精确地对指定包执行命令，配合 Turborepo 使用非常高效。

**⚠️ 常见误区**

- ❌ pnpm 用符号链接，node 解析路径会出问题 → Node.js 的模块解析会跟随 symlink，实际路径没有问题
- ❌ pnpm 安装的包只有一份，内存里也只加载一份 → 磁盘一份（硬链接），但运行时每个进程会独立加载，内存里可能有多份
- ❌ pnpm 和 npm 完全兼容，随时可以切换 → 切换后需要删除 node_modules 重新安装，lockfile 格式不同（pnpm-lock.yaml vs package-lock.json）
