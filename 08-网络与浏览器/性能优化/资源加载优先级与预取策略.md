# 资源加载优先级与预取策略

> 从浏览器默认优先级表出发，系统讲清 `fetchpriority`、`preload`、`modulepreload`、Speculation Rules 与 Early Hints 各自解决什么问题，最后收口成一张「我该用哪个」的决策框架

## 面试高频考点

- 浏览器给每类资源分配的默认优先级是什么？为什么 LCP 图片默认拿不到最高优先级？
- `preload` 和 `prefetch` 的区别是什么？（只答「当前页/下一页」是不够的）
- 字体 `preload` 为什么必须加 `crossorigin`？不加会发生什么？
- Speculation Rules API 的 `prefetch` 和 `prerender` 本质差别在哪？相比 `<link rel="prefetch">` 强在哪？
- 预渲染会真实执行页面 JS，怎么避免埋点 PV 虚高？

---

## 一、先看默认优先级：大多数情况浏览器是对的

所有「加载优化手段」本质上都是**在浏览器默认调度之上做干预**。所以顺序永远是：先打开 DevTools Network 面板的 Priority 列看默认值，确认它真的判断错了，再动手。

### 1.1 Chrome 的五档优先级

Chromium 内部把资源请求分为五档，DevTools Network 面板的 **Priority** 列直接显示：

| 档位 | DevTools 显示 | 典型含义 |
| --- | --- | --- |
| 第 1 档 | **Highest** | 阻塞渲染、缺了页面就是白屏的资源 |
| 第 2 档 | **High** | 首屏可见但不阻塞解析的资源 |
| 第 3 档 | **Medium** | 重要但可以稍晚的资源 |
| 第 4 档 | **Low** | 非关键资源，让出带宽 |
| 第 5 档 | **Lowest** | 纯投机性资源，只在完全空闲时占带宽 |

> 💡 优先级同时影响两件事：**请求发出的排队顺序**，以及 HTTP/2 多路复用下的**带宽分配权重**。它不是「谁先谁后」的硬开关，而是拥塞时的仲裁依据。

### 1.2 默认优先级全表

| 资源类型 | 默认优先级 | 说明 |
| --- | --- | --- |
| HTML 主文档 | **Highest** | 一切的起点，无法也不需要干预 |
| CSS（`<head>` 中阻塞渲染） | **Highest** | 阻塞首次渲染，天然最高 |
| CSS（`media` 查询不匹配当前环境） | **Lowest** | 浏览器判定为非阻塞，例如 `media="print"` |
| 字体（CSS `@font-face` 中引用） | **Highest** | 但**发现得极晚**——要等 CSS 下载并解析完 |
| 字体（通过 `preload` 声明） | **High** | 注意：比 CSS 里发现的字体低一档 |
| 同步 `<script>`（文档靠前，首张图片之前） | **High** | 阻塞解析器 |
| 同步 `<script>`（文档靠后，首张图片之后） | **Medium** | 已过首屏关键路径，降一档 |
| `<script defer>` / `<script async>` | **Low** | 不阻塞解析，让出带宽 |
| JS 动态插入的 `<script>` | **Low** | 同上 |
| `<img>`（视口外） | **Low** | 保持低位 |
| `<img>`（视口内） | **Low → High** | ⚠️ 见下方 1.3，是**布局之后**才提升的 |
| `fetch()` / 异步 XHR | **High** | 通常是数据请求，默认较高 |
| 同步 XHR | **Highest** | 已废弃用法，会卡主线程 |
| `<link rel="preload">` | 继承 `as` 对应类型 | 所以 `as` 必填，见第三章 |
| `<link rel="prefetch">` | **Lowest** | 服务的是「下一个页面」，绝不抢当前页带宽 |

> ⚠️ 具体档位会随 Chromium 版本调整，其他引擎的调度策略也不同。**记这张表的目的不是背数字，而是建立「哪些资源天生吃亏」的直觉**：字体和 CSS 背景图发现得晚，视口内图片提升得晚，`defer`/`async` 脚本永远是 Low。

### 1.3 关键机制：视口内图片的优先级提升发生在布局之后

这是理解 `fetchpriority` 存在意义的前提：

```
HTML 解析阶段                        布局（Layout）完成后
─────────────────────────────       ─────────────────────────────
浏览器看到 <img src="hero.webp">     浏览器才知道 hero 在视口内
        │                                    │
        ▼                                    ▼
  只知道「这是一张图」                  把它从 Low 提升到 High
  → 一律给 Low                              │
        │                                    │
        └──── 这段时间里带宽已经被 ─────────┘
              CSS / 脚本 / 其他图片抢完了
```

**HTML 解析时浏览器还没做布局，因此完全不知道哪个元素会是 LCP 元素**。它只能保守地把所有 `<img>` 放在 Low，等布局算出几何信息后再把视口内的提升上来。对于首屏大图，这个「等一等」往往就是 LCP 变差几百毫秒的直接原因——而这正是 `fetchpriority="high"` 要修的问题。

## 二、`fetchpriority`：调整已知资源的相对优先级

### 2.1 语义：它是提示（hint），不是命令

`fetchpriority` 取三个值：

| 取值 | 语义 | 实际效果 |
| --- | --- | --- |
| `high` | 「这个资源比同类型资源更重要」 | 在**同类型资源内部**上调一档 |
| `low` | 「这个资源比同类型资源不重要」 | 在同类型资源内部下调一档 |
| `auto`（默认） | 交给浏览器判断 | 走第一章的默认表 |

三个要点必须说清：

1. **它是相对的**：`fetchpriority="high"` 不会把一张图片提到 CSS 之上，只是在图片之间重新排序。
2. **它是 hint 不是 directive**：浏览器可以不采纳，最终调度由渲染引擎决定。
3. **它不改变资源发现时机**：`fetchpriority` 只能作用于浏览器**已经发现**的资源。如果资源是「发现得晚」的问题，要用 `preload`（第三章），不是 `fetchpriority`。

### 2.2 HTML 属性用法

```html
<!-- ✅ LCP 图片：抢在其他图片之前下载 -->
<img src="/hero.webp" fetchpriority="high" alt="首屏主图" />

<!-- ✅ preload 也能带优先级 -->
<link rel="preload" as="image" href="/hero.webp" fetchpriority="high" />

<!-- ✅ 非关键第三方脚本：让出带宽 -->
<script src="https://third-party.example.com/widget.js" async fetchpriority="low"></script>

<!-- ✅ 首屏外的 iframe（评论区、地图嵌入）降级 -->
<iframe src="/comments" loading="lazy" fetchpriority="low" title="评论"></iframe>
```

支持该属性的元素：`<img>`、`<link>`、`<script>`、`<iframe>`。

### 2.3 JS 侧：`fetchPriority` 与 `fetch()` 的 `priority`

注意大小写差异——**HTML 属性全小写 `fetchpriority`，JS 属性是驼峰 `fetchPriority`**：

```js
// DOM 属性（驼峰）
const img = new Image();
img.fetchPriority = "high"; // ✅ 驼峰
img.src = "/hero.webp";

// 也可以走 setAttribute（此时用小写属性名）
img.setAttribute("fetchpriority", "high");

// fetch() 用的是 priority 选项，不是 fetchPriority
// ✅ 关键数据请求提优先级
const user = await fetch("/api/me", { priority: "high" });

// ✅ 埋点、日志这类可以最后再走
fetch("/api/track", { priority: "low", keepalive: true, method: "POST", body });
```

在 React 里作为 JSX 属性写小写形式即可：

```jsx
// ✅ React 中 fetchPriority 会被正确映射为 fetchpriority 属性
<img src="/hero.webp" fetchPriority="high" alt="首屏主图" />
```

### 2.4 三个典型场景

| 场景 | 做法 | 收益来源 |
| --- | --- | --- |
| ① LCP 图片 | `fetchpriority="high"` + 不加 `loading="lazy"` | 跳过「等布局才提升」的等待，直接抢占带宽 |
| ② 首屏外轮播图 / 装饰图 | `fetchpriority="low"`（配合 `loading="lazy"`） | 避免轮播第 2~N 张和 LCP 图抢带宽 |
| ③ 非关键第三方脚本 | `fetchpriority="low"` + `async` | 客服组件、A/B 实验 SDK 不拖慢首屏 |

场景 ② 特别值得强调：轮播组件里第一张是 LCP、后面几张都在视口内（只是被 `overflow` 遮住），浏览器会把它们一起提升到 High，于是 LCP 图片被自己的兄弟抢了带宽。正确写法：

```html
<!-- ❌ 五张图并列，浏览器认为都在视口内，一起 High，互相抢带宽 -->
<div class="carousel">
  <img src="/slide-1.webp" alt="1" />
  <img src="/slide-2.webp" alt="2" />
  <img src="/slide-3.webp" alt="3" />
</div>

<!-- ✅ 只让首图 high，其余降到 low -->
<div class="carousel">
  <img src="/slide-1.webp" fetchpriority="high" alt="1" />
  <img src="/slide-2.webp" fetchpriority="low" loading="lazy" alt="2" />
  <img src="/slide-3.webp" fetchpriority="low" loading="lazy" alt="3" />
</div>
```

### 2.5 反例：滥用 `high` 等于没有 `high`

优先级是**相对排序**，不是配额。如果把首屏所有资源都标成 `high`：

```html
<!-- ❌ 全都 high，等于回到了没有优先级的状态 -->
<img src="/hero.webp" fetchpriority="high" alt="" />
<img src="/logo.svg" fetchpriority="high" alt="" />
<img src="/banner.webp" fetchpriority="high" alt="" />
<script src="/analytics.js" fetchpriority="high"></script>
```

排序退化成「都一样重要」，浏览器只能按发现顺序处理，你反而丢掉了原本默认表提供的、经过大量真实数据调优的判断。

**经验法则：一个页面里 `fetchpriority="high"` 的数量应该是个位数，理想情况是 1（LCP 图片）。`low` 可以多用，因为「主动让路」不存在互相抵消的问题。**

## 三、`preload`：解决「发现得晚」，不是解决「优先级低」

第一章那张表里有个反复出现的模式：**有些关键资源浏览器要经过好几步才能发现**。`preload` 唯一的正当用途就是把这类资源的发现时机提前。

### 3.1 真正需要 `preload` 的三类资源

| 资源 | 为什么发现得晚 | 正常发现链路 |
| --- | --- | --- |
| CSS `@font-face` 引用的字体 | 要等 CSS 下载 → 解析 → 匹配到用该字体的元素 | HTML → CSS → 字体（3 跳） |
| CSS `background-image` 里的 LCP 图 | 图片 URL 藏在样式表里，预加载扫描器（preload scanner）看不到 | HTML → CSS → 图片（3 跳） |
| 被 JS 动态加载的关键 chunk | 要等 JS 下载 → 执行 → 才发起 `import()` | HTML → JS → chunk（3 跳） |

**共同点：都不在 HTML 里直接写明，预加载扫描器扫不到。** 反过来说，如果资源已经写在 HTML 里（`<img src>`、`<script src>`、`<link rel="stylesheet">`），浏览器一定能第一时间发现它——这时候你需要的是 `fetchpriority`，不是 `preload`。

```html
<!-- ✅ 字体：CSS 里才引用，必须提前声明 -->
<link rel="preload" as="font" type="font/woff2" href="/fonts/Inter.woff2" crossorigin />

<!-- ✅ CSS background 里的首屏大图 -->
<link rel="preload" as="image" href="/hero-bg.webp" fetchpriority="high" />

<!-- ❌ 多余：这张图 HTML 里已经写了，preload 只是重复一遍 -->
<link rel="preload" as="image" href="/hero.webp" />
<img src="/hero.webp" alt="" />
<!-- ✅ 改成直接标优先级即可 -->
<img src="/hero.webp" fetchpriority="high" alt="" />
```

### 3.2 `as` 为什么必填

`as` 同时决定三件事，缺了浏览器无法正确处理：

1. **优先级**：`preload` 没有自己的优先级，它继承 `as` 对应类型的档位（`as="style"` → Highest，`as="font"` → High，`as="script"` → 按脚本规则）。
2. **请求头**：不同 `as` 会带不同的 `Accept`、`Sec-Fetch-Dest` 值，服务端/CDN 可能据此返回不同格式。
3. **能否复用**：缓存里的 preload 条目要和后续真实请求「匹配」才能命中，`as` 是匹配键之一。

`as` 缺失或写错，最常见的后果就是资源被下载了两次。

### 3.3 最经典的坑：字体 `preload` 必须加 `crossorigin`

```html
<!-- ❌ 缺 crossorigin：字体会被下载两次 -->
<link rel="preload" as="font" href="/fonts/Inter.woff2" />

<!-- ✅ 无论字体是否同源，都要加 -->
<link rel="preload" as="font" href="/fonts/Inter.woff2" crossorigin />
```

**原因链条**（面试要能完整说出来）：

```
字体请求的规范行为：CSS 加载字体一律使用匿名 CORS 模式
（这是 CSS Fonts 规范的硬性要求，即便字体和页面同源也如此）
        │
        ▼
不带 crossorigin 的 <link rel="preload"> 发出的是 no-cors 模式请求
        │
        ▼
浏览器做 preload 复用匹配时，会比较请求的「CORS 模式」
  preload 缓存里躺着一个 no-cors 的响应
  实际字体请求要找的是一个 cors 的响应
        │
        ▼
两者不匹配 → 判定为两个不同的请求 → 重新下载一遍
        │
        ▼
结果：字体下载了两次，而且第一次那份完全浪费掉，
     同时控制台还会给出「preload 了但没用上」的警告
```

> 💡 `crossorigin` 不写值等价于 `crossorigin="anonymous"`。跨域字体还需要服务端返回 `Access-Control-Allow-Origin`，否则字体请求本身就会失败。

### 3.4 「preload 了但没用上」警告的含义

控制台出现这类提示（大意为：某资源被 preload 但在 window load 后数秒内未被使用）时，只有三种可能：

| 根因 | 判断方式 | 解法 |
| --- | --- | --- |
| URL 不完全一致 | 对比 Network 面板里两条请求的完整 URL（含查询串、大小写） | 统一 URL，通常是构建产物 hash 不一致 |
| CORS 模式不匹配 | 检查 `crossorigin` 有无、值是否与实际请求一致 | 字体一律加 `crossorigin` |
| 这个资源真的没用上 | 代码里搜不到引用 | 删掉这条 `preload` |

前两种是「下载了两次」，第三种是「白下载一次」。**两种都是净亏损，不是「顶多没收益」**。

### 3.5 滥用 `preload` 会挤占关键资源带宽

`preload` 会把资源拉到它 `as` 类型对应的优先级上，也就是**真的会和关键资源抢带宽**。常见的失控模式是：为了「优化首屏」把十几个资源全 preload 一遍，结果 CSS 和 LCP 图片被一堆次要资源挤在后面，LCP 反而变差。

**判定标准：如果你无法用一句话说清「这个资源为什么浏览器发现得晚」，就不该 preload 它。**

## 四、Speculation Rules API：从「预取资源」升级到「预取页面」

前三章讨论的都是**当前页面内**的资源调度。Speculation Rules 处理的是另一个维度：**用户下一步要去的页面**。这是 2024 年之后加载优化最重要的新增能力。

### 4.1 声明式 JSON 语法

用一个 `<script type="speculationrules">`（**全小写，中间没有连字符**）内联 JSON 即可，无需任何 JS 逻辑：

```html
<script type="speculationrules">
  {
    "prerender": [
      {
        "where": { "href_matches": "/product/*" },
        "eagerness": "moderate"
      }
    ],
    "prefetch": [
      {
        "urls": ["/cart", "/checkout"],
        "eagerness": "eager"
      }
    ]
  }
</script>
```

两个顶层动作：`prefetch` 和 `prerender`。每条规则按目标写法分两类，这个区分后面讲 `eagerness` 默认值时很关键：

| 规则类型 | 写法 | 含义 |
| --- | --- | --- |
| **list 规则** | `"urls": ["/cart", "/checkout"]` | 显式列出要投机的 URL |
| **document 规则** | `"where": { ... }` | 按条件匹配当前文档里的链接 |

规则可以在运行时动态插入或移除 `<script>` 标签来增删。

### 4.2 特性检测与三种声明途径

```js
// ✅ 标准特性检测
if (HTMLScriptElement.supports("speculationrules")) {
  const script = document.createElement("script");
  script.type = "speculationrules";
  script.textContent = JSON.stringify({
    prerender: [{ where: { href_matches: "/product/*" }, eagerness: "moderate" }],
  });
  document.body.append(script);
} else {
  // 降级：退回老方案
  const link = document.createElement("link");
  link.rel = "prefetch";
  link.href = "/product/hot";
  document.head.append(link);
}
```

除了内联 `<script>`，还可以用响应头指向一个外部 JSON 文件：

```http
HTTP/1.1 200 OK
Speculation-Rules: "/rules/prefetch.json"
```

> ⚠️ 该 JSON 文件必须以 `application/speculationrules+json` 这个 MIME 类型提供，否则会被忽略。响应头方式的好处是规则可以由 CDN / 网关统一下发，不用改页面模板。

**CSP 场景**：如果站点开了严格的 `Content-Security-Policy`，内联规则会被 `script-src` 拦掉。放行方式有三种：

```
Content-Security-Policy: script-src 'self' 'inline-speculation-rules'
```

或者给内联脚本配 hash、或配 nonce。`'inline-speculation-rules'` 是专门为这个场景设计的关键字——它只放行 speculation rules 内联脚本，不会顺带放行普通内联 JS，比直接 `'unsafe-inline'` 安全得多。

### 4.3 `prefetch` vs `prerender`：本质区别

| 维度 | `prefetch` | `prerender` |
| --- | --- | --- |
| 做什么 | 只取回文档响应体 | 在后台**完整渲染**整个页面 |
| 执行目标页 JS | ❌ 不执行 | ✅ 执行 |
| 发起目标页的接口请求 | ❌ 不发起 | ✅ 发起（含 JS 主动发的数据请求） |
| 子资源（CSS/JS/图片） | ❌ **完全不取** | ✅ 全部下载并解析 |
| 同站导航 | ✅ 支持 | ✅ 同源默认支持；跨源同站需响应头（见 4.6） |
| 跨站导航 | ✅ 支持，但**仅当目标站未设置 cookie**（隐私考虑） | ❌ **不可能** |
| 省掉了什么 | 文档的网络往返 | 网络往返 + 解析 + 子资源 + 执行 + 渲染 |
| 点击后的体感 | 明显变快 | **近乎瞬时，接近 SPA 路由切换** |
| 资源成本 | 低（一个文档） | 高（一整套渲染管线 + 内存） |
| 副作用风险 | 中（服务端可能有副作用） | ⚠️ **高**：埋点、A/B 分流、接口调用都会真实发生 |
| 适用判断 | 「很可能被访问」 | 「几乎确定被访问」 |

一句话记忆：**`prefetch` 省的是网络，`prerender` 省的是网络加上之后的一切**。

```
用户点击后的时间线对比

无预测：  [DNS/TCP/TLS][文档][解析][子资源][JS执行][渲染] ──→ 可见
prefetch:              [解析][子资源][JS执行][渲染] ──→ 可见
                       ↑ 文档已在本地
prerender:  ──→ 可见（激活即显示，上述工作已在后台完成）
```

### 4.4 `where`：`href_matches` 与 `selector_matches`

两种匹配维度，可以用 `and` / `or` / `not` 自由组合：

```html
<script type="speculationrules">
  {
    "prefetch": [
      {
        "where": {
          "and": [
            { "href_matches": "/*" },
            { "not": { "href_matches": "/logout" } },
            { "not": { "href_matches": "/admin/*" } },
            { "not": { "selector_matches": ".no-speculate" } },
            { "not": { "selector_matches": "[data-destructive]" } }
          ]
        },
        "eagerness": "moderate"
      }
    ]
  }
</script>
```

| 写法 | 匹配依据 | 典型用途 |
| --- | --- | --- |
| `href_matches` | URL Pattern（支持 `*` 通配、`:name` 命名组） | 「所有文章详情页」这类批量规则 |
| `selector_matches` | CSS 选择器（匹配链接元素本身） | 由前端加 class / data 属性精细控制 |

**必须排除的链接类型**（这是安全底线，不是优化建议）：

| 类型 | 举例 | 为什么必须排除 |
| --- | --- | --- |
| 退出登录 | `/logout`、`/signout` | 预取可能直接注销用户会话 |
| 删除 / 归档 / 取消操作 | `/delete?id=1` | 即使是 GET 链接，也可能触发服务端状态变更 |
| 加入购物车 | `?add-to-cart=123` | 用户没点就进了购物车 |
| 发送验证码 / OTP | `/send-otp` | 短信白发，还可能触发风控 |
| 切换语言 / 切换主题 | `/set-lang?zh` | 服务端会真的改用户偏好 |
| 一次性令牌链接 | 邮件验证、重置密码 | 令牌被消费掉，用户真正点击时已失效 |
| 有配额计数的资源 | 抽奖、领券、API 调用次数 | 名额 / 额度被预取消耗 |
| 广告转化回传链接 | 联盟 / 归因跳转 | 转化数据虚高，可能造成结算纠纷 |
| 大流量下载链接 | 安装包、大文件 | 白白消耗用户流量 |

```html
<!-- ✅ 明确排除有副作用的 URL -->
<script type="speculationrules">
  {
    "prefetch": [
      {
        "where": {
          "and": [
            { "href_matches": "/*" },
            { "not": { "href_matches": "/logout" } },
            { "not": { "href_matches": "/*\\?*add-to-cart=*" } },
            { "not": { "selector_matches": "[data-destructive]" } }
          ]
        }
      }
    ]
  }
</script>
```

> 💡 **实用审计方法：直接看 `robots.txt` 的 `Disallow` 条目。** 站点早就把「不希望爬虫访问」的 URL 列在那里了，而这批 URL 和「不该被预取」的 URL 高度重合——因为两者的根因是同一个：这些 GET 请求有服务端副作用。

> ⚠️ 更深一层的根因是：**规范意义上 GET 应当是安全（safe）且幂等的，但真实项目里经常不是**。前端排除清单只是补救，服务端幂等性才是根治。此外服务端也可以主动防御：对投机请求返回非 2xx 状态码即可阻止预取（例如 `503`）；`204` / `205` 会阻止 prerender 但**不会**阻止 prefetch。

### 4.5 `eagerness`：四档触发时机

`eagerness` 控制「什么时候真的开始投机」，这是成本与收益的调节旋钮：

| `eagerness` | 触发时机 | 成本 | 适用场景 |
| --- | --- | --- | --- |
| `immediate` | 尽快开始，只受用户偏好（省电/省流量）与资源限制约束 | 最高 | 少量、几乎确定要去的 URL，配 `urls` 列表使用 |
| `eager` | 任何**轻微暗示**即触发：鼠标朝链接方向移动、hover 或 focus 片刻、滚动停在链接显眼位置 | 高 | 目标少且明确的场景 |
| `moderate` | **合理暗示**时触发：链接滚入视口且被 hover / focus **一段时间** | 中 | ✅ 桌面端 document 规则的常用选择 |
| `conservative` | 用户**开始点击**时触发（`mousedown` / `pointerdown`） | 最低 | ✅ 移动端、或规则命中链接非常多时 |

> ⚠️ 规范**没有为 `eager` / `moderate` 定义具体的毫秒阈值**，「一段时间」由实现自行决定并可能随版本变化。任何写死「hover 200ms 触发」的说法都不要当成规范行为。

**默认值分两种规则**，这点很容易踩：

| 规则类型 | `eagerness` 默认值 | 备注 |
| --- | --- | --- |
| list 规则（用 `urls`） | `immediate` | 当前实现下 `eager` 与 `immediate` 效果相同，所以 `eagerness` 对 list 规则意义有限 |
| document 规则（用 `where`） | `conservative` | 默认最保守，想要更激进必须显式写 |

也就是说：**`eagerness` 主要是给 document 规则用的旋钮**。用 `where` 做批量匹配时，不要轻易用 `immediate` / `eager`——那等于把页面上所有匹配到的链接一次性全部投机掉。

```json
{
  "prefetch": [
    { "urls": ["/checkout"] },
    { "where": { "href_matches": "/product/*" }, "eagerness": "moderate" }
  ]
}
```

上面第一条不写 `eagerness`，默认 `immediate`（立刻预取结算页）；第二条显式写 `moderate`（不写就是 `conservative`，只在按下时才动）。

### 4.6 ⚠️ 埋点虚高：预渲染必须处理的第一个坑

**`prerender` 会真实执行目标页的全部 JS，包括埋点 SDK 的初始化和 PV 上报。** 如果不处理，用户仅仅把鼠标悬停在链接上、根本没有访问，你的埋点系统里就已经多了一个 PV。这会直接污染 PV/UV、转化漏斗、页面停留时长和 A/B 实验分流结果。

浏览器提供了多种检测手段，各自覆盖不同情形：

| 检测手段 | 回答的问题 | 用在哪 |
| --- | --- | --- |
| `document.prerendering` | 「我**现在**正在被预渲染吗」 | 决定是否推迟执行 |
| `prerenderingchange` 事件 | 「我**什么时候**被激活」 | 推迟逻辑的执行时机 |
| `PerformanceNavigationTiming.activationStart > 0` | 「我**曾经**被预渲染过吗」 | 激活后补充判断、指标时间校正 |
| `PerformanceResourceTiming.deliveryType === "navigational-prefetch"` | 「这个文档是**从 prefetch 缓存**来的吗」 | 区分 prefetch 命中 |
| 服务端 `Sec-Purpose` 请求头 | 「这是投机流量吗」 | 服务端日志与业务统计过滤 |

**推荐的埋点写法**（`document.prerendering` + `prerenderingchange` 组合，覆盖两种情形）：

```js
// ✅ 标准写法
if (document.prerendering) {
  // 预渲染中：等激活再初始化
  document.addEventListener("prerenderingchange", initAnalytics, { once: true });
} else {
  // 普通导航，或已经激活完成
  initAnalytics();
}
```

封装成通用工具，所有「只能在真实访问时执行」的逻辑都走它：

```js
// ✅ 通用封装
function onActivated(callback) {
  if (document.prerendering) {
    document.addEventListener("prerenderingchange", () => callback(), {
      once: true,
    });
  } else {
    callback();
  }
}

// 埋点上报
onActivated(() => tracker.sendPageView({ page: location.pathname }));

// A/B 实验曝光上报同理——不然实验样本会被预渲染污染
onActivated(() => tracker.sendExposure({ experiment: "checkout_v2", group }));
```

判断「曾被预渲染」以及检测 prefetch 命中：

```js
const nav = performance.getEntriesByType("navigation")[0];

// ✅ activationStart > 0 说明这次导航是从预渲染激活来的
if (nav && nav.activationStart > 0) {
  console.log("本次导航来自预渲染，指标需减去", nav.activationStart);
}

// ✅ 检测文档是否命中了 prefetch 缓存
if (nav && nav.deliveryType === "navigational-prefetch") {
  console.log("文档来自 prefetch 缓存");
}
```

```js
// ❌ 直接在模块顶层上报：预渲染时就发出去了，PV 虚高
tracker.sendPageView({ page: location.pathname });

// ❌ 用 DOMContentLoaded 也没用：预渲染时这个事件同样会触发
document.addEventListener("DOMContentLoaded", () => {
  tracker.sendPageView({ page: location.pathname });
});
```

**哪些逻辑必须推迟到激活之后**：

| 类型 | 是否推迟 | 原因 |
| --- | --- | --- |
| PV / UV 上报 | ✅ 必须 | 直接导致数据虚高 |
| A/B 实验曝光上报 | ✅ 必须 | 污染实验样本与分流统计 |
| 页面停留时长计时起点 | ✅ 必须 | 否则计时从预渲染开始，时长虚高 |
| 视频 / 音频自动播放 | ✅ 必须 | 后台播放是明确的体验事故 |
| 弹窗、Toast、引导层 | ✅ 必须 | 激活时状态已错乱 |
| 性能指标采集 | ⚠️ 需校正 | 用 `activationStart` 做时间基准校正，见第 4.7 与关联笔记 |
| 静态数据预取、组件预渲染 | ❌ 不用推迟 | 这正是 prerender 想帮你做的事 |

> 💡 服务端同样需要配合：投机请求会带上 `Sec-Purpose` 请求头——prefetch 是 `Sec-Purpose: prefetch`，prerender 是 `Sec-Purpose: prefetch;prerender`。服务端日志与业务统计应据此把投机流量单独标记，不要算进真实访问量；有副作用的接口也可以据此直接跳过副作用逻辑。

### 4.7 prerender 期间被限制的 API：它不是万能的

预渲染页面在后台运行、用户看不见也没有交互，因此浏览器会**延迟或禁止**一批可能造成困扰的能力。这是「prerender 不能无脑上」的重要边界：

| 处理方式 | 涉及能力 | 后果 |
| --- | --- | --- |
| **延迟到激活后** | Geolocation（地理位置）、Notifications（通知）、Push、Web Audio、Service Worker 的 `register()` / `postMessage()` | 相关 Promise 会挂起，激活后才继续；依赖这些能力的初始化逻辑会「卡住」而不是报错 |
| **直接限制** | `window.open()`、`window.print()`、`alert()` / `confirm()` / `prompt()`、文件下载、跨源 `<iframe>` 加载 | 调用会被阻止；某些情况下会导致**整个预渲染被丢弃**，白做一遍 |

实践含义有两点：

1. **不要在页面初始化路径上依赖这些能力**。比如「进页面就请求定位权限」的写法，在预渲染时会静默挂起，激活后才弹权限框，时序和你预期的不一样——正确做法是把它放进 `onActivated()`。
2. **含 `alert` 类调试代码的页面可能压根预渲染不了**。上线前用 DevTools 的 Application → Speculative loads 面板确认预渲染是否真的成功，而不是想当然。

### 4.8 其他限制与注意事项

| 限制 | 说明 |
| --- | --- |
| prefetch 的跨站条件 | 跨站 prefetch **可以**做，但仅在目标站点未设置 cookie 时生效（隐私考虑，避免通过预取做跨站追踪） |
| prerender 的作用域 | 默认仅同源；**跨源同站**需要目标响应 `Supports-Loading-Mode: credentialed-prerender`；**跨站 prerender 不可能** |
| 并发与配额 | 浏览器对同时进行的投机数量有上限，超出会丢弃较早的规则；低内存设备上可能整体不启用 |
| 内存成本 | 一个 prerender 相当于后台跑一个完整页面，滥用会挤占内存并触发浏览器主动放弃 |
| 缓存有效期有限 | Chrome 中投机缓存约 5 分钟即失效，因此用户看到的内容可能**略微陈旧**；需要主动失效时服务端可返回 `Clear-Site-Data: "prefetchCache"` 或 `"prerenderCache"` |
| 只适用于导航 | 投机对象是页面导航，不是任意资源；且限于 GET 导航 |
| 服务端可拒绝 | 对 `Sec-Purpose` 请求返回非 2xx（如 `503`）即可阻止预取；`204` / `205` 阻止 prerender 但不阻止 prefetch |
| 引擎支持 | 目前属于 **Limited availability / Experimental**，**不是 Baseline**，主要在 Chromium 系可用；生产使用前必须查兼容表 |
| 天然降级 | 不支持的浏览器会直接忽略 `<script type="speculationrules">`，页面功能完全不受影响，所以可以放心当渐进增强来做 |

### 4.9 与老方案 `<link rel="prefetch">` 的对比

| 维度 | `<link rel="prefetch">` | Speculation Rules |
| --- | --- | --- |
| 声明方式 | 每个 URL 一个标签 | 一段 JSON，支持 URL Pattern 批量匹配 |
| 能否按 CSS 选择器筛选 | ❌ | ✅ `selector_matches` |
| 能否排除特定链接 | ❌ 只能不写 | ✅ `not` / `and` 组合 |
| 触发时机可控 | ❌ 由浏览器决定（Lowest 优先级空闲时） | ✅ `eagerness` 四档（对 document 规则有效） |
| 真正的预渲染 | ❌ 只能取资源 | ✅ `prerender` |
| 是否受 `Cache-Control` 阻断 | ⚠️ 会被 `no-store` / `no-cache` 之类阻断 | ✅ **不被 `Cache-Control` 阻断**，使用独立的投机缓存 |
| 优先级管理 | 需自己权衡，容易抢带宽 | ✅ 自动降低优先级，浏览器统一管理并发与内存配额 |
| 尊重用户偏好 | ❌ 不感知 | ✅ 尊重省电模式 / 省流量模式，低内存设备自动退化 |
| 动态链接（JS 渲染出来的） | 需手动插入标签 | 规则自动匹配新出现的链接 |
| 声明途径 | 只能是 HTML 标签 | 内联 `<script>` 或 `Speculation-Rules` 响应头 |
| 引擎支持面 | 广 | 目前以 Chromium 系为主，非 Baseline |

实践上两者可以并存：用 `HTMLScriptElement.supports("speculationrules")` 检测，支持时用 Speculation Rules，不支持时退回到 `<link rel="prefetch">` 或「hover 时 `import()` 路由 chunk」策略。

### 4.10 易混点澄清：Speculation Rules 的 prerender ≠ React 的 PPR

这两个东西名字里都有 "prerender"，但**没有任何关系**：

| | 浏览器 Speculation Rules `prerender` | React / Next.js 的 Partial Prerendering（PPR） |
| --- | --- | --- |
| 发生在哪 | **用户浏览器**里，后台标签页 | **服务端**（构建期 + 请求期） |
| 解决什么问题 | 下一次**页面导航**的耗时 | 单个页面**首字节到完整内容**的耗时 |
| 机制 | 提前把下一个页面完整渲染好，点击时直接激活 | 先产出静态外壳（prelude），动态部分标记为 postponed，请求时再 resume 恢复流式输出 |
| 触发者 | 浏览器根据 `eagerness` 与用户行为 | 服务端渲染流水线 |
| 相关 API | `document.prerendering`、`prerenderingchange`、`activationStart` | `prerender()` / `resume()` / `prerenderToNodeStream()` 等 |

面试里被问到「预渲染」时，先确认对方问的是哪一个。两者甚至可以叠加使用：一个用了 PPR 的页面，同时可以被浏览器 Speculation Rules 预渲染。

## 五、`modulepreload`：拆掉 ESM 的依赖图瀑布

### 5.1 问题：ESM 依赖要一层层「发现」

原生 ESM 的依赖关系写在模块源码的 `import` 语句里，浏览器必须先拿到并解析一个模块，才知道它依赖谁：

```
入口 main.js
   │ 下载 + 解析
   ▼
发现 import "./router.js"
   │ 下载 + 解析          ← 第 2 个网络往返
   ▼
发现 import "./pages/Home.js"
   │ 下载 + 解析          ← 第 3 个网络往返
   ▼
发现 import "./components/Chart.js"
   │ 下载 + 解析          ← 第 4 个网络往返
   ▼
可以开始执行

依赖链有多深，串行往返就有多少次
```

依赖链深度直接乘上 RTT，在弱网下极其致命。

### 5.2 `modulepreload` 让整张依赖图并行拉取

```html
<!-- ✅ 把依赖图摊平，一次性并行下载 -->
<link rel="modulepreload" href="/assets/main.js" />
<link rel="modulepreload" href="/assets/router.js" />
<link rel="modulepreload" href="/assets/vendor.js" />

<script type="module" src="/assets/main.js"></script>
```

### 5.3 与 `preload as="script"` 的区别

| 维度 | `<link rel="preload" as="script">` | `<link rel="modulepreload">` |
| --- | --- | --- |
| 目标 | 任意脚本（含传统脚本） | 明确是 ES 模块 |
| 请求模式 | 按普通脚本处理 | 按模块规则处理（含正确的 CORS / credentials 语义） |
| 是否解析依赖 | ❌ 只下载字节 | ✅ 可以解析模块并**递归发现并预取其依赖** |
| 是否预处理 | ❌ 仅进 HTTP 缓存 | ✅ 可以提前编译并存入模块图（module map） |
| 后续执行 | 还要重新走一遍模块解析 | 直接复用已就绪的模块 |

**核心差异：`preload` 只是「提前把字节搬过来」，`modulepreload` 是「提前把模块准备好」——包括依赖发现和编译。** 对深依赖图，只有后者能真正消掉瀑布。

### 5.4 Vite 生产构建会自动注入

Vite 生产构建会分析入口的静态依赖图，并在产物 HTML 里自动注入对应的 `<link rel="modulepreload">`：

```html
<!-- Vite build 产出的 index.html（示意） -->
<script type="module" crossorigin src="/assets/index-a1b2c3.js"></script>
<link rel="modulepreload" crossorigin href="/assets/vendor-d4e5f6.js" />
<link rel="modulepreload" crossorigin href="/assets/router-g7h8i9.js" />
```

同时，Vite 对**动态导入**的 chunk 也会在运行时按需注入 `modulepreload`，把 `import()` 触发的二级依赖一起并行拉取。所以用 Vite 的项目通常不需要手写 `modulepreload`；**需要手写的场景是：SSR 框架自定义模板、微前端子应用手动挂载、或者你自己拼装 HTML**。

> ⚠️ 别把 `modulepreload` 当成「越多越好」。它是 `as="script"` 量级的优先级，全量预加载所有懒加载 chunk 会直接抵消掉 code splitting 的收益。只预加载**首屏路径上**的模块。

## 六、Early Hints（103）与 `Link` 响应头

### 6.1 解决的问题：TTFB 期间浏览器完全空闲

SSR 页面的典型时间线里，浏览器在等后端处理时无事可做：

```
传统流程
────────────────────────────────────────────────
浏览器 ──请求──▶ 服务端
                 │ 查数据库、渲染模板（比如 400ms）
   ⏳ 完全空闲    │
                 ▼
        ◀──200 + HTML──
  开始解析 HTML，才发现要加载 CSS / JS
        │
        ▼ 现在才开始下载关键资源


Early Hints 流程
────────────────────────────────────────────────
浏览器 ──请求──▶ 服务端
        ◀──103 Early Hints──   （立刻返回，带 Link 头）
   ✅ 开始下载 CSS / JS ！      │ 后端继续渲染（400ms）
        │                       ▼
        │              ◀──200 + HTML──
        ▼ 关键资源已经在本地或下载中
```

### 6.2 用法

服务端在正式响应之前先发一个 `103` 信息性响应，带上 `Link` 头：

```http
HTTP/1.1 103 Early Hints
Link: </assets/critical.css>; rel=preload; as=style
Link: </assets/main.js>; rel=modulepreload
Link: <https://api.example.com>; rel=preconnect

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
...
```

`Link` 响应头和 HTML 里的 `<link>` 标签是等价的两种表达，在 `200` 响应里也可以用（此时收益是「比 HTML 解析更早」，但不如 103 早）：

```
Link: </assets/critical.css>; rel=preload; as=style; fetchpriority=high
```

### 6.3 适用场景与前提

| 项 | 说明 |
| --- | --- |
| ✅ 最适合 | TTFB 明显偏长的 SSR / 动态页面（后端有查询、鉴权、模板渲染） |
| ❌ 收益很小 | 静态站点、CDN 边缘直出的页面（TTFB 本来就几十毫秒，没有空档可利用） |
| 前提 1 | **CDN / 网关 / 服务器必须支持转发 103**，这是最大的落地门槛 |
| 前提 2 | 必须能在渲染完成前就确定关键资源 URL（构建时产出资源清单，SSR 时读取） |
| 前提 3 | `rel` 一般限于 `preload` / `preconnect` / `modulepreload` 这类，不是所有 `rel` 都被支持 |
| 关联 | 它是已被移除的 HTTP/2 Server Push 的现代替代方案——不推送内容，只提示 URL，由浏览器自己决定要不要下载（因此不会像 Push 那样浪费已缓存资源的带宽） |

### 7.2 对照表

| 我的问题 | 该用什么 | 一句话理由 | 不要用什么 |
| --- | --- | --- | --- |
| 字体加载太晚，文字闪动 | `preload as="font" crossorigin` | 字体要 3 跳才被发现 | 光调 `fetchpriority` 没用，浏览器还没发现它 |
| CSS background 里的 LCP 图慢 | `preload as="image" fetchpriority="high"` | 同样发现得晚 | — |
| `<img>` 写在 HTML 里但 LCP 还是慢 | `fetchpriority="high"` | 已被发现，只是排队靠后 | `preload` 是多余的重复声明 |
| 轮播后几张抢了首图带宽 | 后几张 `fetchpriority="low"` | 视口内图片会被一起提升 | 给首图加更多 `high` 没有意义 |
| 第三方 SDK 拖慢首屏 | `async` + `fetchpriority="low"` | 主动让路 | 别 `preload` 它 |
| ESM 依赖链深、弱网首屏慢 | `modulepreload`（仅首屏路径） | 摊平依赖图瀑布 | `preload as="script"` 不解析依赖 |
| 列表页 → 详情页想秒开 | Speculation Rules `prerender` + `moderate` | hover 意图信号强，命中率高 | `prefetch` 只省网络往返，达不到瞬时 |
| 站内导航整体想变快 | Speculation Rules `prefetch`（document 规则默认 `conservative`） | 成本低、覆盖广 | 批量规则改成 `immediate` 会失控 |
| 跨域 API 域名握手慢 | `preconnect`（数量控制在 2~4 个） | 提前完成 DNS+TCP+TLS | 预连一堆用不到的域名反而浪费 |
| SSR 页面 TTFB 400ms+ | Early Hints 103 + `Link` | 利用后端处理的空档 | 静态页做这个几乎没收益 |
| 预渲染后埋点数据虚高 | `document.prerendering` + `prerenderingchange` | 上报必须推迟到激活后 | 用 `DOMContentLoaded` 判断无效 |

## 八、常见踩坑表

| 现象 | 根因 | 解法 |
| --- | --- | --- |
| 字体被下载两次 | `preload` 没加 `crossorigin`，CORS 模式与实际字体请求不匹配 | `<link rel="preload" as="font" crossorigin>` |
| 控制台警告「preload 了但未使用」 | URL 不一致 / CORS 模式不匹配 / 确实没用上 | 逐项核对 Network 面板里的两条请求 |
| 加了 `preload` 后 LCP 反而变差 | preload 的资源抢走了 CSS 与 LCP 图的带宽 | 只 preload「发现得晚」的资源，其余删掉 |
| 首屏全标 `high`，性能没变化 | 优先级是相对排序，全 high 等于都不 high | 只给 LCP 资源 `high`，其余用 `low` 让路 |
| LCP 图片加了 `high` 仍然慢 | 同时写了 `loading="lazy"`，两者语义冲突 | LCP 图片绝不能 lazy |
| `fetchpriority` 没生效 | HTML 里写成了驼峰 `fetchPriority` | HTML 属性小写，JS 属性驼峰 |
| `fetch()` 里写 `fetchPriority` 无效 | `fetch()` 的选项名是 `priority` | `fetch(url, { priority: "high" })` |
| 预渲染后 PV / UV 暴涨 | prerender 真实执行了埋点代码 | `document.prerendering` + `prerenderingchange` 推迟上报 |
| 页面停留时长指标全部虚高 | 计时起点落在预渲染开始时刻 | 用 `activationStart` 校正基准，或激活后再开始计时 |
| 用户莫名被登出 | 预取规则命中了 `/logout` | `where` 里用 `not` 明确排除；审计 `robots.txt` 的 `Disallow` 找出同类 URL |
| 购物车莫名多了商品 | 预取命中了 `?add-to-cart=` 这类带副作用的 GET | 排除该 URL 模式 + 服务端识别 `Sec-Purpose` 跳过副作用 |
| 一次性令牌链接失效 | 预取消耗了令牌 | 排除令牌链接 + 服务端识别 `Sec-Purpose` 跳过消费 |
| A/B 实验分流数据异常 | 预渲染触发了实验曝光上报 | 曝光上报同样推迟到激活后 |
| 预渲染页面「卡在初始化」 | 页面启动时调用了 Geolocation / Notifications 等被延迟的 API | 把这些调用放进 `onActivated()` |
| 预渲染似乎从来没成功过 | 页面里有 `alert` / `window.open` / 下载等被限制的调用 | DevTools → Application → Speculative loads 看丢弃原因 |
| 用户看到的是旧内容 | 投机缓存有有效期（Chrome 约 5 分钟），期间内容已变 | 需要主动失效时返回 `Clear-Site-Data: "prefetchCache"` / `"prerenderCache"` |
| `speculationrules` 规则完全不生效 | 类型名写错（写成 `speculation-rules`）／JSON 语法错误／CSP 拦了内联脚本 | 类型名全小写无连字符；CSP 加 `'inline-speculation-rules'`；用 DevTools Speculative loads 排查 |
| 外部规则 JSON 不生效 | 文件 MIME 类型不是 `application/speculationrules+json` | 修正服务端 Content-Type |
| 跨站 prerender 配了没反应 | 跨站 prerender 根本不可能 | 跨站只能用 prefetch，且目标站未设 cookie 才生效 |
| 跨源同站 prerender 不生效 | 缺少 `Supports-Loading-Mode: credentialed-prerender` 响应头 | 目标站加上该响应头 |
| 预加载了一堆懒加载 chunk，包体收益消失 | `modulepreload` 覆盖范围过大 | 只预加载首屏路径上的模块 |
| Early Hints 配了但没效果 | CDN / 网关未转发 103 响应 | 先确认链路支持，再谈配置 |

## 九、落地清单

**Must（不做就是明确的性能损失）**

- [ ] LCP 图片加 `fetchpriority="high"` 且不加 `loading="lazy"` —— 不做则 LCP 白等一次布局，通常损失几百毫秒
- [ ] 所有字体 `preload` 都带 `crossorigin` —— 不做则字体下载两次，浪费带宽并延后文字渲染
- [ ] `preload` 一律显式写 `as` —— 不做则优先级错乱、缓存复用失败
- [ ] 清理控制台所有「preload 未使用」警告 —— 不做则每条警告背后都是一次纯浪费的下载
- [ ] 启用 prerender 前先接入 `document.prerendering` / `prerenderingchange` —— 不做则 PV、转化率、实验数据全部失真
- [ ] Speculation Rules 的 `where` 里排除登出 / 删除 / 加购 / OTP / 令牌类链接（拿 `robots.txt` 的 `Disallow` 对照审计）—— 不做则可能造成真实的业务事故
- [ ] 视口内的轮播图 / 图集，除首图外一律 `fetchpriority="low"` —— 不做则 LCP 图片被兄弟节点抢带宽

**Should（收益明显，成本可控）**

- [ ] 列表页 → 详情页配 `prerender` + `eagerness: "moderate"` —— 不做则放弃了近乎瞬时导航的体感提升
- [ ] 其余站内导航配 `prefetch` document 规则（默认 `conservative`）—— 不做则每次跳转都白等一次文档往返
- [ ] 用 `HTMLScriptElement.supports("speculationrules")` 做特性检测并保留降级 —— 不做则不支持的引擎完全拿不到收益
- [ ] 页面初始化路径上不依赖 prerender 期间被延迟的 API（Geolocation / Notifications / Push / Web Audio / SW register）—— 不做则预渲染时初始化静默挂起，时序错乱
- [ ] 第三方非关键脚本统一 `async` + `fetchpriority="low"` —— 不做则第三方抖动直接传导到首屏
- [ ] SSR 自定义模板检查 `modulepreload` 是否覆盖首屏模块 —— 不做则弱网下依赖瀑布明显
- [ ] 服务端日志按 `Sec-Purpose` 区分投机流量（`prefetch` / `prefetch;prerender`）—— 不做则服务端统计与容量评估被预取流量污染
- [ ] 有严格 CSP 的站点提前配好 `'inline-speculation-rules'` 或 nonce —— 不做则规则被 CSP 静默拦掉，排查很费时间
- [ ] `preconnect` 域名数量控制在 2~4 个，且只保留首屏确定要用的 —— 不做则连接资源被无用域名占用

**Could（视场景取舍）**

- [ ] 上线后用 DevTools → Application → Speculative loads 核对投机命中率与丢弃原因 —— 不做则不知道优化到底生效没有
- [ ] 规则改用 `Speculation-Rules` 响应头下发（MIME 须为 `application/speculationrules+json`）—— 不做则规则要跟着页面模板一起发版
- [ ] 关键页面内容更新后返回 `Clear-Site-Data: "prefetchCache"` / `"prerenderCache"` —— 不做则用户可能看到最多几分钟前的旧内容
- [ ] 有副作用的 GET 接口对投机请求返回 `503` 主动拒绝 —— 不做则完全依赖前端排除清单，一处漏写就出事
- [ ] TTFB 偏长的 SSR 页面接 Early Hints —— 不做则 TTFB 期间的空档被浪费，但需 CDN 支持
- [ ] `fetch()` 数据请求按重要性区分 `priority` —— 不做则关键数据与埋点请求平等竞争
- [ ] 首屏外 `<iframe>` 加 `loading="lazy"` + `fetchpriority="low"` —— 不做则嵌入内容和首屏抢资源
- [ ] 用 `deliveryType === "navigational-prefetch"` 与 `activationStart > 0` 在 RUM 里区分投机命中导航 —— 不做则无法量化投机策略的真实收益

## 面试高频问答 🎯

### Q1：`preload` 和 `prefetch` 有什么区别？

表层区别是「preload 用于当前页面、prefetch 用于下一个页面」，但更本质的差别有三层。第一层是**目的**：preload 解决的是「关键资源被浏览器发现得太晚」，比如字体要等 CSS 解析完才被发现、CSS background 里的图预加载扫描器根本看不到；prefetch 解决的是「未来页面的缓存预热」。第二层是**优先级**：preload 会继承 `as` 指定类型的优先级，是真的会和当前页关键资源抢带宽的，所以滥用会让 LCP 变差；prefetch 是 Lowest，只在空闲时占带宽，几乎不会伤害当前页。第三层是**约束**：preload 的 `as` 必填，字体还必须加 `crossorigin`，否则会重复下载；prefetch 没有这些要求。所以判断标准是：如果资源已经明确写在 HTML 里，你需要的是 `fetchpriority` 而不是 preload——preload 修的是发现时机，不是排队顺序。

### Q2：为什么 LCP 图片默认拿不到高优先级？加了 `fetchpriority="high"` 之后浏览器做了什么？

因为浏览器在 HTML 解析阶段还没有做布局，它只知道「这里有一张图」，完全不知道这张图会不会出现在视口里、更不知道哪个元素会成为 LCP 元素。所以保守起来，所有 `<img>` 一律先给 Low 优先级；等布局算完，浏览器才知道哪些图在视口内，把它们从 Low 提升到 High。问题就在这个「等一等」——在等布局的这段时间里，带宽已经被 CSS、脚本和其他图片抢完了，LCP 图片实际开始下载的时间被推后。加上 `fetchpriority="high"` 相当于你把自己的先验知识告诉浏览器：「这张图我确定是最重要的」，于是它从一开始就按 High 处理，跳过等布局的过程。需要注意这是一个 hint 而不是命令，浏览器可以不采纳；而且它是相对排序，把首屏所有资源都标成 high 就等于回到了没有优先级的状态，理想情况是整页只有一个 `high`。

### Q3：Speculation Rules API 相比 `<link rel="prefetch">` 有什么优势？

四个方面。一是**表达能力**：老方案一个 URL 一个标签，Speculation Rules 是一段 JSON，用 `href_matches` 可以按 URL Pattern 批量匹配（比如所有 `/product/*`），用 `selector_matches` 可以按 CSS 选择器筛选，还能用 `and` / `not` 组合排除登出、删除这类危险链接，也天然覆盖 JS 后续动态渲染出来的链接。二是**触发时机可控**：`eagerness` 有四档，`immediate` 立刻触发，`moderate` 是链接滚入视口且悬停一段时间后触发，`conservative` 是 pointerdown 触发，你可以按命中率和成本自己调；老方案只能交给浏览器在空闲时决定。三是**多了真正的预渲染**：`prerender` 会在后台完整渲染目标页面，执行 JS、发起接口请求，点击时近乎瞬时，体感接近 SPA 路由切换，这是 `<link rel="prefetch">` 做不到的——它只能取回文档字节。四是**配额统一管理**：浏览器统一管理并发数和内存配额，低内存设备会自动退化，不像手写一堆 prefetch 标签那样容易失控。代价是目前以 Chromium 系为主，其他引擎会直接忽略这段脚本，所以它天然是渐进增强的，可以保留老方案兜底。

### Q4：预渲染怎么避免埋点虚高？

关键认知是 `prerender` 会**真实执行**目标页的全部 JS，所以埋点 SDK 的初始化和 PV 上报会在用户根本没访问的时候就发出去了。只要用户在链接上悬停一下，你的埋点系统里就多了一个 PV，PV/UV、转化漏斗、停留时长、A/B 实验分流全都会被污染。解法是浏览器提供的两个 API：`document.prerendering` 是布尔值，告诉你当前是否处于预渲染状态；`prerenderingchange` 是 `document` 上的事件，页面被真正激活时触发一次。标准写法是封装一个 `onActivated(callback)`：如果 `document.prerendering` 为真就监听 `prerenderingchange`（加 `once: true`），否则直接执行。所有 PV 上报、实验曝光上报、停留时长计时起点、自动播放和弹窗都走这个通道。注意用 `DOMContentLoaded` 判断是无效的，预渲染时这个事件同样会触发。此外服务端也要配合：投机请求会带 `Sec-Purpose` 头，服务端日志和业务统计应据此把预取流量单独标记；性能指标采集则要用 `PerformanceNavigationTiming.activationStart` 做时间基准校正，否则指标会虚低到失真。

### Q5：`modulepreload` 和 `preload as="script"` 有什么区别？什么时候需要手写它？

区别在于「搬字节」和「准备模块」。`preload as="script"` 只是提前把文件下载到 HTTP 缓存里，浏览器并不会去看这个文件的内容；等真正 `import` 的时候，还要重新走一遍模块解析，然后才发现它 `import` 了别的模块，再发起下一轮请求。`modulepreload` 则是按模块规则处理：它会用正确的 CORS 和 credentials 语义发请求，可以解析模块内容、**递归发现并预取依赖**，还能提前编译好放进模块图。原生 ESM 最大的性能问题就是依赖图瀑布——依赖链每深一层就多一次串行网络往返，弱网下依赖链深度直接乘上 RTT。只有 `modulepreload` 能把这张图摊平成并行下载。实际项目里大多不需要手写：Vite 生产构建会分析静态依赖图自动注入 `modulepreload`，动态 `import()` 的 chunk 也会在运行时按需注入。需要手写的场景是 SSR 框架自定义 HTML 模板、微前端子应用手动挂载、或者自己拼装 HTML。注意别贪多——它是脚本量级的优先级，把所有懒加载 chunk 都预加载会直接抵消 code splitting 的收益，只覆盖首屏路径上的模块就够了。
