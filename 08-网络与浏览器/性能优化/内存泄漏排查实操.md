# 内存泄漏排查实操

> 从「感觉内存在涨」到「定位到那一行代码」：Chrome DevTools 取证式排查全流程，重点补齐游离 DOM（Detached DOM）与保留路径（Retainers）两个最常被跳过的环节

## 面试高频考点

- 内存一直在涨，怎么判断到底是不是泄漏？误报率最高的地方在哪？
- Shallow Size 和 Retained Size 有什么区别？为什么一个几十字节的小对象能有几十 MB 的 Retained Size？
- 什么是游离 DOM（Detached DOM）？在堆快照（Heap Snapshot）里怎么把它揪出来？
- 三快照法（3-snapshot technique）为什么要打三个快照，两个不行吗？
- 从「发现某个构造函数的实例在涨」到「定位到具体代码」，中间靠什么？

---

## 一、前置：哪些对象会被回收

只需要记住一句话：**GC 回收的判据是「不可达」，不是「不再使用」**。从 GC roots（全局对象、执行栈上的变量、DOM 树、活跃的定时器与监听器等）出发，沿引用链能走到的对象一律不回收。

所谓内存泄漏，本质就是：**对象在业务语义上已经废弃，但引用链上还挂着，GC 无权回收**。

分代回收（Generational GC）、Scavenge、标记清除（Mark-Sweep）、三色标记等 GC 内部机制不在本篇展开，见 → [V8 垃圾回收机制](../../02-JavaScript/10-性能与优化/V8垃圾回收机制.md)。本篇只讲**工具怎么用、怎么从工具里定位到代码**。

## 二、内存增长 ≠ 内存泄漏：先做判定

这一节是全篇最重要的部分。**大量「内存泄漏」工单最后查出来是误报**，原因是把下面三种情况混为一谈。

### 2.1 三种「内存上涨」的真相

| 现象 | 本质 | 表现特征 | 要不要修 |
| --- | --- | --- | --- |
| **正常缓存增长** | 业务主动缓存（图片缓存、列表数据、状态库） | 涨到某个量级后**趋于平缓**，有上限 | 不用修，必要时给缓存加 LRU 上限 |
| **GC 未及时触发** | V8 觉得还不着急，堆里全是可回收垃圾 | 强制 GC（Collect garbage）后内存**明显掉回去** | 不用修，是假象 |
| **真泄漏** | 废弃对象仍被引用链持有 | 强制 GC 后基线**仍然逐次抬高**，永不回落 | 必须修 |

### 2.2 唯一可靠的判定标准

> **重复相同操作 N 次 + 每次都强制 GC，观察 JS heap 的「基线」是否单调上升。**

「基线」指的是每次 GC 完成后的最低点，而不是曲线的峰值。峰值抖动是正常的，基线抬升才是泄漏。

```
正常（无泄漏）：GC 后回到同一水位
  heap
   │      ╱╲      ╱╲      ╱╲      ╱╲
   │     ╱  ╲    ╱  ╲    ╱  ╲    ╱  ╲
   │ ───╱────╲──╱────╲──╱────╲──╱────╲───  ← 基线水平
   └──────────────────────────────────────► time

缓存增长（可接受）：基线抬升但收敛
  heap
   │              ╱╲    ╱╲    ╱╲
   │        ╱╲   ╱  ╲  ╱  ╲  ╱  ╲
   │   ╱╲  ╱  ╲ ╱    ╲╱    ╲╱    ╲
   │ ─╱──╲╱────╳──────────────────────  ← 基线先升后平
   └──────────────────────────────────────► time

真泄漏：基线持续单调上升，GC 拉不下来
  heap                              ╱╲
   │                        ╱╲     ╱  ╲
   │                ╱╲     ╱  ╲   ╱
   │        ╱╲     ╱  ╲   ╱
   │   ╱╲  ╱  ╲   ╱
   │ ─╱──╲╱────╲─╱  ← 基线一路向上，锯齿整体右上漂移
   └──────────────────────────────────────► time
```

### 2.3 判定阶段的三个纪律

1. **操作必须可重复、可归位**。选一个「做完之后页面应该回到原状」的动作，比如「打开弹窗 → 关闭弹窗」「进详情页 → 返回列表」。做完一轮内存理应回到起点，这样基线才有意义。
2. **必须手动强制 GC**。Memory 面板左上角的垃圾桶图标 **Collect garbage**（Performance 面板录制工具栏也有）。不点这一下，你看到的每一个数字都不可信。
3. **在生产构建（production build）上验证**。开发模式下 React DevTools、HMR、source map、各类 dev warning 都会额外持有对象，很容易得出错误结论。

```js
// 需要在代码里做基线对比时（仅 Chrome，非标准 API，且做了粒度粗化）
console.log(performance.memory.usedJSHeapSize); // ⚠️ 非标准、已不推荐

// ✅ 标准替代：需要跨源隔离（COOP + COEP），返回值包含 iframe/worker 明细
const r = await performance.measureUserAgentSpecificMemory();
console.log(r.bytes, r.breakdown);

// ✅ 想在页面里手动触发 GC 做实验，需要用特定 flag 启动 Chrome：
// chrome --js-flags="--expose-gc"  然后控制台可以调用 window.gc()
// 注意：这只用于本地排查，线上代码里绝不能依赖 gc()
```

## 三、三个入口工具的分工

很多人一上来就打堆快照，结果面对几十万个对象无从下手。正确顺序是**先粗筛、再观察、最后取证**。

### 3.1 Task Manager（浏览器任务管理器）

- 入口：`Shift + Esc`，或菜单 → 更多工具 → 任务管理器。
- 关键动作：**右键表头，勾选「JavaScript 内存」（JavaScript memory）列**，默认是不显示的。
- 两个数要分清：
  - **内存占用（Memory footprint）**：该渲染进程的原生内存总量，包含 DOM、图片、GPU 相关等。
  - **JavaScript 内存**：括号里的数字是**真正活跃（live）的 JS 对象大小**，判断 JS 侧泄漏要看这个。
- ⚠️ **准确性提醒**：Task Manager **没有** DOM 节点数这一列，DOM 节点计数只有 Performance Monitor 有。想「一眼看有没有问题」就看 JavaScript 内存这一列的括号值随时间的走势。

### 3.2 Performance Monitor（性能监视器）

- 入口：DevTools 右上角 `⋮`（More tools）→ **Performance monitor**。注意它和 Performance 面板是两个不同的东西，它是**实时曲线**，不需要录制。
- 可勾选指标：CPU usage、JS heap size、DOM Nodes、JS event listeners、Documents、Document Frames、Layouts / sec、Style recalcs / sec。
- 排查泄漏只盯三条线：

| 曲线 | 一路上升说明什么 |
| --- | --- |
| **JS heap size** | JS 对象在堆积（闭包、数组、Map、组件实例） |
| **DOM Nodes** | 节点被创建后没有被回收 → 极可能是游离 DOM |
| **JS event listeners** | 监听器只加不解绑 → 顺带把回调闭包和整棵子树都留住了 |

> 💡 **DOM Nodes 只升不降是游离 DOM 最强的信号**。反复进出同一个页面，节点数应该在一个区间内波动；如果每轮固定 +200，基本可以直接跳到第八节。

### 3.3 Memory 面板

取证与定位阶段的工具。它开销大、结果需要解读，只在前两步已经确认「确实有问题」之后才用。

### 3.4 分工表与阶段流程

| 阶段 | 工具 | 回答的问题 | 开销 |
| --- | --- | --- | --- |
| ① 粗筛 | Task Manager | 到底有没有问题？涨了多少？ | 极低，可长时间挂着 |
| ② 观察 | Performance Monitor | 是哪一类在涨？和哪个操作相关？ | 低，适合边复现边看 |
| ③ 取证 | Memory 面板 | 具体是哪些对象？谁在持有它们？ | 高，会暂停页面 |
| ④ 验证 | Console `queryObjects()` | 修完之后实例真的没了吗？ | 低，最快的回归手段 |

```
        用户反馈「越用越卡」
                │
                ▼
   ┌────────────────────────────┐
   │ ① Task Manager (Shift+Esc) │  JS 内存有没有单调涨？
   └────────────┬───────────────┘
        没涨 ◄──┤──► 涨了
          │     │
     结束排查   ▼
   ┌────────────────────────────┐
   │ ② Performance Monitor      │  哪条线在涨？
   └────────────┬───────────────┘
                │
       ┌────────┼────────────────┐
       ▼        ▼                ▼
   JS heap   DOM Nodes    Event listeners
       │        │                │
       └────────┴────────────────┘
                │
                ▼
   ┌────────────────────────────┐
   │ ③ Memory 面板：三快照法      │  哪些对象 Delta 为正？
   └────────────┬───────────────┘
                ▼
   ┌────────────────────────────┐
   │ ④ Retainers 保留路径        │  谁在持有它？→ 定位到代码
   └────────────┬───────────────┘
                ▼
   ┌────────────────────────────┐
   │ ⑤ 修复 → queryObjects 验证  │
   └────────────────────────────┘
```

## 四、Memory 面板的几种 Profiling Type

打开 Memory 面板，第一屏就是选择分析类型。选错类型会浪费大量时间。

| 类型 | 中文 | 产出 | 适用场景 | 开销 |
| --- | --- | --- | --- | --- |
| **Heap snapshot** | 堆快照 | 某一瞬间堆里所有对象的完整拓扑 | 已经知道「有泄漏」，要定位**是什么对象、谁持有** | 高，拍摄瞬间页面卡住 |
| **Allocation instrumentation on timeline** | 时间轴分配记录 | 带时间轴的分配柱状图，蓝柱=仍存活，灰柱=已回收 | 要定位泄漏**发生在哪个操作的哪个时刻** | 很高，只能录几十秒 |
| **Allocation sampling** | 分配采样 | 按调用栈聚合的分配量（类似 CPU profiler） | **长时间**运行观察，或想直接看**哪个函数在疯狂分配** | 低，可长时间开 |
| **Detached elements** | 游离元素 | 当前所有游离 DOM 元素列表 | 专查游离 DOM（见第八节） | 低 |

选择建议：

```
不知道是什么对象在泄漏      → Heap snapshot + 三快照法
知道对象但不知道哪步操作产生 → Allocation instrumentation on timeline
泄漏很慢，要挂十几分钟      → Allocation sampling
DOM Nodes 曲线只升不降     → Detached elements
```

> ⚠️ Allocation instrumentation on timeline 里**蓝色柱条代表快照结束时仍然存活的对象**，这些才是嫌疑对象；灰色柱条已经被回收，可以直接忽略。

## 五、Shallow Size vs Retained Size

这是读懂堆快照的地基。看不懂这两个值，快照就只是一堆数字。

| 概念 | 定义 | 直觉 |
| --- | --- | --- |
| **Shallow Size**（自身大小） | 对象**自己**这块内存占多少字节，不含它引用的其他对象 | 「这个盒子本身多重」 |
| **Retained Size**（保留大小） | **如果删掉这个对象，总共能释放多少内存**，包含它独占持有的全部下游对象 | 「拆掉这个盒子，能腾出多大空间」 |
| **Distance**（距离） | 从 GC roots 到该对象的最短引用跳数 | 数字越小离根越近，越难被回收 |

关键点：**Retained Size 只统计「独占」持有的下游**。如果一个大对象同时被别人引用，删掉当前对象也释放不了它，就不计入。

### 5.1 为什么小对象能有巨大的 Retained Size

```
                 (GC roots)
                     │
                     ▼
              ┌─────────────┐
              │  cacheHolder │  Shallow: 32 B
              │  (小对象)     │  Retained: 8.2 MB   ◄── 删掉它能释放 8.2MB
              └──────┬───────┘
                     │ 独占引用
                     ▼
              ┌─────────────┐
              │  Array(1e5)  │  Shallow: 800 KB
              │              │  Retained: 8.2 MB
              └──────┬───────┘
            ┌────────┼────────┐
            ▼        ▼        ▼
        ┌──────┐ ┌──────┐ ┌──────┐
        │record│ │record│ │ ...  │  各 Shallow ≈ 76 B
        └──┬───┘ └──────┘ └──────┘
           │ 独占引用
           ▼
        ┌──────────────┐
        │ detached <div>│  ← 每条 record 还挂着一个游离 DOM 子树
        └──────────────┘

结论：cacheHolder 自己只有 32 字节，但它是这条链的唯一入口，
      Retained Size = 32B + 整棵子树 ≈ 8.2 MB。
      排查时要按 Retained Size 倒序排，而不是 Shallow Size。
```

反例也要注意：

```
        (GC roots)
         │       │
         ▼       ▼
      ┌────┐  ┌────┐
      │ A  │  │ B  │   A、B 都引用 bigData
      └──┬─┘  └─┬──┘
         └──┬───┘
            ▼
      ┌──────────┐
      │ bigData  │  10 MB
      └──────────┘

此时 A 的 Retained Size 里 **不包含** bigData（因为 B 也持有它，
删 A 释放不了）。所以只修一处引用往往内存不降 —— 必须把所有持有方都清掉。
```

> 💡 排序纪律：**Summary 视图点 Retained Size 列倒序**，从大到小逐个看。前 10 个通常就能覆盖 90% 的问题。

## 六、Retainers（保留路径）怎么读

Retainers 是从「发现泄漏对象」到「定位到代码」的**唯一桥梁**。选中 Summary 视图里的任一对象，下方 **Retainers** 面板就会显示「谁在持有它」，可以一层层展开往上追，直到 `(GC roots)`。

### 6.1 读法：从下往上，一层层问「谁引用了我」

```
Retainers 面板（自下而上就是引用链，从被持有者指向持有者）

  detached HTMLDivElement          ← 你选中的泄漏对象
   └─ in element_cache             ← 被某个叫 element_cache 的属性引用
       └─ in context               ← 而这个属性在一个闭包的 context 里
           └─ in bound_this / handler
               └─ in listener      ← 挂在某个 EventListener 上
                   └─ in window    ← 监听器注册在 window 上
                       └─ (GC roots)   ← 到根了：这条链永不回收

解读：window 上的一个事件监听器，其闭包里有个 element_cache，
      缓存了已经从文档移除的 <div> → 定位到注册这个监听器的那段代码。
```

### 6.2 边名（edge name）就是线索

Retainers 里每一行的名字告诉你**这是什么类型的引用**，直接映射到代码结构：

| Retainers 中的边名 | 含义 | 对应代码形态 |
| --- | --- | --- |
| `in context` | 闭包作用域（Closure context）里的变量 | 函数闭包捕获了它 |
| `in <某个属性名>` | 普通对象属性 | `obj.foo = target` |
| `[0]` / `[123]` 这类数字 | 数组元素 | `arr.push(target)` |
| `in table` / 出现在 `Map`/`Set` 下 | Map/Set 的键或值 | `map.set(k, target)`，注意普通 Map 是强引用 |
| `in native_bindings` / `in listener` | 原生绑定、事件监听器 | `addEventListener` 未解绑 |
| `in internal` / `system / Context` | 引擎内部结构 | 通常继续往上看，别停在这里 |
| `(GC roots)` | 已经追到根 | 这条链的源头，就是问题所在 |

### 6.3 `(GC roots)` 意味着什么

看到 `(GC roots)`，说明这条引用链从根可达，**该对象在语义上再废弃也不会被回收**。常见的根有：

- `Window` / 全局对象 → 全局变量、`window.xxx`
- 执行栈上的局部变量 → 通常一瞬即逝，不是泄漏源
- `Document` / DOM 树 → 还在文档里的节点
- 活跃的 `setInterval` / `setTimeout` 回调、`EventListener`
- Pending 的 Promise、未取消的 `AbortController` 关联对象

技巧：

- Retainers 里同一个对象可能有**多条**保留路径，DevTools 默认展示一条最短的。修复时要确认是否还有别的链。
- 每一行右边有 `@12345` 这样的对象 id，跨快照对比时可以用它确认「是不是同一个对象」。
- 展开链的过程中在 Summary 视图搜索框里输入构造函数名做二次过滤，能快速缩小范围。

## 七、三快照法（3-snapshot technique）

内存排查的标准作业流程。目标是：**排除一次性初始化的噪声，只留下「每次操作都稳定增加」的对象**。

### 7.1 完整操作步骤

```
① 打开生产构建页面，进入「稳定状态」（首屏加载完、接口都回来了）
② Memory 面板 → Heap snapshot → 点垃圾桶 Collect garbage → Take snapshot
   → 得到 Snapshot 1（基线）
③ 执行怀疑泄漏的操作 10 次（例：打开弹窗 → 关闭弹窗，重复 10 轮）
④ 点垃圾桶 Collect garbage 强制回收
⑤ Take snapshot → 得到 Snapshot 2
⑥ 用完全相同的方式再执行同样的操作 10 次
⑦ Collect garbage → Take snapshot → 得到 Snapshot 3
⑧ 选中 Snapshot 3 → 视图下拉框切到 Comparison → Base 选 Snapshot 2
⑨ 按 # Delta 或 Size Delta 倒序排，找「正且量级和操作次数成比例」的构造函数
```

### 7.2 为什么是三个快照，不是两个

| 对比 | 包含的内容 | 问题 |
| --- | --- | --- |
| Snapshot 1 → 2 | 真泄漏 **+ 首次操作的一次性初始化**（懒加载模块、单例、首次建立的缓存、字体/图标注册） | 噪声极大，一堆假阳性 |
| **Snapshot 2 → 3** | **只有稳定重复产生的增量** | 一次性初始化在第一轮已经完成，这里剩下的高度可疑 |

再加一条判据：如果第二轮和第一轮做的操作次数相同，那么**真泄漏对象的 `# Delta` 应该和操作次数成比例**（做 10 次涨 10 个或 10 的倍数）。数量对不上比例的，多半是别的因素。

### 7.3 Comparison 视图的四个关键列

| 列 | 含义 | 怎么用 |
| --- | --- | --- |
| `# New` | 新分配的对象数 | 和 `# Deleted` 一起看回收比例 |
| `# Deleted` | 被回收的对象数 | 远小于 `# New` 就是嫌疑 |
| `# Delta` | `# New - # Deleted` | **主排序列**，持续为正 = 泄漏 |
| `Size Delta` | 字节增量 | 判断严重程度，决定修复优先级 |

### 7.4 Summary 视图里的另一条捷径

不切 Comparison 也可以：选中 Snapshot 3，把视图旁边的**类过滤下拉框**切成 `Objects allocated between Snapshot 2 and Snapshot 3`，列表里就只剩这两次快照之间新分配且**仍然存活**的对象——这些天然就是嫌疑名单。

### 7.5 常见干扰项与排除

| 快照里常见但通常不是泄漏 | 原因 |
| --- | --- |
| `(string)` / `(array)` / `(system)` / `(compiled code)` | 引擎内部聚合项，先看具体业务构造函数 |
| DevTools 自身产生的对象 | 关掉不必要的 DevTools 面板，别开着 React DevTools 做取证 |
| Source map、HMR 相关对象 | 换生产构建 |
| 首次点开某个懒加载路由 | 一次性代价，三快照法本身就是为了排除它 |

## 八、游离 DOM（Detached DOM）专题

最经典、最高频，同时也是**最容易在排查中被漏掉**的一类泄漏。

### 8.1 什么是游离 DOM

**游离 DOM（Detached DOM）= 已经从文档树（document tree）中移除，但仍被 JS 引用，因此无法回收的 DOM 节点。**

```
正常回收：
  document ──► <div> ──► <ul> ──► 1000×<li>
  remove() 之后：
  document ──✕  <div>（无人引用）──► ... ──► GC 全部回收 ✅

游离 DOM：
  document ──✕  <div> ◄── cache.list（JS 还持有）
                  │
                  ▼
                <ul> ──► 1000×<li>   ← 整棵子树全部留在内存里 ❌

  关键：只要子树里 **任意一个节点** 还被 JS 引用，
       整棵子树（含父节点方向的 parentNode 链）都无法回收。
```

三个必须理解的性质：

1. **一个引用留住一整棵树**。你只缓存了一个 `<li>`，但 `li.parentNode` 一路往上把整个 `<div>` 子树都留住了。
2. **它同时污染两个指标**：Performance Monitor 的 `DOM Nodes` 和 `JS heap size` 都会涨。
3. **它常常伴随事件监听器泄漏**。节点上挂的监听器，其闭包又会持有组件实例、数据 —— 一条链能拖住几 MB。

### 8.2 在堆快照里怎么找

```
1. Memory 面板 → Heap snapshot → Take snapshot
2. Summary 视图顶部的 Class filter 输入框里键入：Detached
3. 会看到这类条目：
     Detached HTMLDivElement       ×128
     Detached HTMLLIElement        ×1280
     Detached <div class="modal">  （较新 Chrome 会带上标签与类名）
     Detached InternalNode
4. 展开任意一条，看下方 Retainers 面板 → 一层层往上追到 (GC roots)
5. 也可以直接搜 detached，两种大小写写法都试一下
```

配色也是线索：

| 高亮色 | 含义 |
| --- | --- |
| **黄色背景**节点 | 该游离节点**被 JS 直接引用** —— 这就是要修的那个引用点 |
| **红色背景**节点 | 该游离节点自己没有 JS 引用，只是被黄色节点所在的树牵连 —— 修黄色的，红色会跟着一起被回收 |

> 💡 所以排查纪律是：**只找黄色节点、只修黄色节点的持有方**。对着几百个红色节点逐个看是纯浪费时间。

### 8.3 Detached elements 专用面板

较新版本的 Chrome 在 **Memory 面板的 Profiling type 里提供了 `Detached elements`** 这一项（早期以独立的 Detached Elements 面板 / 实验特性形式提供）。

```
用法：
  ① Memory 面板 → 选择 Detached elements
  ② 执行怀疑泄漏的操作（进入 → 退出，重复几次）
  ③ 点 "Get detached elements"（或工具栏的刷新/采集按钮）
  ④ 列表里按元素分组展示当前所有游离元素及数量
  ⑤ 想确认是不是「GC 还没跑」造成的假象，先点垃圾桶 Collect garbage 再采集一次
     —— 采集前 GC 之后还在的，才是真游离
```

对比一下两条路径：

| 方式 | 优点 | 局限 |
| --- | --- | --- |
| **Detached elements** | 直接列出游离元素，零解读成本，开销低，适合快速确认 | 只覆盖 DOM 元素，看不到 JS 侧的持有细节 |
| **Heap snapshot + `Detached` 过滤** | 能顺着 Retainers 一路追到持有它的闭包/数组/Map，定位到代码 | 需要理解 Shallow/Retained/Retainers，开销高 |

实战组合：**先用 Detached elements 确认「有几百个游离 div」→ 再用 Heap snapshot 的 Retainers 找出「是谁在持有」**。

### 8.4 三类典型成因与修复对照

**成因一：缓存了 DOM 引用之后 remove**

```js
// ❌ 缓存里的引用让整棵子树留在内存
const domCache = {};
function openPanel() {
  const panel = document.createElement("div");
  panel.innerHTML = buildHugeList(); // 内含 1000+ 个 <li>
  document.body.appendChild(panel);
  domCache.panel = panel; // 缓存了 DOM 节点
}
function closePanel() {
  domCache.panel.remove(); // 只从文档移除，domCache 还握着 → 游离 DOM
}

// ✅ 移除时同步解除引用
function closePanel() {
  domCache.panel?.remove();
  domCache.panel = null; // 关键：把 JS 侧引用一起断掉
}

// ✅ 或者干脆别缓存节点，缓存「怎么找到它」的信息
const domCache = { panelId: "panel-1" };
const panel = document.getElementById(domCache.panelId);
```

**成因二：事件监听未解绑，把整棵子树留住**

```js
// ❌ 监听器闭包持有 listEl，listEl 又持有整棵列表子树
function mountList(container) {
  const listEl = renderBigList(); // 1000 个 <li>
  container.appendChild(listEl);
  window.addEventListener("resize", () => {
    listEl.style.width = window.innerWidth + "px"; // 闭包捕获 listEl
  });
  // 组件销毁时没有 removeEventListener → window 是 GC root → 永不回收
}

// ✅ 保存 handler 引用并在销毁时解绑
function mountList(container) {
  const listEl = renderBigList();
  container.appendChild(listEl);
  const onResize = () => {
    listEl.style.width = window.innerWidth + "px";
  };
  window.addEventListener("resize", onResize);
  return () => {
    window.removeEventListener("resize", onResize); // 必须传同一个函数引用
    listEl.remove();
  };
}

// ✅ 更省心：用 AbortController 一次性批量解绑
function mountList(container) {
  const ac = new AbortController();
  const listEl = renderBigList();
  container.appendChild(listEl);
  window.addEventListener("resize", onResize, { signal: ac.signal });
  document.addEventListener("scroll", onScroll, { signal: ac.signal });
  return () => ac.abort(); // 所有带该 signal 的监听器一起移除
}
```

> ⚠️ 配套排查技巧：控制台里 `getEventListeners(document.body)` 可以列出某节点上的所有监听器（**DevTools Console 专用命令行 API，不是标准 API**），修复前后各跑一次做对照。

**成因三：ref / 实例变量持有已卸载的节点**

```js
// ❌ React：把 DOM 节点抄到外部（模块级 / 全局 / 外部 store）
let cachedNode = null; // 模块级变量，生命周期跟着整个 bundle
function Chart() {
  const ref = useRef(null);
  useEffect(() => {
    cachedNode = ref.current; // 组件卸载后 cachedNode 仍指向已移除的 DOM
    chartLib.init(ref.current);
  }, []);
  return <div ref={ref} />;
}

// ✅ 卸载时归零，并销毁第三方实例
function Chart() {
  const ref = useRef(null);
  useEffect(() => {
    const instance = chartLib.init(ref.current);
    return () => {
      instance.dispose(); // ECharts / Swiper / Monaco 等都要显式销毁
      cachedNode = null;
    };
  }, []);
  return <div ref={ref} />;
}
```

```js
// ❌ Vue：class 实例上挂 DOM，且第三方库未销毁
export default {
  mounted() {
    this.$el.chartDom = this.$refs.chart;
    this.chart = echarts.init(this.$refs.chart);
    this.bus.$on("refresh", this.redraw);
  },
  // 没有 beforeUnmount → 节点 + 实例 + 事件总线回调全部留住
};

// ✅ 成对清理
export default {
  mounted() {
    this.chart = echarts.init(this.$refs.chart);
    this.bus.$on("refresh", this.redraw);
  },
  beforeUnmount() {
    this.bus.$off("refresh", this.redraw); // 事件总线解绑
    this.chart?.dispose(); // 第三方实例销毁
    this.chart = null; // 解除引用
  },
};
```

> 💡 补充：`ResizeObserver` / `IntersectionObserver` / `MutationObserver` 观察的节点也算引用，销毁时必须 `disconnect()` 或 `unobserve()`，否则同样制造游离 DOM。

## 九、`queryObjects()` 控制台技巧

验证修复效果**最快**的手段，没有比它更省时间的。

```js
// 在 DevTools Console 里执行
queryObjects(MyModalController); // 列出该构造函数创建的所有存活实例
queryObjects(HTMLDivElement); // 列出所有存活的 div（含游离的）
queryObjects(Promise); // 列出所有存活 Promise
```

用法要点：

| 要点 | 说明 |
| --- | --- |
| **只在 Console 可用** | 它是 **DevTools 命令行 API（Console Utilities API）**，**不是标准 JS API**。页面代码里写 `queryObjects(...)` 会直接 `ReferenceError`，也不能写进单测或线上代码 |
| 参数必须是构造函数本身 | 传 `MyClass`，不是 `new MyClass()`；类要在当前作用域可访问（可先 `window.__MyClass = MyClass` 临时暴露，或用 Sources 面板断点在类作用域内执行） |
| 会先触发一次 GC | 调用时 DevTools 会先做垃圾回收，所以返回的都是**真正存活**的实例，天然排除「GC 未跑」的假象 |
| 结果本身会被 DevTools 持有 | 返回的数组存在 Console 里就是一条引用，验证完 `清空控制台` 或刷新页面，别在中途拿它做基线对比 |

典型用法：**验证「组件卸载后实例是否还在」**

```js
// 步骤（在 Console 里手动执行）
// ① 挂载组件前
queryObjects(ModalController); // → []（或 N 个）

// ② 打开关闭弹窗 5 次后
queryObjects(ModalController); // → 泄漏时会看到 5 个实例；修好后仍应是 []（或 N 个）

// ③ 也可以量化
queryObjects(ModalController); // 结果数组在 Console 里，看 length 即可
```

配套的其他 Console 命令行 API（同样非标准，仅 DevTools 可用）：

| 命令 | 用途 |
| --- | --- |
| `getEventListeners(node)` | 列出节点上所有监听器，排查未解绑 |
| `monitorEvents(node, 'click')` | 打印节点上触发的事件，确认监听器是否重复注册 |
| `$0` | 当前在 Elements 面板选中的节点，配合 `getEventListeners($0)` 很顺手 |

## 十、前端五大泄漏模式与 React 专项

### 10.1 五大通用模式速查

| 模式 | 根（GC root） | 排查抓手 | 一句话修法 |
| --- | --- | --- | --- |
| 全局变量意外挂载 | `Window` | 快照里 Retainers 直接指向 `Window` | 开严格模式 / ESLint `no-undef` |
| 定时器未清 | 活跃 timer 回调 | `Timeout` / `Interval` 实例数在涨 | 保存 id，销毁时 `clearInterval` |
| 事件监听未解绑 | `EventListener` | Performance Monitor 的 `JS event listeners` 曲线 | 保存 handler 引用 / `AbortController` |
| 闭包持有大对象 | 闭包所在的函数被根持有 | Retainers 出现 `in context` | 只闭包捕获需要的最小数据 |
| DOM 引用缓存 | 缓存对象被根持有 | 快照里 `Detached` 条目 | `remove()` 之后置 `null` |

### 10.2 React 专项五连

```js
// ❌ 1. useEffect 没有返回清理函数
useEffect(() => {
  const id = setInterval(tick, 1000);
  socket.on("msg", onMsg);
}, []);

// ✅ 成对清理，一个都不能漏
useEffect(() => {
  const id = setInterval(tick, 1000);
  socket.on("msg", onMsg);
  return () => {
    clearInterval(id);
    socket.off("msg", onMsg); // on 必须配 off，且传同一个引用
  };
}, []);
```

```js
// ❌ 2. 闭包捕获陈旧 state（stale closure）：既是 bug 也拖住整份旧 state
useEffect(() => {
  const id = setInterval(() => {
    console.log(list.length); // 永远是首次渲染那份 list，旧数组无法释放
  }, 1000);
  return () => clearInterval(id);
}, []); // 依赖数组为空

// ✅ 用 ref 承载最新值，闭包只持有稳定的 ref 对象
const listRef = useRef(list);
useEffect(() => {
  listRef.current = list;
}, [list]);
useEffect(() => {
  const id = setInterval(() => console.log(listRef.current.length), 1000);
  return () => clearInterval(id);
}, []);
```

```js
// ❌ 3. Context 里塞大对象，且随手往里累加
const CacheContext = createContext(null);
function App() {
  const cacheRef = useRef(new Map()); // 只增不减，跟着 App 的生命周期永久存活
  const put = (k, v) => cacheRef.current.set(k, v);
  return <CacheContext.Provider value={{ put }}>{children}</CacheContext.Provider>;
}

// ✅ 给缓存加容量上限（LRU），并在路由切换等时机主动清理
function App() {
  const cacheRef = useRef(new Map());
  const put = (k, v) => {
    const m = cacheRef.current;
    if (m.size >= 100) m.delete(m.keys().next().value); // 淘汰最旧
    m.set(k, v);
  };
  useEffect(() => () => cacheRef.current.clear(), []);
  return <CacheContext.Provider value={{ put }}>{children}</CacheContext.Provider>;
}
```

```js
// ❌ 4. 未取消的异步请求回来后 setState
useEffect(() => {
  fetch("/api/list")
    .then((r) => r.json())
    .then(setData); // 组件已卸载，闭包仍持有 setData → 整个 fiber 相关引用被拖住
}, []);

// ✅ 用 AbortController 真正取消请求（比 cancelled 标志更彻底）
useEffect(() => {
  const ac = new AbortController();
  fetch("/api/list", { signal: ac.signal })
    .then((r) => r.json())
    .then(setData)
    .catch((e) => {
      if (e.name !== "AbortError") throw e;
    });
  return () => ac.abort();
}, []);
```

```js
// ❌ 5. 事件订阅没在 cleanup 里 off；以及 useSyncExternalStore 订阅泄漏
useEffect(() => {
  store.subscribe(onChange); // subscribe 返回了 unsubscribe，被丢掉了
}, []);

// ✅ 把返回的取消函数直接当 cleanup
useEffect(() => store.subscribe(onChange), [onChange]);
```

## 十一、WeakMap / WeakRef / FinalizationRegistry

弱引用不是「防泄漏万能药」，而是解决**「我想给某个对象附加数据，但不想因此延长它的生命周期」**这一类问题。

| API | 弱在哪 | 典型用途 | 限制 |
| --- | --- | --- | --- |
| `WeakMap` | **键**是弱引用 | 给 DOM 节点 / 实例挂元数据、缓存 | 键**必须是对象**（或 Symbol）；不可遍历、无 `size` |
| `WeakSet` | 成员是弱引用 | 标记「这个对象处理过了」 | 同上 |
| `WeakRef` | 显式持有一个弱引用 | 大对象的可选缓存 | `deref()` 可能返回 `undefined`，必须做兜底 |
| `FinalizationRegistry` | 对象被回收后触发回调 | 释放外部资源（WASM 内存、文件句柄）的**兜底** | **不保证执行、不保证时机**，绝不能承载关键逻辑 |

```js
// ✅ WeakMap：DOM 元数据的标准做法
const meta = new WeakMap();
meta.set(el, { clickCount: 0 }); // el 被移除且无其他引用 → 条目自动消失

// ❌ 普通 Map 是强引用，等于亲手做了一个泄漏池
const meta = new Map();
meta.set(el, { clickCount: 0 }); // el 从文档移除后依然被 Map 的键强引用 → 游离 DOM
```

```js
// ❌ WeakMap 的键不能是原始值
const wm = new WeakMap();
wm.set("userId", data); // TypeError: Invalid value used as weak map key

// ✅ 键必须是对象引用
wm.set(userObj, data);
```

```js
// ✅ WeakRef：可以随时被丢弃的大对象缓存
class ImageCache {
  #ref = null;
  set(bitmap) {
    this.#ref = new WeakRef(bitmap);
  }
  get() {
    const v = this.#ref?.deref();
    return v ?? this.#rebuild(); // ⚠️ deref() 可能是 undefined，必须有重建路径
  }
}
```

```js
// ⚠️ FinalizationRegistry 只能当兜底日志/清理，不能当业务逻辑
const registry = new FinalizationRegistry((key) => {
  console.warn("[leak-probe] 实例已被回收:", key); // 排查期用它验证「到底有没有被回收」很好用
});
registry.register(instance, "ModalController#1");

// ❌ 绝不要这样：回调可能永远不触发（页面关闭、GC 未跑、引擎实现差异）
registry.register(conn, () => conn.close()); // 关连接这种事必须显式做
```

> 💡 排查小技巧：临时用 `FinalizationRegistry` 给可疑组件实例注册一个日志回调，反复进出页面 + 强制 GC。**日志一次都不打**就是泄漏的强证据。

## 十二、完整排查手册

### 12.1 按现象选起点

| 现象 | 最可能的原因 | 从哪个工具开始 |
| --- | --- | --- |
| 页面用久了越来越卡，滚动掉帧 | DOM 节点堆积（游离 DOM）+ 监听器堆积 | Performance Monitor 看 `DOM Nodes` / `JS event listeners` |
| 切换路由内存不降，来回切一直涨 | 组件卸载未清理（定时器/订阅/ref） | 三快照法（每轮 = 进入 + 返回） |
| 长时间运行后标签页崩溃（Out of Memory） | 大对象缓存无上限 / 集合只增不减 | Allocation sampling 长时间挂着 |
| 只有某个弹窗/图表页出问题 | 第三方库实例未 dispose | Heap snapshot 按 Retained Size 倒序 |
| 内存涨但 DOM 节点正常 | 纯 JS 侧：闭包 / Map / 数组 | Heap snapshot + Retainers 看 `in context` |

### 12.2 标准流程（编号步骤，照做即可）

1. **切生产构建**。关掉 React DevTools 等扩展，新开一个干净的窗口，最好用无痕模式排除扩展干扰。
2. **确认问题存在**。`Shift + Esc` 打开 Task Manager，右键表头勾上「JavaScript 内存」，重复操作若干轮，看括号里的活跃值是否单调上升。
3. **定位泄漏类别**。`⋮` → More tools → Performance monitor，勾选 `JS heap size` / `DOM Nodes` / `JS event listeners`，边复现边看哪条线在涨。
4. **排除假象**。Memory 面板点垃圾桶 **Collect garbage**，再看基线。GC 后能回落 = 不是泄漏，收工。
5. **取证**。Heap snapshot 走三快照法（第七节），Comparison 视图对比 Snapshot 2 → 3，按 `# Delta` 倒序，记下 Delta 与操作次数成比例的构造函数。
6. **专查游离 DOM**。如果 `DOM Nodes` 在涨：Memory 面板选 `Detached elements` 采集一次；或在快照的 Class filter 里输入 `Detached`，**只看黄色高亮的节点**。
7. **定位到代码**。选中泄漏对象 → 下方 **Retainers** 面板逐层展开到 `(GC roots)`，按第 6.2 节的边名对照表判断是闭包（`in context`）、数组（`[n]`）、Map（`table`）还是监听器（`listener`）在持有；再去仓库里搜对应的变量名 / 属性名。
8. **补充确认「何时分配」**（可选）。若第 7 步指向不明，换 `Allocation instrumentation on timeline` 录一遍操作，点**蓝色柱条**看它的分配调用栈，直接跳到源码行。
9. **修复**。按第八、十节的 ❌/✅ 对照改，坚持一条纪律：**每一个 `add` / `on` / `subscribe` / `observe` / `setInterval` / `init` 都必须在销毁路径上有配对的反操作**。
10. **验证**。Console 里 `queryObjects(那个构造函数)` 对比修复前后的实例数；游离 DOM 用 `Detached elements` 再采集一次；最后回到第 2 步重跑一遍基线，确认 GC 后能回落。
11. **加防线**。在 CI 或本地脚本里用 Puppeteer / Playwright 跑「重复操作 N 次 + `Runtime.evaluate` 取 heap 基线」的回归用例，把阈值固化下来，防止复发。

### 12.3 取证 Checklist（漏一条结论就不可信）

- [ ] 生产构建，无扩展干扰
- [ ] 操作是「可归位」的（做完应回到原状）
- [ ] 每次快照前都点过 **Collect garbage**
- [ ] 至少三个快照，对比的是 2 → 3
- [ ] 按 Retained Size / `# Delta` 倒序，而不是 Shallow Size
- [ ] 游离 DOM 只追黄色节点
- [ ] Retainers 一路追到了 `(GC roots)`，而不是停在 `internal`
- [ ] 修完用 `queryObjects()` 或 `Detached elements` 做了闭环验证

## 面试高频问答

**Q1：内存一直在涨，你怎么判断到底是不是泄漏？**

先明确一点：**内存增长不等于内存泄漏**。上涨有三种可能：一是业务正常缓存，涨到一定量级会趋于平缓、有上限；二是 GC 还没触发，堆里全是可回收垃圾；三才是真泄漏。判定方法是找一个「可归位」的操作，比如打开再关闭弹窗，重复十几轮，每轮之后在 Memory 面板点垃圾桶图标强制 GC，然后看 JS heap 的**基线**——也就是每次 GC 之后的最低点——是不是单调上升。峰值抖动是正常的，只有基线持续抬高、GC 拉不下来，才叫泄漏。这一步不做，后面全是误报。另外一定要在生产构建上测，开发模式下 HMR、source map、React DevTools 都会额外持有对象。

**Q2：Shallow Size 和 Retained Size 有什么区别？读快照该看哪个？**

Shallow Size 是对象自身那块内存占多少字节，不含它引用的下游。Retained Size 是「删掉这个对象总共能释放多少内存」，包含它**独占**持有的全部下游对象。排查时要按 Retained Size 倒序排，因为泄漏的入口往往是个很小的对象——比如一个几十字节的缓存对象，独占持有一个十万元素的数组，数组里每条记录又挂着一棵游离 DOM 子树，它自己 Shallow 只有 32 字节，Retained 可能有 8 MB。反过来也要注意「独占」这个前提：如果一个大对象同时被两处引用，那它不计入任何一方的 Retained Size，这也解释了为什么有时只改一处引用内存却不降——必须把所有持有方都清掉。

**Q3：什么是游离 DOM？怎么排查？**

游离 DOM 指已经从文档树移除、但仍被 JS 引用因此无法回收的节点。它的杀伤力在于**一个引用能留住一整棵子树**：你只缓存了一个 `<li>`，但通过 `parentNode` 链，整个容器和上千个兄弟节点全都留在内存里，同时还会把节点上的事件监听器及其闭包持有的数据一起拖住。排查分两步：先用 Performance Monitor 看 `DOM Nodes` 曲线，反复进出页面如果节点数只升不降，基本可以确诊；然后要么用 Memory 面板的 `Detached elements` 类型直接采集游离元素列表，要么打堆快照在 Class filter 里输入 `Detached`。快照里**黄色高亮**的节点是被 JS 直接引用的，那才是要修的点；红色的只是被牵连，修完黄色它们会一起被回收。

**Q4：三快照法具体怎么做？为什么要三个而不是两个？**

流程是：进入稳定状态后先强制 GC 打第一个快照作基线；执行怀疑泄漏的操作十次；强制 GC 后打第二个快照；用完全相同的方式再操作十次；强制 GC 打第三个快照；最后切到 Comparison 视图，把 Base 设成 Snapshot 2、对比 Snapshot 3，按 `# Delta` 和 `Size Delta` 倒序找持续为正的构造函数。之所以必须三个，是因为快照 1 到 2 里混了大量**一次性初始化**的噪声——懒加载模块、单例、首次建立的缓存都会在第一轮操作时分配一次并永久存活，这些不是泄漏但会造成一大堆假阳性。而快照 2 到 3 之间那一轮初始化已经完成，剩下的增量就是稳定重复产生的，高度可疑。再加一条判据：真泄漏对象的数量增长应该和操作次数成比例，做 10 次涨 10 个或 10 的倍数。

**Q5：从快照里发现某个构造函数在涨，怎么定位到具体代码？**

靠 **Retainers（保留路径）**，这是从「发现泄漏对象」到「定位代码」的唯一桥梁。选中泄漏对象，下方 Retainers 面板会显示谁在引用它，一层层往上展开直到 `(GC roots)`。每一行的边名就是线索：`in context` 说明被闭包作用域捕获，`[123]` 这样的数字下标说明被数组 `push` 进去了，出现在 Map/Set 的 `table` 下说明是普通 Map 的强引用，`in listener` 说明是事件监听器没解绑。看到 `(GC roots)` 意味着这条链从根可达、永不回收，通常根就是 `Window`、活跃的 timer 或 `EventListener`。拿到属性名或变量名之后回仓库全局搜索就能定位。如果链路指向不明，可以换 `Allocation instrumentation on timeline` 模式录一遍，点蓝色柱条直接看分配时的调用栈。修完用 Console 的 `queryObjects(构造函数)` 对比实例数做闭环验证——注意它是 DevTools 命令行 API，不是标准 JS API，只能在 Console 里用。
